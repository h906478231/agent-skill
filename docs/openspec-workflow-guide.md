# OpenSpec 工作流选择指南

当你面对一个需求或问题时，应该用 `/opsx:explore` 还是 `/opsx:grill`？

本文档帮助你快速判断。

---

## 快速决策树

```text
                需求/问题出现
                     │
                     ▼
              有未决决策吗？
              ┌──────┴──────┐
             YES            NO
              │              │
              ▼              ▼
     决策要先查事实吗？   直接 propose / update
        ┌────┴────┐
       YES        NO
        │          │
        ▼          ▼
 /opsx:explore  /opsx:grill（决策树分轮访谈）
 查清事实后回到判定 → 共识 + CONTEXT.md + docs/adr/
                       │
                       ▼
                 propose / update
```

---

## 两者的本质区别

### openspec-explore：思考伙伴

```text
定位：自由模式的设计探索
目标：想清楚要做什么、怎么做
输出：proposal.md + design.md

特点：
  ✓ 没有固定问题清单
  ✓ 不强制产出格式
  ✓ 可以随时切换方向
  ✓ 思考过程就是价值
```

### openspec-grill：质疑者

```text
定位：决策树访谈 + 假设验证
目标：消除隐含假设、识别遗漏风险
输出：discussion-log.md + CONTEXT.md + ADR

特点：
  ✓ 有明确的决策树
  ✓ 分轮清空frontier
  ✓ 强制区分事实vs决策
  ✓ 沉淀领域资产
```

## 详细判断标准

### 场景1: 需求刚出现，还没想清楚

| 问题 | 回答 | 应该用 |
|------|------|--------|
| 需求是什么？ | 不清楚 | explore |
| 有哪些方案？ | 没想过 | explore |
| 推荐哪个？ | 不知道 | explore |

**示例**：
```text
用户：我想做个Agent功能
你：用什么模型？做哪些能力？怎么保证权限隔离？
→ /opsx:explore
```

---

### 场景2: 方案已确定，准备实施

| 问题 | 回答 | 应该用 |
|------|------|--------|
| 方案定了吗？ | 定了 | 看风险等级 |
| 是否L2/L3？ | 是 | grill |
| 是否BREAKING？ | 是 | 按升级信号定级后处理 |
| 影响范围？ | 单模块/L0/L1 | 可选grill |

**示例**：
```text
设计：streaming replies已经写好了design.md
风险：L2（跨运行时、HTTP、UI）
→ /opsx:grill（检查决策充分性；有有效共识只问未决项）
```

---

### 场景3: 设计到一半发现问题

| 问题 | 回答 | 应该用 |
|------|------|--------|
| 是技术事实问题？ | 是 | explore |
| 是方向性问题？ | 是 | explore |
| 是假设验证问题？ | 是 | grill |

**示例**：
```text
情况1：做到一半发现单表扛不住
→ 回到 /opsx:explore 重新设计

情况2：设计完成，但"用户平均输入50字"这个假设没验证
→ /opsx:grill 验证假设
```

---

### 场景4: 多个技术方案不知道选哪个

```text
这是典型的explore场景：
  1. 列出候选方案（至少 2 个有实质差异的方案，含 MVP）
  2. 四维对比（成本/性能/复杂度/风险）
  3. 推荐方案并说明理由
  
→ /opsx:explore
```

---

## 风险等级 → Grill 要求

| 等级 | 典型变更 | Grill 要求 |
|------|---------|-----------|
| L3 | MQ/异步、并发消费、状态机、大数据量、新建核心表、对外开放接口 | 检查决策充分性；有有效共识直接复用，只访谈未决项 |
| L2 | 新增业务流程、跨模块调用、引入缓存、批量操作 | 检查决策充分性；有有效共识直接复用，只访谈未决项 |
| L1 | 单表单接口 CRUD、新增非核心字段、既有能力的小范围扩展 | 可选 |
| L0 | 纯文案/注释/日志文案、配置值调整、格式化、纯测试补充 | 不需要 |

- 「检查决策充分性」不要求重新访谈一遍：已有共识直接复用，只问未决项。
- 分级与执行规则的事实源：`../skills/openspec-technical-review/shared/gate-levels.md` 与 `../skills/openspec-grill/SKILL.md`；本文档与两者不一致时，以事实源为准。

## 实战案例对照

### 案例A: add-agent-streaming-replies

```text
阶段1: 需求出现
  用户：想要流式输出
  → /opsx:explore
  产出：proposal.md（第一性原理分析）

阶段2: 方案探索
  → 继续 /opsx:explore
  产出：design.md（3个候选方案对比）

阶段3: 实施前决策检查
  风险等级：L2
  → /opsx:grill（应检查决策充分性，当时跳过了）
  实际：用户直接授权实施
  后果：5个假设未确认（H1-H5）
```

**正确流程应该是**：
```text
grill（只访谈未决项） → explore / propose → 实施
```

---

### 案例B: cleanup-agent-documentation

```text
需求：整理文档，减少重复
风险等级：L0（纯文档）
是否需要grill：不需要

流程：
  /opsx:explore（分析文档结构）
  → 直接 propose
  → 实施
```

---

### 案例C: separate-agent-conversations-and-business-tasks

```text
需求：会话与任务分离
风险等级：L3（改变身份关联、确认路由）
BREAKING：是

流程：
  /opsx:grill（检查决策充分性，只问未决项）✓ 应该做
  → /opsx:explore（设计分离方案）
  → propose
  → 实施
```

**实际情况**：看起来没有独立的grill change，可能在explore中完成了假设验证。

## 两者的协作模式

### 模式1: 串行（推荐）

```text
grill → explore / propose → 实施
  ↓            ↓
共识与未决项   方案与正式产物
```

**适用于**: L2/L3变更、存在未决决策的变更

---

### 模式2: 迭代

```text
grill → 访谈中发现事实待查 → explore 查清 → 回到 grill 继续未决项
```

**适用于**: 复杂变更，决策依赖代码现状或外部事实

---

### 模式3: 跳过 grill

```text
explore / propose → 实施
```

**适用于**: L0/L1变更、没有未决决策的变更

---

## Grill 的具体产出

Grill 不改代码、不产出正式 artifact，它的产出是**共识**与**项目级资产**：

### 实际产出位置

```text
项目根/
├── CONTEXT.md         ← 领域术语（跨变更复用）
└── docs/adr/          ← 重大权衡决策（跨变更复用）
    └── 0001-xxx.md

变更目录/
└── discussion-log.md  ← 未决问题与访谈留痕（可选；未决项也可带入 explore 继续）
```

### 共识摘要包含什么

访谈达到结束条件时输出，作为 explore / propose 的输入：

```markdown
## 共识摘要

### 定了什么
- 决策1：XXX（理由：XXX）

### 弃了哪些方案
- 方案B：未采用，理由 XXX

### 开放问题
- 未决项1：XXX（下一步：查事实 / 问用户 / 带入 explore）
```

- 访谈中敲定的术语立即写进 `CONTEXT.md`；满足「难以撤销 / 无上下文会显得反常 / 存在真实权衡」三条件的决策记为 `docs/adr/NNNN-<slug>.md`（格式见 `../skills/openspec-grill/shared/`）。
- Grill **没有签字门禁**，也不产出 `grill-<name>/` 目录。

## 常见误区

### 误区1: "我已经想清楚了，不需要explore"

❌ 错误思维：
```text
我心里有答案 → 直接写design.md
```

✅ 正确流程：
```text
我心里有答案 → /opsx:explore（可能发现新视角）
→ 调整方案或确认方案 → design.md
```

**explore不是"想不清楚才用"，而是"帮助想得更清楚"。**

---

### 误区2: "grill就是写验证文档"

❌ 错误理解：
```text
grill = 写一堆测试用例和边界场景
```

✅ 正确理解：
```text
grill = 决策树访谈 + 消除隐含假设 + 沉淀领域资产

不是你写什么，而是你问了什么、用户回答了什么
```

---

### 误区3: "低风险变更不需要explore，直接写代码"

❌ 危险思维：
```text
改个配置 → 直接改 → 提交
```

✅ 推荐流程：
```text
改个配置 → 想清楚影响范围 → 简单explore或直接propose → 改 → 提交
```

**即使是L0变更，也建议过一遍思考流程。**

## 实用检查清单

### Explore结束检查

在结束explore之前，确认：
- [ ] 问题的根本原因清楚了吗？（第一性原理）
- [ ] 是否有至少 2 个有实质差异的候选方案（含 MVP）？L0/L1 允许单一方案，但要写明不选其他方案的理由。
- [ ] 做了四维对比吗？（成本/性能/复杂度/风险）
- [ ] 推荐方案有理由吗？（为什么不选其他）
- [ ] 可以写proposal.md和design.md了吗？

---

### Grill 结束检查

结束 grill 前，确认：
- [ ] 本次范围内的阻断 frontier 已清空（重要决策已确认，范围外或已延期的问题已记录）？
- [ ] 用户已显式确认共识？
- [ ] 访谈中敲定的术语已写入 `CONTEXT.md`？
- [ ] 满足三条件（难以撤销 / 无上下文会显得反常 / 存在真实权衡）的决策已记为 `docs/adr/` 下的 ADR？
- [ ] 未决问题已记录（`discussion-log.md` 或带入 explore 继续）？

## 快速参考卡片

打印或收藏这个决策表：

| 问题 | 回答 | 用什么 |
|------|------|--------|
| 需求不清楚 | 是 | explore |
| 方案未确定 | 是 | explore |
| 需要对比方案 | 是 | explore |
| 设计已完成 | 是 | 看等级 ↓ |
| 是L2/L3吗 | 是 | grill（检查决策充分性） |
| 有未决决策吗 | 是 | grill |
| 没有未决决策 | 是 | 直接 propose / update |

---

## 总结

记住这三句话：

1. **explore 帮你想清楚方案**（有待查事实时）
2. **grill 帮你消除未决决策**（决策要用户拍板时）
3. **L2/L3 检查决策充分性，L0/L1 可跳过 grill**

当你不确定时，问自己：
- "我现在缺的是方案，还是决策？"
- "这个决策要用户拍板，还是我自己查得到？"

根据答案选择工具。
