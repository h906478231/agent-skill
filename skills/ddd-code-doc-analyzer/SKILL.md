# DDD 代码与文档分析器

> 将已有代码和需求文档转换为结构化的业务描述，作为 `ddd-modeling-workflow` 的输入

## 定位

- 本 skill 是代码和文档的**分析提取器**，不负责建模
- 输出格式化的业务描述，供 `ddd-modeling-workflow` 消费
- 不负责生成流程图，不负责文件落盘

## 输入

- **代码路径**：包含已有业务逻辑的代码目录或文件列表
- **文档路径**（可选）：需求文档、设计文档、API 文档等
- **分析范围**（可选）：指定要分析的业务模块或子域

## 输出

统一的业务描述文本，包含：

1. **业务目标与核心场景**
2. **业务术语表**
3. **参与者与外部系统**
4. **业务流程描述**
5. **隐含的业务规则与约束**
6. **待确认问题清单**

## 执行流程

### 阶段 1：代码结构分析

**目标**：理解代码的技术结构，识别可能的领域边界

**执行规则**：
1. 扫描代码目录结构，识别模块划分
2. 识别主要的类、接口、方法签名
3. 提取类之间的依赖关系和调用链
4. 识别数据模型（实体、DTO、VO）
5. 识别可能的聚合边界（通过类的内聚性判断）
6. 识别持久化相关代码（Repository、Mapper）
7. 识别事件相关代码（EventListener、EventPublisher）

**分析线索**：
- `@Service` / `@Component` → 可能的应用服务或领域服务
- `@Entity` / `@Table` → 数据模型（不一定等于聚合）
- `@Transactional` → 事务边界，可能对应一个用例
- `@EventListener` / `@EventHandler` → 事件监听器，可能对应 Policy
- `Repository` / `Mapper` 接口 → 聚合持久化
- 命名模式（`XxxCommand`、`XxxEvent`、`XxxPolicy`）→ DDD 组件

**输出格式**：
```markdown
## 代码结构分析

### 模块划分
- 模块 A：用户管理（`com.example.user`）
- 模块 B：订单管理（`com.example.order`）

### 主要类清单
| 类名 | 类型 | 职责推测 | 依赖的其他类 |
|------|------|---------|-------------|
| OrderService | Service | 订单业务逻辑 | OrderRepository, InventoryService |
| Order | Entity | 订单实体 | OrderItem |

### 可能的聚合边界
- Order + OrderItem（生命周期绑定，总是一起加载）
- UserAccount（独立生命周期）

### 事件相关代码
| 事件类 / 监听器 | 触发点 | 监听动作 |
|----------------|--------|---------|
| OrderCreatedEvent | OrderService.createOrder() | NotificationService 发送通知 |
```

---

### 阶段 2：业务语义提取

**目标**：从代码和文档中提取业务含义

**执行规则**：
1. **从方法名推测业务动作**：
   - `createOrder()` → 创建订单
   - `cancelOrder()` → 取消订单
   - `verifyPayment()` → 验证支付

2. **从类名推测业务对象**：
   - `Order` → 订单
   - `UserAccount` → 用户账号
   - `InventoryItem` → 库存商品

3. **从注释/文档提取业务规则**：
   - 代码注释中的"必须"、"不能"、"当...时"
   - 文档中的业务约束、前置条件、后置条件

4. **从数据流推测事件**：
   - 状态字段变化 → 可能对应领域事件
   - 数据库写入 → 可能对应聚合状态变更

5. **从异常处理推测业务规则**：
   - `throw new InsufficientStockException()` → 库存不足时不能下单

6. **从事务边界推测用例边界**：
   - 一个 `@Transactional` 方法可能对应一个完整的业务用例

**分析策略**：
- 优先分析文档（业务意图更明确）
- 代码用于验证和补充文档
- 代码和文档冲突时，标注为待确认问题

**输出格式**：
```markdown
## 业务语义提取

### 业务目标
从代码和文档中推测：
- 支持用户在线下单购买商品
- 支持订单支付与发货流程
- 支持库存管理

### 业务术语表
| 术语 | 定义来源 | 定义 |
|------|---------|------|
| 订单 | Order.java + 需求文档 | 用户一次购买行为对应的业务对象 |
| 库存 | InventoryService.java | 商品的可售数量 |

### 业务流程
根据代码调用链推测：
1. 用户发起下单 → OrderService.createOrder()
2. 系统校验库存 → InventoryService.checkAvailable()
3. 创建订单 → Order.create() → 保存到数据库
4. 发布订单创建事件 → OrderCreatedEvent
5. 监听器收到事件 → NotificationService 发送通知

### 隐含的业务规则
从代码中提取：
- 规则 1：库存不足时不能下单（from: InventoryService.checkAvailable()）
- 规则 2：订单创建后状态为"待支付"（from: Order.create()）
- 规则 3：支付成功后自动通知发货（from: PaymentSuccessListener）

### 参与者与外部系统
| 类型 | 名称 | 识别依据 |
|------|------|---------|
| Actor | 用户 | Controller 接收的请求主体 |
| 外部系统 | 支付平台 | PaymentGatewayClient.pay() |
```

### 阶段 3：生成统一业务描述

**目标**：将提取的信息整合为 `ddd-modeling-workflow` 可消费的格式

**输出格式**：
```markdown
# 业务需求描述

## 业务背景
从代码和文档中提取：
{整合的业务目标和背景}

## 核心场景
1. 用户下单购买商品
2. 用户支付订单
3. 系统通知发货
4. ...

## 业务术语
{术语表}

## 参与者
{参与者清单}

## 外部系统
{外部系统清单}

## 业务流程与规则
{详细的业务流程描述，包含条件、分支、异常处理}

## 待确认问题
- Q1：代码中 OrderService.cancelOrder() 允许取消已支付订单，但文档未提及，需确认是否为遗留代码
- Q2：InventoryService 未发现库存扣减的回滚逻辑，超时未支付订单的库存如何恢复？
```

## 核心原则

### 分析原则
- **代码是真相**：代码反映实际实现，但可能包含技术债务
- **文档是意图**：文档反映业务意图，但可能过时
- **交叉验证**：代码和文档冲突时，标注为待确认问题
- **保守推测**：不确定的业务语义标记为"推测"，不凭空补齐

### 质量原则
- 提取的业务描述应该让不懂代码的业务专家能理解
- 技术细节（框架、注解、持久化）不进入业务描述
- 聚焦业务语义，不聚焦代码质量

### 边界原则
- 本 skill 只负责提取和转换，不负责建模
- 不输出领域事件、聚合、命令等 DDD 产物（由 `ddd-modeling-workflow` 输出）
- 不生成流程图（由 `ddd-event-storm-visualizer` 输出）

## 使用示例

### 示例 1：分析 Java 项目

**输入**：
```
代码路径: /path/to/project/src
文档路径: /path/to/docs/requirement.md
分析范围: 订单模块
```

**执行**：
1. 扫描 `com.example.order` 包下的所有类
2. 读取 `requirement.md` 中关于订单的需求描述
3. 提取业务语义并生成统一描述

**输出**：
提供给 `ddd-modeling-workflow` 的业务需求描述文本
