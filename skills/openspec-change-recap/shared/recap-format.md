# 完成清单格式与内容规则（唯一事实源）

> 完成清单 `recap.md` 是一个已归档变更的单页文件，回答「这个变更交付了什么、没有交付什么」。它是派生视图，可以重新生成。
> 编写方：`/opsx:archive` 第 7 步与 `/opsx:recap <变更名>`，由一个子 agent 生成（`../SKILL.md`）。检查方：`recap.mjs check`。读取方：`recap.mjs list`（跨变更总表，只读头部字段）。
> 脚本 `<RECAP>` = `../scripts/recap.mjs`（相对本文件）；其他 skill 用 `../openspec-change-recap/scripts/recap.mjs` 解析，读不到时 Glob 搜 `**/openspec-change-recap/scripts/recap.mjs`。运行需 Node.js ≥ 16，不需要 `npm install`。

## 文件格式

位置：`<archiveDir>/<YYYY-MM-DD>-<变更名>/recap.md`。只有已归档的变更有完成清单。

```markdown
# 完成清单：eval-harness-v2

- 归档日期：2026-10-28
- 分级：L0
- 主题：评测与测试
- 摘要：新增 6 个单阶段评测用例与阶段快照检查

## 新增
## 修改
## 删除
## 修复
## 没做与遗留
## 落点
```

| 部分 | 规则 |
|---|---|
| 标题行 | 第一行固定为 `# 完成清单：<变更名>`。变更名等于归档目录名删除 `YYYY-MM-DD-` 前缀之后的部分 |
| 头部字段 | 标题行之后按顺序写 4 个列表项：`- 归档日期：`、`- 分级：`、`- 主题：`、`- 摘要：`，值不能为空 |
| `归档日期` | `YYYY-MM-DD` 格式、日历中存在的日期，等于归档目录名的日期前缀 |
| `分级` | 取值域与读法见下文「分级的取值与读法」 |
| `主题` | 一个短语，用于跨变更总表分组。复用与保留规则见 `../SKILL.md`「主题」 |
| `摘要` | 一句话，写这个变更交付的主要结果 |
| 二级标题 | 头部字段之后按顺序写 `## 新增`、`## 修改`、`## 删除`、`## 修复`、`## 没做与遗留`、`## 落点` |
| `无` | 一类没有事项时，这一节只写一行 `无` |
| `未定义` | 产物没有写出的信息写 `未定义`，不用常识补全。读者由此区分「没有读到」与「没有」 |

- 头部字段用列表项，与 `verification.md` 的头部写法一致，脚本用行首匹配解析。不使用 YAML front matter。
- `归档日期` 与变更名都能从归档目录名得到。`check` 比较两者，发现手改或复制错误。

### 分级的取值与读法

`分级` 只写等级或方案类型，取值为 `L0`、`L1`、`L2`、`L3`、`MVP`、`未定义` 之一，不写判定人、日期与依据。同一个变更在归档门禁与完成清单中得到同一个分级。

读法与归档门禁的 `readTier`（`../../openspec-technical-review/scripts/implementation-gate.mjs`）相同，按顺序：

1. 读 `overview.md` 中以 `分级：` 开头的一行（行首可以有 `>`），取第一个 `｜` 之前的字段。
2. 字段含 `MVP` 时写 `MVP`。字段同时有 `MVP` 与等级时也写 `MVP`。
3. 否则写字段中的 `L0`–`L3`。字段中没有等级时，查整行。
4. 没有 `分级：` 行、但有旧写法 `方案类型：MVP` 开头的一行时，写 `MVP`。
5. `overview.md` 读不到等级时（没有文件、没有分级行、或写「未判定」），取 `review-summary.md` 中 `Gate-Level:` 行的值。
6. 都没有时写 `未定义`。

示例：

| 分级行 | `分级` |
|---|---|
| `> 分级：L0 豁免 ｜ 判定人：用户 ｜ 日期：2026-10-14 ｜ 依据：…` | `L0` |
| `> 分级：L0 豁免。判定人：用户。日期：2026-10-12。依据：…`（没有 `｜`） | `L0` |
| `> 分级：方案类型 MVP ｜ 升级信号：无 ｜ …` | `MVP` |
| `> 分级：完整方案 ｜ … ｜ 依据：属于 L2` | `L2`（字段中没有等级，查整行） |
| 没有 `overview.md`，`review-summary.md` 有 `Gate-Level: L1` | `L1` |

`check` 检查取值域，值不在取值域时写入 `blocking`。

## 内容来源

完成清单以实际结果为准。下表之外的来源不能写入完成清单。

| 分类 | 来源 | 不能作为来源 |
|---|---|---|
| `新增`、`修改`、`删除` | `tasks.md` 中已勾选的任务；delta specs 的 `ADDED`、`MODIFIED`、`REMOVED` 要求 | `proposal.md` 的 What Changes |
| `修复` | 变更开始前已经存在、由已勾选任务或 delta 要求修正的缺陷 | 评审中发现的本变更新代码的问题 |
| `没做与遗留` | `design.md` 中移出范围的决策；未勾选的任务；双轴报告中状态为 `open` 的 finding（读法见下文）；Risk Accepted；`pending-environment` 的切片（切片证据的 `## 待环境补测`）；`deployment.md` 的条目 | 对话内容 |
| `落点` | 主规格同步结果；切片证据 `## 变更文件` 的并集，按第一级目录计数 | 当前工作区的 git diff |

- `proposal.md` 只作参考。它的 What Changes 在实现前编写。只有已勾选任务或 delta 要求支持的条目才能写入 `新增`、`修改`、`删除`。
- 不读取当前工作区的 git diff：归档后的工作区已经包含其他变更的修改。
- 不读取对话内容：换会话后对话丢失，完成清单的结果必须能从归档目录重新得到。

### 修复的口径

`修复` 只列出变更开始前已经存在的缺陷。评审 finding 修正的是本变更新写的代码，修正结果已经体现在 `新增` 与 `修改` 中，不重复列出。

例如 `close-tier-review-leftovers` 修正上一个变更留下的 STD-13、STD-14，这两项写入 `修复`。本变更新增文件上的 finding 即使已经关闭，也不写入 `修复`。

### Finding 状态的读法

Finding 状态只从实现后的双轴报告 `review/standards.md`、`review/spec-fidelity.md` 读取：

1. 报告有 `## Finding 台账` 一节时，只读台账的 `状态` 列。Findings 表与台账会重复出现同一个 ID，不读 Findings 表。
2. 报告没有台账时（旧格式，例如 `2026-10-08-add-change-model-visualization`、`2026-10-12-add-explainer-video`），读 `## Findings` 表的最后一列 `闭环状态`：空值按 `open`，`risk-accepted` 计入 Risk Accepted，同一 ID 只计一次。
3. 两处都没有状态时，`## 没做与遗留` 的 finding 部分写 `未定义`，不写 `无`。读者由此区分「没有读到」与「没有遗留」。
4. 编码前的五维报告（`review/<role>.md`，例如 `review/database.md`）不读取：这些报告的 finding 在 `design.md` 的「评审意见闭环记录」中关闭，报告的 `闭环状态` 列不改。

- 一份报告中 `open` 的 finding 合并成一条事项，写出数量、每个严重级别的数量与 ID，例如「`review/standards.md` 有 8 个 `open` 的 finding：Minor 7 个、Major 1 个（STD-02～STD-08、STD-10）」。
- 状态为 `risk-accepted` 的 finding 单独写一条 Risk Accepted 事项，写出 ID 与留痕位置。
- 状态为 `closed`、`false-positive` 的 finding 不写入 `没做与遗留`。
- 变更没有双轴报告时（L0、L1 可以不运行 `/opsx:quality`），finding 部分写「没有双轴评审报告」，不写 `无`。

### 事项的写法

- 每条事项是一句话，写成列表项。
- `新增`、`修改`、`删除`、`修复` 的每条事项以 `（<落点>）` 结尾，落点写文件、目录或主规格，例如 `（claude/commands/opsx/recap.md）`。
- 每类最多 8 条。超过时把同一来源的事项合并，例如同一个目录的多个文件合并为一条。
- `## 落点` 写两部分：
  - 主规格：delta specs 中每个能力对应的 `openspec/specs/<能力>/spec.md`，写出 `ADDED`、`MODIFIED`、`REMOVED` 要求的数量。主规格文件不存在时如实写「主规格文件不存在」。
  - 文件：切片证据 `## 变更文件` 的并集，按第一级目录计数，例如「`skills/` 5 个、`scripts/` 3 个」。变更没有 `evidence/` 目录时写 `文件：未定义`。

### 完成清单描述归档时的状态

完成清单描述变更归档时的状态。归档之后才修正的 finding，在完成清单中仍为 `open`。需要反映新状态时，重新生成完成清单（`/opsx:recap <变更名>`）：归档目录中的产物不会因后续修正而改变，重新生成的结果也相同。
