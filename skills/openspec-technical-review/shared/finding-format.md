# finding 统一格式（所有评审角色共用）

> 本文件是 finding 字段与维度结论的**唯一事实源**。角色提示词、SKILL.md、命令、workflow 脚本一律引用本文件，不复制。
> 路径：`<SKILL_DIR>/shared/finding-format.md`

## 设计原则

技术评审的产出要让**非技术方案作者**也能理解：
1. **业务因果清晰**：这个技术问题影响哪个用户功能、什么业务场景
2. **代码定位明确**：需要改哪些模块、类、方法、表
3. **改动范围可估算**：能看出工作量，能分配到具体任务

## 字段

每条 finding 必须含以下 **9 个字段**，缺一不可：

| 字段 | 内容 | 说明 |
|------|------|------|
| `ID` | 维度前缀 + 序号，如 `ARCH-01` | 前缀见各角色提示词，不得与历史 ID 冲突 |
| `严重级别` | `Blocker` / `Major` / `Minor` | - |
| `影响业务功能` | 用户视角的功能名称 | **新增**：如"素材上传"、"消息收藏"、"客户列表查询" |
| `位置` | 指向 `design.md` 的具体章节 | 实现层评审则指向 `文件:行` |
| `涉及代码模块` | 需要改动的代码位置 | **新增**：如"MaterialService.upload"、"material 表"、"MessageCollectionController" |
| `一句话白话` | 用大白话说清「哪里会出什么事」 | 不得出现未解释的专有名词 |
| `触发场景` | 什么条件下会真的发生 | 必须可复现，写不出来降级为 Major |
| `不修的后果` | 影响面 + 严重度 | 不写空话，要写清具体影响 |
| `建议修复` | 具体到可执行的动作 | 要说清改哪里、怎么改、为什么这样改 |

表格写法：

```markdown
| ID | 严重级别 | 影响业务功能 | 位置 | 涉及代码模块 | 一句话白话 | 触发场景 | 不修的后果 | 建议修复 |
|----|---------|------------|------|------------|-----------|---------|-----------|---------|
| CONC-01 | Blocker | 消息同步 | §4.1 幂等设计 | MessageSyncService.consumeMessage、message_consume_log 表 | 同一条消息被消费两次，计数会多加一次 | MQ 至少一次投递下消费者超时后重投；两个消费者同时处理同一 msg_id，都读到 count=5，都写 count=6 | 客户看到的联系人总数偏大，且无法自愈，需人工对账修数 | 1. message_consume_log 表的 msg_id 字段加唯一索引；2. MessageSyncService.consumeMessage 方法改用 `UPDATE contact_stat SET count=count+1, version=version+1 WHERE id=? AND version=?` 并判断 affected=1 |
```

## 五条硬规则

这些规则是为了让**没参与设计的人**也能理解问题、评估影响、执行修复 —— 门禁的读者不只是方案作者。

### 1. 「影响业务功能」必须用用户视角的功能名称

写清这个技术问题影响哪个用户可见的功能或业务流程。不能只写技术组件名。

- ✅ 「素材上传」「消息收藏」「客户列表查询」「企微同步」
- ✅ 「素材上传 → 暂存资源清理环节」（如果只影响某个子流程）
- ❌ 「MessageSyncService」（这是代码模块，不是业务功能）
- ❌ 「幂等处理」（这是技术手段，不是业务功能）

**为什么重要**：让产品经理、测试、项目经理能快速判断影响范围，决定是否需要延期发布。

### 2. 「涉及代码模块」必须精确到类/方法/表

列出需要修改的具体位置，让开发能直接定位。至少包含：
- **服务类和方法**：如 `MaterialService.upload`、`MessageCollectionController.collect`
- **数据库表和字段**：如 `material 表的 created_at 字段`、`quota_usage 表增加 fencing_token 列`
- **配置文件或常量**：如 `application.yml 的限流配置`、`RateLimitConstants.MAX_SYNC_PER_MINUTE`

格式示例：
- ✅ 「MaterialService.upload 方法、StagingBatchService.cleanup 方法、staging_batch 表增加 status/fencing_token 字段」
- ✅ 「MessageCollectionController.collect、AuthorizationService.checkMessagePermission、message_collection 表的唯一索引」
- ❌ 「后端代码」（太笼统）
- ❌ 「数据库」（哪个表？）

**为什么重要**：让任务分配和工作量评估有依据，避免"看起来很小，改起来牵一发动全身"。

### 3. 「一句话白话」不得出现未解释的专有名词

写给不了解本方案细节的人看。出现幂等、CAS、IDOR、N+1、公式注入这类词时，要么换成大白话，要么当场用半句话解释。

- ✅ 「同一条消息被消费两次，计数会多加一次」
- ✅ 「恶意用户知道消息 ID 后，可以收藏别人的私密聊天记录」
- ❌ 「幂等性缺失导致 at-least-once 语义下状态机非幂等累加」
- ❌ 「存在 IDOR 漏洞」（要说清楚是什么）

**为什么重要**：让签字人真正理解风险，而不是被术语吓住就签字或拒签。

### 4. 「触发场景」必须可复现，写不出来的 Blocker 一律降级为 Major

必须说清这四类中至少一类的具体取值，并写出**可观测的现象**（报错信息、数据错乱的表现、超时、内存增长）：

| 触发维度 | 要写清什么 |
|---------|-----------|
| 输入 | 什么参数 / 什么文件 / 什么字符 |
| 时序 | 谁和谁并发、按什么顺序交错 |
| 数据量 | 多少条 / 多大 / 什么增长速度 |
| 故障 | 超时、重启、网络抖动、部分成功 |

示例：
- ✅ 「用户 A 和用户 B 同时上传素材到企业 X，两个请求都读到 used_count=199，都写入 used_count=200，实际创建了 201 个素材，超过 200 上限」
- ✅ 「用户在上传 500MB 视频时，上传到 80% 网络断开，重新上传后系统创建了两个暂存批次，占用双倍存储」
- ❌ 「高并发场景下可能出现问题」（什么并发？多高？）
- ❌ 「理论上存在竞态条件」（如何复现？）

**只能写出「理论上可能有风险」而给不出具体触发场景的，不得判 Blocker，降级为 Major 并注明「触发条件未确认」。**

**为什么重要**：一是逼着评审说人话而不是堆术语；二是压住 AI 误报 —— 编不出复现路径的问题，多半本来就不成立，不该卡住整个变更。

### 5. 「不修的后果」不写空话

要写影响面（哪些用户 / 哪些数据 / 哪个接口）+ 严重度（能否自愈、要不要人工修数、是否有数据泄露）。

- ✅ 「企业 X 的所有用户看到的联系人总数偏大，且无法自愈，需运维人工对账修数，影响月度报表」
- ✅ 「恶意用户可以遍历收藏其他销售与客户的聊天记录，泄露商业机密，违反 PIPL 个人信息保护法」
- ✅ 「正在上传的 500MB 视频被清理任务删除，用户重新上传耗时 10 分钟，投诉率上升」
- ❌ 「可能影响数据准确性」
- ❌ 「存在安全风险」

**为什么重要**：让决策者能判断风险是否可接受，是否需要 Risk Accepted 而不是修复。

## 维度结论（verdict）

每份评审末尾给出该维度结论，三值之一：

| 结论 | 含义 |
|------|------|
| `通过` | 无 Blocker，可进入下一步 |
| `有条件通过` | 无 Blocker，但存在必须落地的前提条件 |
| `打回` | 存在未闭环 Blocker |

- 存在未闭环 Blocker（含「上轮声称已闭环但实际未闭环」）时，结论**必须**为 `打回`，并单独列出 Blocker 清单。
- **「有条件通过」的每一条条件都必须能映射到 `tasks.md` 的一个可勾选任务项**；映射不上的条件视同 Blocker —— 它没有落地路径，写完就没人管。

## 「建议修复」的写法要求

修复建议必须说清楚三点：**改哪里 + 怎么改 + 为什么**

### 改哪里
列出具体的代码位置（服务类、方法、表、字段、配置），与「涉及代码模块」呼应。

### 怎么改
给出可执行的步骤，如果涉及算法或数据结构变更，要说清楚：
- **数据库改动**：建表语句、加字段、改索引、加约束
- **代码逻辑改动**：用什么 API、加什么判断条件、改什么查询语句
- **配置改动**：加什么配置项、设置什么值

示例：
- ✅ 「1. message_consume_log 表的 (corp_id, msg_id) 加唯一索引；2. MessageSyncService.consumeMessage 方法改用 `UPDATE contact_stat SET count=count+1, version=version+1 WHERE id=? AND version=?` 并判断 affected=1，如果 affected=0 说明版本冲突，放弃本次写入」
- ❌ 「使用乐观锁」（太抽象，不知道怎么做）

### 为什么这样改
用一句话解释这个修复如何解决问题，建立**技术手段**与**业务影响**的因果链。

示例：
- ✅ 「唯一索引保证数据库层面同一 msg_id 只能插入一次；版本号机制保证并发更新时只有一个成功，避免计数多加」
- ✅ 「通过 JWT token 提取 corpId，而不是从请求参数读取，防止用户篡改企业 ID 跨租户越权」

### 完整示例

| 建议修复 |
|---------|
| **改哪里**：1. `quota_usage` 表结构；2. `MaterialService.create` 方法；3. `MaterialService.delete` 方法<br>**怎么改**：1. `quota_usage` 表的 `owner_id` 字段改为 `NOT NULL DEFAULT '0'`，唯一键固定为 `(corp_id, category, user_type, region, owner_id)` 五维；2. `MaterialService.create` 改用 `UPDATE quota_usage SET used_count=used_count+1 WHERE corp_id=? AND category=? AND user_type=? AND region=? AND owner_id='0' AND used_count<max_count`，检查 `affected=1` 才继续创建素材；3. `MaterialService.delete` 改用 `UPDATE quota_usage SET used_count=used_count-1 WHERE ... AND used_count>0`<br>**为什么**：用数据库的行锁 + WHERE 条件实现原子性配额占用/释放，避免读-改-写的并发窗口；owner_id 非空避免 NULL 在唯一键中的语义问题 |
