# ADR（架构决策记录）格式与门槛

> 本文件是 ADR 格式的唯一事实源。ADR 存于 `docs/adr/`（项目级资产：提交 git、不随 `openspec archive` 归档），目录懒创建——第一条 ADR 需要时才建。

## 三条件门槛（全满足才记，缺一跳过）

1. **难以撤销**：事后改主意的代价显著（换存储、改事件契约、调整限界上下文边界）
2. **无上下文会显得反常**：半年后的读者看代码会问「为什么这么搞？」
3. **真实权衡的产物**：存在真正的备选项，且因为具体理由选了这个

好撤销的决策跳过（改回来就是了）；不反常的跳过（没人会问）；没有真实备选的跳过（那就是显然的事）。

**ADR 泛滥比没有 ADR 更糟**——每条都记，读者就一条都不读了。

## 模板

```markdown
# {决策的一句话标题}

{1–3 句：什么背景、定了什么、为什么。}
```

就这些。ADR 可以只有一段。**价值在于记录「做过这个决定」和「为什么」，不在于填满章节。**

## 可选小节（真正有用才加）

- **Status**（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策会被重新讨论时才需要
- **Considered Options**：被否的备选项值得被记住时才需要
- **Consequences**：非显然的下游影响需要专门指出时才需要

## 编号

扫 `docs/adr/` 取当前最大号 +1：`0001-slug.md`、`0002-slug.md`…

## 什么够格（对照清单）

- **架构形态**：用单体仓 / 写模型事件溯源、读模型投影
- **领域间集成模式**：Ordering 与 Billing 通过领域事件通信，不走同步 HTTP
- **带锁定的技术选型**：数据库、消息中间件、认证方式、部署目标——换一下要花一个季度的那种；不是每个依赖库
- **边界与归属决策**：客户数据归 Customer 上下文，其他上下文只按 ID 引用——明确的「不」与「是」同样有价值
- **对显然路径的刻意偏离**：手写 SQL 不用 ORM 因为 X。不记，下一个工程师会把它「修掉」
- **代码里看不见的约束**：合规原因不能上云、合作方接口契约要求 P99 < 200ms
- **非显然的被否方案**：考虑过 GraphQL 选了 REST 且理由微妙——不记，六个月后有人会再提 GraphQL

## 与 OpenSpec 变更的关系

- ADR 记**跨变更长期有效**的决策；design.md 记**单次变更**的方案
- grill 访谈中冒出的三条件决策 → 当场提议记 ADR，用户同意后立即写入
- design.md 的「推荐方案及决策依据」涉及三条件决策时，引用 ADR 编号而不是复述理由（单一事实源）
