# OpenSpec 工作流 5 分钟上手指南

> **给新人的话**：看完这一页，你就能开始第一个变更。不用记住所有细节，跟着例子走一遍就懂了。

---

## 🎯 核心理念：一句话记住

**大改动先想清楚，小改动直接改，改完让 AI 帮你检查。**

```
小改动（文案/注释/配置）
    ↓
 直接改代码 → 提交
 
大改动（新功能/跨模块/表结构）
    ↓
 先聊天想清楚 → AI 检查方案 → 人工签字 → 写代码 → 验证 → 归档
```

---

## 🚦 第一步：判断你的变更属于哪一类

### 3 个问题快速分级

```
┌─────────────────────────────────────────────────┐
│ Q1: 是否只改文案、注释、配置、格式？              │
│     是 → L0 豁免（直接改，无需门禁）              │
│     否 → 继续                                    │
└─────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────┐
│ Q2: 是否涉及以下任一关键词？                      │
│     • 异步 / MQ / 消息队列                       │
│     • 批量操作 ≥ 1 万条                          │
│     • 新建表 / 改表结构 / 改字段类型              │
│     • 对外开放接口 / 处理用户上传                │
│     • 租户隔离 / 权限判定 / 敏感数据              │
│     是 → L3 全量门禁（5 维度，4-8 分钟）          │
│     否 → 继续                                    │
└─────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────┐
│ Q3: 是否跨模块调用、引入缓存、或新增业务流程？     │
│     是 → L2 标准门禁（4 维度，3-6 分钟）          │
│     否 → L1 轻量门禁（2 维度，2-4 分钟）          │
└─────────────────────────────────────────────────┘
```

**拿不准就升一级** —— 漏评审的代价远高于多跑一个维度。

## 📖 完整示例：给用户表加"昵称"字段

假设你的任务是：给用户表加个 `nickname` 字段，用于显示在个人主页。

### 场景判定

```
Q1: 只改文案/注释？
    否（要加字段）
    
Q2: 涉及 MQ/异步/大批量/对外接口？
    否（只是加个字段）
    
Q3: 跨模块调用或新增业务流程？
    否（单表单字段，不跨模块）
    
→ 结论：L1 轻量门禁（database + security 两维度）
```

---

### Step 1：先聊天（想清楚）

运行命令：

```bash
/opsx:explore add-user-nickname
```

**AI 会问你**：
- 为什么要加这个字段？（第一性原理分析）
- 长度限制是多少？有没有特殊字符限制？
- 是否可以为空？默认值是什么？
- 需要唯一吗？需要索引吗？
- 有没有敏感信息？需要脱敏吗？

**你回答后，AI 会生成**：

```
openspec/changes/add-user-nickname/
├── proposal.md          ← 需求澄清（含第一性原理分析）
└── design.md            ← 技术方案（含候选方案对比）
```

**典型的 proposal.md 内容**：

```markdown
## 第一性原理分析

### 表面需求 vs 底层问题
- **用户提出的需求**：给用户加个"昵称"字段
- **真正要解决的问题**：用户希望展示个性化名称而非真实姓名
- **是否存在需求误解**：确认不是"用户名"（username 已有），是展示用的别名

### 基本约束
| 约束类型 | 具体约束 | 影响 |
|---------|---------|------|
| 业务约束 | 昵称可重复，但需防止冒充官方 | 需要敏感词过滤 |
| 技术约束 | 单表字段，不影响既有查询 | 无性能影响 |
| 资源约束 | 1 人日完成 | 方案要简单 |

### 必要性验证
- **不做会怎样**：用户投诉真实姓名暴露隐私（已收到 3 次投诉）
- **做了能带来什么**：提升用户体验，满足隐私需求
- **是否有更简单的替代方案**：前端显示时截取姓名？（不可行，需后端存储）
- **必要性结论**：必须做
```

**典型的 design.md 内容**：

```markdown
## 候选方案交叉验证矩阵

| 维度 | 方案 A：users 表加字段 | 方案 B：新建 user_profile 表 |
|------|----------------------|---------------------------|
| **成本** | 0.5 人日 / 无额外资源 | 1.5 人日 / 需建表+关联查询 |
| **性能** | 无影响（单字段） | 多一次 JOIN，略降低 |
| **复杂度** | 低：ALTER TABLE | 中：需改既有查询逻辑 |
| **风险** | 低：向下兼容 | 中：既有代码需改动 |

### 推荐方案
- **推荐**：方案 A（users 表加字段）
- **决策依据**：
  1. 成本低，1 人日内完成
  2. 性能无影响
  3. 风险可控，向下兼容
- **为什么不选方案 B**：过度设计，当前只有 1 个扩展字段不值得建新表
```

---

### Step 2：门禁检查（找漏洞）

运行命令：

```bash
/opsx:review add-user-nickname
```

**AI 做什么**：
- 并行启动 2 个评审子 agent（database + security）
- 每个 agent 从专业视角审查你的方案
- 4 分钟后汇总结果

**可能的评审结果**（`review-summary.md`）：

```markdown
## 摘要

发现 1 个 Blocker、1 个 Major、2 个 Minor。
主要问题：昵称字段缺少长度限制和敏感词校验。
需回改 design.md 后重走门禁。

## 门禁裁决：BLOCKED

## 各维度结论

| 维度 | 结论 | Blocker | Major | Minor | 状态 |
|------|------|---------|-------|-------|------|
| 数据库 | 有条件通过 | 0 | 1 | 1 | 本轮重跑 |
| 安全 | 打回 | 1 | 0 | 1 | 本轮重跑 |

## 已确认风险

### 数据库维度

**DB-01 [Major]**
- **一句话白话**：昵称字段没有长度限制，可能被恶意填充
- **触发场景**：用户输入 10000 字符的昵称 → 数据库写入超大字段
- **不修的后果**：单条记录过大，影响查询性能；存储空间浪费
- **建议修复**：限制 VARCHAR(50)

**DB-02 [Minor]**
- **一句话白话**：昵称字段无索引，模糊搜索会全表扫描
- **触发场景**：后台管理员按昵称搜索用户 → 慢查询
- **不修的后果**：管理后台搜索慢（当前用户量 5000，影响小）
- **建议修复**：若有搜索需求，建 FULLTEXT 或用 ES

### 安全维度

**SEC-01 [Blocker]**
- **一句话白话**：昵称未做敏感词过滤和 XSS 转义
- **触发场景**：用户昵称填 `<script>alert('xss')</script>` → 前端展示时执行
- **不修的后果**：XSS 攻击，盗取其他用户 Cookie
- **建议修复**：
  1. 后端入库前做 HTML 转义
  2. 敏感词过滤（防止冒充官方）
  3. 前端展示时用 `textContent` 而非 `innerHTML`

**SEC-02 [Minor]**
- **一句话白话**：昵称长度未限制，可能被用于钓鱼（超长昵称遮挡界面）
- **触发场景**：用户昵称填 1000 个空格 → 前端显示异常
- **不修的后果**：界面破坏，影响用户体验
- **建议修复**：前后端都限制长度 ≤ 50

## 修改建议

1. **design.md 第 3 节"字段定义"**：改为 `nickname VARCHAR(50) NOT NULL DEFAULT ''`
2. **design.md 新增第 4 节"安全设计"**：
   - 入库前 HTML 转义
   - 敏感词过滤（黑名单：'官方'、'管理员'、'客服'）
   - 前端用 `textContent` 渲染
3. **tasks.md 新增任务**：
   - [ ] 实现敏感词过滤工具函数
   - [ ] 前端渲染改用 `textContent`

## 有条件通过的条件清单

| 条件ID | 来源维度 | 条件内容 | 对应 tasks.md 任务 | 状态 |
|--------|---------|---------|-------------------|------|
| C-01 | 安全 | 入库前必须 HTML 转义 | T-02 Service 层数据校验 | 待实现 |
| C-02 | 安全 | 敏感词过滤必须生效 | T-02 Service 层数据校验 | 待实现 |
| C-03 | 安全 | 前端必须用 textContent | T-04 前端展示改造 | 待实现 |

## 术语表

- **XSS（跨站脚本攻击）**：攻击者在网页注入恶意脚本，盗取用户信息
- **HTML 转义**：把 `<` 转成 `&lt;`，防止被浏览器当作标签执行
- **敏感词过滤**：禁止用户使用特定词汇（如"官方"），防止冒充

## 人工确认区

⚠️ **门禁裁决：BLOCKED**

需先回改 design.md，在末尾「评审意见闭环记录」区块登记 SEC-01，然后重走门禁。

闭环后重跑门禁，通过后在下方签字：

Technical Review Approved: __________（待人工填写）
```

### Step 3：改方案（闭环）

根据评审建议，你确认按建议执行：

**AI 会自动**：
1. 修改 `design.md`（加安全设计章节、改字段定义）
2. 更新 `tasks.md`（加新任务项）
3. 在 `design.md` 末尾生成闭环记录表格：

```markdown
## 评审意见闭环记录

| finding ID | 维度 | 原始问题 | 处理方式 | 落在 design 的哪一节 | 轮次 |
|-----------|------|---------|---------|-------------------|------|
| SEC-01 | 安全 | 昵称未做 XSS 转义和敏感词过滤 | 已采纳：新增 §4 安全设计 | §4 安全设计 | R1 |
| DB-01 | 数据库 | 昵称字段无长度限制 | 已采纳：改为 VARCHAR(50) | §3 字段定义 | R1 |
| SEC-02 | 安全 | 昵称长度未限制导致界面破坏 | 已采纳：前后端都限 50 | §4 安全设计 | R1 |
| DB-02 | 数据库 | 昵称无索引搜索慢 | risk accepted：当前用户量小，暂不加索引。触发阈值：用户量 > 5 万时建 FULLTEXT 索引 | — | R1 |
```

---

### Step 4：重走门禁

```bash
/opsx:review add-user-nickname
```

这次评审会：
1. 先验证 SEC-01、DB-01、SEC-02 是否真的闭环
2. 再做新一轮审查

**通过后的 `review-summary.md`**：

```markdown
## 上轮闭环验证

| 历史 finding ID | 结论 | 判断依据 |
|----------------|------|---------|
| SEC-01 | 已闭环 | §4 已给出 HTML 转义与敏感词过滤逻辑 |
| DB-01 | 已闭环 | §3 已改为 VARCHAR(50) |
| SEC-02 | 已闭环 | §4 前后端都限制长度 50 |
| DB-02 | risk accepted 沿用 | 触发阈值明确（5 万用户），接受该决策 |

## 门禁裁决：READY_FOR_HUMAN_APPROVAL

全部维度通过，无未闭环 Blocker。
有 3 条"有条件通过"的条件（C-01/C-02/C-03），已映射到 tasks.md。

## 人工确认区

请审阅上述评审结论，认可后在下方签字：

Technical Review Approved: __________（待人工填写）
```

### Step 5：人工签字

你（或同事）审阅 `review-summary.md`，确认无误后：

**在文件中写入**：

```markdown
Technical Review Approved: 张三  2026-08-20
```

**保存并提交 git**：

```bash
git add openspec/changes/add-user-nickname/
git commit -m "feat(user): 技术评审通过 - 用户昵称字段

Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>"
```

### Step 6：写代码（实现）

```bash
/opsx:apply add-user-nickname
```

**AI 会做什么**：
1. 检查是否有人工签字（没有会拦截）
2. 按 `design.md` 和 `tasks.md` 写代码：
   - 数据库迁移脚本（`migrations/xxx_add_nickname.sql`）
   - Service 层校验逻辑（HTML 转义 + 敏感词过滤）
   - Controller 接口调整
   - 前端展示改造（`textContent`）
   - 单元测试

**AI 写完后会勾选 `tasks.md`**：

```markdown
- [x] 数据库迁移脚本
- [x] Service 层数据校验（含 HTML 转义和敏感词过滤）
- [x] Controller 接口调整
- [x] 前端展示改造
- [x] 单元测试
```

---

### Step 7：代码质量检查（可选但推荐）

```bash
/opsx:quality add-user-nickname
```

**AI 会检查**：
- 重复代码
- 可读性问题（过长函数、嵌套过深）
- 死代码（未使用的变量）
- 复杂度（圈复杂度过高）
- 设计偏离（实现与 design.md 不一致）

**输出**：`review/code-quality.md`

---

### Step 8：验证（三维校验）

```bash
/opsx:verify add-user-nickname
```

**AI 做什么**：
1. **Completeness（完整性）**：`tasks.md` 是否都勾选了？
2. **Correctness（正确性）**：需求是否都实现了？
3. **Coherence（一致性）**：代码是否偏离了 `design.md` 的设计？

**还需手工做**：
- 运行项目自己的测试（`npm test` / `mvn test` 等）
- 核对 `overview.md` 的条件矩阵（C-01/C-02/C-03 是否真的落地）

**全部通过**，继续下一步。  
**有 CRITICAL 问题**，修复后重跑 Step 8。

---

### Step 9：归档（收口）

```bash
/opsx:archive add-user-nickname
```

**AI 做什么**：
1. 把能力沉淀到 `openspec/specs/user-management/spec.md`
2. 把整个变更目录移到归档区：

```
openspec/changes/archive/add-user-nickname/
├── proposal.md
├── design.md
├── tasks.md
├── discussion-log.md
├── overview.md
└── review/
    ├── database.md
    ├── security.md
    ├── code-quality.md
    └── review-summary.md  ← 含人工签字，永久保留
```

**提交 PR**，完成！

## 🆘 常见问题

### Q1：门禁卡住了（BLOCKED），但我觉得是误报怎么办？

**三条逃生通道**：

1. **误报（问题不成立）** → 在 `review/<role>.md` 追加驳回记录：

```markdown
> **驳回**：SEC-03
> 理由：该导出接口仅对内部管理员开放，且经角色校验，不存在外部输入路径。
> 判定：误报（非 Blocker）
> 驳回人：张三  日期：2026-08-20
```

2. **risk accepted（问题真实但决定不修）** → 追加 risk accepted 记录：

```markdown
> **risk accepted**：PERF-02
> 理由：当前数据量 3000 条，全量加载内存可控。
> 触发阈值：单次 > 5 万条时须改流式处理，届时重开变更。
> 接受人：李四  日期：2026-08-20
```

3. **都不是，确实要改** → 回 `design.md` 闭环（见 Step 3）

**注意**：驳回或 risk accepted 后，不用重走门禁，直接更新裁决即可。

---

### Q2：我这个变更真的只是改个文案，还要走流程吗？

**不用！** 这就是 L0 豁免：

```bash
# 直接改代码，不走 /opsx:explore 和 /opsx:review
git commit -m "fix: 修正登录按钮文案"
```

**唯一要求**：在变更目录下创建 `review-summary.md`，记一行豁免理由：

```markdown
## L0 豁免

变更类型：纯文案修正
豁免理由：登录按钮文案"登陆"错别字改"登录"
豁免人：张三  日期：2026-08-20
```

（这是为了留痕，供事后审计和 hook 放行）

---

### Q3：门禁要等 4-8 分钟，能不能边跑边写代码？

**暂时不行**（但我们在规划"快速通道"）。

**当前最佳实践**：
- 门禁跑的时候去干别的（喝咖啡、看文档、code review）
- 迭代时用增量重走（只重跑改动的维度，1-3 分钟）

---

### Q4：我是老手，心里有数，能跳过门禁吗？

**可以，但要承担责任**：

L0/L1 变更可以自签：

```markdown
Technical Review Approved: 张三（自签）  2026-08-20
```

L2/L3 变更**不建议自签**（自己设计自己批准，门禁就退化成形式）。

**但注意**：门禁是流程纪律工具，不是技术强制。你始终可以：
- 驳回所有 finding（标为误报或 risk accepted）
- 或者直接让 Agent 用 Edit 改代码（绕过门禁）

**兜底靠 PR review 和 CI**，不是靠门禁拦截。

---

### Q5：文档太多了，要看 6 个文件（proposal / design / spec / tasks / review-summary / overview）？

**日常只看 3 个**：

| 阶段 | 主要看的文档 |
|------|------------|
| Phase 1-2（想方案） | `proposal.md` + `design.md` |
| Phase 3-4（门禁） | `review-summary.md`（其他 review/*.md 按需看） |
| Phase 5-6（实现+验证） | `tasks.md` + `overview.md` 条件矩阵 |

**overview.md 是"一页纸总览"**，汇总了：
- 文档地图（哪些文档存在、在哪）
- 端到端流程图
- 字段变更台账
- 规则条件矩阵（把 4 份文档的条件合成一张表）

**不用每份都手工看**。

---

### Q6：我改了代码后发现设计不对，要重走门禁吗？

**看情况**：

| 场景 | 是否重走门禁 |
|------|------------|
| 纯 bug 修复，未动技术方案 | 否（重跑 `/opsx:verify` 即可） |
| 改了技术方案（换存储、改并发模型、改表结构） | **是**（回 `design.md` 更新后按牵连关系重走对应维度） |

**判据**：`design.md` 变了没有。代码改了但设计没变 → 不重走。

---

### Q7：子 agent 讨论的结论怎么不丢？

按 `opsx-discussion-sync` 规则：

子 agent 返回固定五段：
1. 结论
2. 依据
3. 建议落点（proposal / design / tasks 哪一节）
4. 未决问题
5. 弃案（考虑过但不采纳的方案）

主 agent 必须把每条建议落到 artifact，或记为「未采纳 + 理由」，并追加到 `discussion-log.md`。

**结束前有防丢自检**。
