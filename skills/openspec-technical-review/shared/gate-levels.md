# 技术评审门禁适用范围分级

**不是所有变更都要跑全部门禁维度。** 强行全跑会让开发者放弃整套流程。按变更性质分级：

| 等级 | 典型变更 | 门禁要求 | 人工签字 |
|------|---------|---------|---------|
| **L0 豁免** | 纯文案/注释/日志文案、配置值调整、格式化、依赖小版本升级、纯测试补充 | **跳过门禁**，直接 apply | 不需要；**不要创建 `review-summary.md`**（该文件存在即视为已启用门禁，hook 会要求签字行） |
| **L1 轻量** | 单表单接口 CRUD、新增非核心字段、既有能力的小范围扩展 | 只跑 **database + security** | 需要 |
| **L2 标准** | 新增业务流程、跨模块调用、引入缓存、批量操作 | 跑 **architecture + database + security + performance** | 需要 |
| **L3 全量** | 涉及 MQ/异步、并发消费、分布式一致性、状态机、大数据量、新建核心表、对外开放接口 | **五维度全跑** | 需要，且建议第二人复核（`review-summary.md` 的 `复核:` 行，建议项，不拦截） |

> 「门禁要求」列的维度同时写在 `../technical-review-gate.workflow.js` 的 `LEVEL_ROLES` 常量里，workflow 按调用参数 `level` 推导纳入维度。改动本表时两边同步（本仓的文档一致性测试会比对两者）。


> **L0 的落点（勿与门禁产物混用）**：L0 豁免**不要创建 `review-summary.md`** —— 该文件的存在本身就是「本变更已启用技术评审门禁」的开关（见 `apply-gate-check.md`「何时执行」与 `hooks/check-review-approval.sh`），创建了就必须有非空签字行，与「跳过门禁」的初衷矛盾。豁免理由写在变更目录的 `overview.md` 开头一行，注明豁免人与日期，供事后追溯，由 `/opsx:propose`、`/opsx:ff` 收尾时写入（写法见下文「分级决策责任」）；**还没进 OpenSpec 的纯小改（改文案、调配置、格式化）直接改代码即可，不必为留痕单独建变更目录**。记录只需文件头与分级行，**不必为这一行跑完整总览生成**（格式见 `../../openspec-change-overview/SKILL.md`）。
## 判定口诀

**拿不准就升一级。** 漏评审的代价远高于多跑一个维度。

## 触发升级的信号

命中任一，至少 L3：

- 出现「异步」「MQ」「并发消费」「重试」「幂等」
- 出现「批量」且量级 ≥ 1 万
- 新建表，或对既有表加唯一索引/改字段类型
- 接口对外网开放，或处理用户上传内容
- 涉及租户隔离、权限判定、敏感数据

## 方案类型维度（MVP / 完整方案）

上面的 L0–L3 只看风险信号。分级还要看 `design.md`「候选方案交叉验证矩阵」推荐的**方案类型**：

| 方案类型 | 升级信号 | 编码前评审范围 |
|---------|---------|---------------|
| MVP | 未命中 | **跳过技术评审**，不创建 `review-summary.md` |
| MVP | 命中 1 个及以上 | **只跑**下表映射出的维度（各信号映射维度的并集），使用 MVP 评审标准（`mvp-review-standard.md`），仍需人工签字 |
| 完整方案 | 任意 | 沿用上文 L1–L3 |

- 方案类型取 `design.md` 的推荐方案：推荐方案标为 MVP 才算 MVP；没有写明时按完整方案处理。
- **判定不确定时取较大的范围**（MVP 拿不准是否命中信号 → 按命中处理；方案类型拿不准 → 按完整方案处理）。
- MVP 且未命中信号时，在 `overview.md` 开头写分级行，写法见下文「分级决策责任」。
- MVP 且命中信号时，`review-summary.md` 把未运行的维度列为「不适用」，理由引用下表命中的信号行。
- **本分层只影响编码前技术评审**。实现后双轴评审（`/opsx:quality`）按自身分级：L2/L3 必需，L0/L1 推荐（未生成不阻断归档）。**MVP 时仍要求两轴** —— 未命中信号时它已跳过编码前评审，双轴评审是它唯一的代码侧评审。

### 信号到维度的映射表

| 升级信号 | 维度 |
|---------|------|
| 异步、MQ、并发消费、重试、幂等、状态机 | concurrency |
| 租户隔离、权限判定、敏感数据、对外开放接口、用户上传内容 | security |
| 新建表、唯一索引、修改字段类型 | database |
| 批量量级 ≥ 1 万、大数据量 | performance |
| 新增跨模块依赖、新建模块 | architecture |

示例：

- 命中「租户隔离」「MQ 重试」→ security + concurrency；
- 命中「新建表」「批量 ≥ 1 万」→ database + performance。

MVP 时 workflow 的 `roles` 参数直接取映射结果（如 `["security","concurrency"]`）；完整方案传 `level`，不传映射结果。见 `../SKILL.md` 前置第 4、5 步。

## 分级决策责任

分级结论必须写进变更目录的 `overview.md` 开头（方案类型 + 命中信号 + 等级或维度 + 判定人 + 依据）—— **分级本身也是一个需要负责的决策**。该记录只占一行，`overview.md` 的全部五块内容仍是按需生成。若本变更走了门禁（即存在 `review-summary.md`），该结论同时写入 `review-summary.md` 的分级结论项（见 `../SKILL.md` Step 2 第 14 项）。**实现阶段的归档门禁只从 `overview.md` 这一行读等级**（判定双轴评审是否必需，口径见 `implementation-gate-check.md`「适用范围与不追溯」）：分级行为 MVP、L2、L3 时必需，与任务清单是否按切片声明 `Evidence:` 无关；缺行或写「未判定」时，声明了 `Evidence:` 的变更按保守口径要求双轴，没有声明的按历史变更不追溯。

谁写这一行：

| 分级 | 写入环节 |
|------|---------|
| L0；MVP 且未命中信号 | `/opsx:propose`、`/opsx:ff` 收尾时写入，判定人写该命令（agent）。这类变更不运行 `/opsx:review` |
| L1–L3；MVP 且命中信号 | `/opsx:review` 汇总时写入（`../SKILL.md` Step 2 第 14 项），已有分级行时改为本次判定 |

写法（`overview.md` 文件头的一行，`/opsx:overview` 重新生成时原样保留；没有 `overview.md` 时创建只含文件头与分级行的最小文件，格式见 `../../openspec-change-overview/SKILL.md`）：

```markdown
> 分级：L0 豁免 ｜ 判定人：/opsx:propose（agent） ｜ 日期：2026-10-28 ｜ 依据：只改日志文案
> 分级：方案类型 MVP；升级信号：无 ｜ 判定人：/opsx:propose（agent） ｜ 日期：2026-10-28 ｜ 依据：复用既有接口，没有命中升级信号
> 分级：L2 标准 ｜ 判定人：张三 ｜ 日期：2026-10-28 ｜ 依据：新增业务流程
```

等级或方案类型写在第一个 `｜` 之前：归档门禁先读这一段，判定人与依据中的文字不改变这一段的判定。旧写法 `方案类型：MVP；升级信号：无；判定人：…；日期：…` 已写过的原样保留，归档门禁照样识别为 MVP。

## 迭代成本

**迭代时优先用增量重走，别每次都全量**：各维度子 agent 并行，墙钟接近最慢的那个而非累加；重跑只跑被改动的维度（命令见 `../SKILL.md`「增量重走」）。

> 面向人的耗时与 token 成本预期表见 `workflow/OpenSpec-AI-研发流程.md`「门禁耗时与成本预期」。本文件是 agent 执行规则，不复制那张表。
