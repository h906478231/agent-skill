# 从「一问一答」到「工程化工作流」

> 团队内技术分享讲稿 · 目标时长 20–30 分钟 · 约 20 页
>
> 用法：每页给出【画面】（幻灯片上写什么）与【口播】（照着讲）。斜体是节奏提示，不用念。

---

## 第一幕：问题（约 4 分钟）

### Slide 1 — 封面

**画面**

```
从「一问一答」到「工程化工作流」
—— 我是怎么用 AI 做研发的，以及为什么不再直接对话

<你的名字> · <日期>
```

**口播**

今天不讲某个模型多强，也不讲提示词技巧。讲一件更朴素的事：**同样一个 AI，用两种方式使唤它，产出的可靠性差了一个数量级。**

---

### Slide 2 — 先讲一个都经历过的场景

**画面**

```
你：帮我写一个批量导入联系人的接口
AI：（写了。写得还挺好）
你：review 一遍，改两处，提交 ✅

—— 三个月后 ——

某租户 10 万条数据，接口超时
MQ 重复消费，联系人翻倍
```

**口播**

*停顿，让大家看完。*

这个流程哪里错了？

**一个字都没错。** AI 没写错代码，你 review 得也认真。

问题在于：从头到尾，**没有人问过「量级多大」，也没有人问过「会不会重复消费」**。

AI 不会主动问。它把你给的那句话，尽职尽责地实现了。

---

### Slide 3 — 核心命题

**画面**

```
一问一答的天花板，
不是 AI 的能力，
是提问者当天想到了什么。
```

**口播**

这是我今天想说的第一句核心的话。

一问一答的模式里，**AI 的能力上限根本不是瓶颈**。瓶颈是：你有没有想到该问它这个问题。

你记得问性能，它就分析性能。你那天赶工期，忘了问并发，它就一个字都不提。

而且 —— 这是最要命的地方 —— **你不会知道你漏问了什么。**

---

### Slide 4 — 一问一答的失败是静默的

**画面**

```
编译错误   → 红的，立刻知道
单测失败   → 红的，立刻知道
Sonar 告警 → 黄的，看得见

漏问了一个维度 → 什么都没有
              代码跑起来了
              三个月后线上炸
```

**口播**

我们工程上所有的质量手段，本质都是**把静默失败变成显式信号**。编译器、类型系统、单测、CI、静态扫描 —— 全都是。

唯独「用 AI 做研发」这件事，目前绝大多数人还停留在没有任何信号的状态。

**我做这套工作流，核心目的就一个：给 AI 研发过程装上红灯。**

---

## 第二幕：一问一答的五个结构性缺陷（约 5 分钟）

### Slide 5 — 缺陷总览

**画面**

```
① 覆盖度取决于提问者          → 漏问 = 漏做，且无感
② 共识是易失的               → 会话一关，全部归零
③ 没有关口                   → 需求没清楚就开始写代码
④ 决策不可审计               → 谁批的？为什么这么定？否过什么？
⑤ 质量不可复制               → 高手的提问方式带不走
```

**口播**

我把一问一答的问题归成五条。注意，**这五条都不是「AI 不够聪明」**，换个更强的模型一条都解决不了。这是**流程结构**的问题。

*下面五页逐条展开，每页 30–40 秒，不要恋战。*

---

### Slide 6 — 缺陷 ①：覆盖度取决于提问者

**画面**

```
你问的：  这个接口怎么写？
没问的：  数据量级？并发？幂等？索引？租户隔离？回滚？
         灰度？监控埋点？告警阈值？怎么单测？

覆盖度 = f(提问者当天的状态)
```

**口播**

一次设计要考虑的维度是固定的那么多。一问一答里，这些维度全靠人**临场回忆**。

人的记性是会波动的。周一上午和周五下午，你能想起来的东西不一样。

**工作流的第一个作用，就是把「该问的问题」从人的记性里搬出来，变成文件。**

---

### Slide 7 — 缺陷 ②：共识是易失的

**画面**

```
对话里达成的共识：
  "这里用 DB 做唯一真值源，缓存只做读加速"
  "方案 A 否掉了，因为跨机房延迟扛不住"

会话关闭 → 归零
下一个人接手 → 从零开始
下一轮 AI（全新上下文）→ 把死路重走一遍
```

**口播**

这条我觉得是最被低估的。

你和 AI 聊了两个小时，聊出了一个很好的方案，中间否掉了三个候选。**这些「为什么不选 A」的信息，价值不亚于「为什么选 B」。**

会话一关，全没了。

三个月后另一个人接手，或者你自己开一个新会话，AI 会**兴致勃勃地把方案 A 重新推荐给你一遍** —— 因为它不知道那条路已经走过了。

*可以插一句自嘲：我被这个坑过不止一次。*

---

### Slide 8 — 缺陷 ③：没有关口

**画面**

```
需求没明确 → 已经在分析性能
方案没定   → 已经在写 Controller

核心原则：
  需求未明确，不分析性能
  方案未确定，不开始编码
```

**口播**

一问一答天然没有阶段感。你说「写个接口」，它下一秒就在写代码了。

这在人的团队里是不可想象的 —— 需求评审没过就开工，PM 会找你。但 AI 不会拒绝你。

右边这两句话，是我整套流程的第一原则，写在流程文档最前面。

---

### Slide 9 — 缺陷 ④：决策不可审计

**画面**

```
半年后出事，你需要回答：

  这个方案当初谁批的？          → 没记录
  基于什么结论批的？            → 没记录
  当初有没有人提过这个风险？     → 提过，但会话没了
  为什么明知有风险还上？         → 忘了
```

**口播**

这条对团队来说是硬伤。

我们对人写的代码有 PR、有 review 记录、有 commit message。**对 AI 参与的设计决策，目前是一片空白。**

出事之后做复盘，你连「当初考虑过没有」都答不上来。

---

### Slide 10 — 缺陷 ⑤：质量不可复制

**画面**

```
同一个模型，同一个需求

老王问：  层层追问，覆盖 8 个维度  → 方案扎实
新人问：  一句话，拿到就写         → 埋雷

老王的提问方式，无法交付给团队
```

**口播**

这条决定了这件事能不能规模化。

团队里总有几个人特别会用 AI。但**他们的能力封装在他们脑子里**，写不进 wiki，也带不走。

新人拿到同一个模型，产出的东西完全是另一个水平。

*停顿。*

**这五条加起来指向同一个结论：需要把研发流程本身，做成资产。**

---

## 第三幕：我的工作流（约 6 分钟）

### Slide 11 — 全景图

**画面**（直接用流程文档里的图，可精简）

```
Explore  ── Phase 1 需求澄清 → proposal.md
         └─ Phase 2 方案探索 → design.md（候选方案 + 推荐方案 + 决策理由）
              ※ 子 agent 讨论结论回流 → discussion-log.md
                     ↓
        /opsx:overview → overview.md（文档地图 / 端到端流程 / 字段台账 / 条件矩阵）
                     ↓
              【分级判定】L0 豁免 ─────────────┐
                     ↓ L1 / L2 / L3           │
   ┌── Phase 3 技术评审门禁（仍不写代码）──┐    │
   │  架构 / 并发 / 性能 / 数据库 / 安全   │    │
   │  五个 Agent 并行 → review/*.md       │    │
   └──────────────┬───────────────────────┘    │
                  ↓                             │
        Phase 4 汇总 → review-summary.md（门禁裁决）
                  ├─ BLOCKED → 回改 design.md（留闭环记录）→ 重走 ⟲
                  ↓ READY_FOR_HUMAN_APPROVAL
        【人工签字】← 硬门禁                     │
                  ↓ ◄───────────────────────────┘
        Phase 5   /opsx:apply    代码实现
        Phase 5.5 /opsx:quality  代码质量评审（diff 层）
        Phase 6   /opsx:verify   三维校验 + 条件核对
                  ↓
        Archive → 能力沉淀进 specs，评审产物随变更归档
```

**口播**

这是全景。看着复杂，其实只有一条主线：**先把话说清楚，再评审，人签字，然后才写代码，写完再核。**

我逐个讲关键机制 —— 每一个机制，都是在治前面那五条缺陷中的某一条。

*不要逐页念图。给 20 秒让大家扫一眼，然后翻页。*

---

### Slide 12 — 机制一：分级，先解决「会不会没人用」

**画面**

```
L0 豁免  文案/注释/配置值/格式化/依赖小版本  → 跳过门禁，记一行豁免理由
L1 轻量  单表单接口 CRUD、非核心字段         → database + security
L2 标准  新业务流程、跨模块、缓存、批量       → + architecture + performance
L3 全量  MQ/异步/并发/分布式一致性/新建核心表  → 五维度全跑 + 第二人复核

判定口诀：拿不准就升一级
```

**口播**

**我先讲这一页，是因为这是整套流程能不能活下来的关键。**

如果改个错别字也要跑五个 Agent 评审，团队三天就把整套流程扔了。

所以第一件事是分级。**大部分日常改动是 L0 和 L1。**

耗时也给大家一个实测量级：

| 模式 | 墙钟 |
|---|---|
| L1（2 维度） | 2–4 分钟 |
| L2（4 维度） | 3–6 分钟 |
| L3（5 维度全量） | 4–8 分钟 |
| 增量重走（1 维度） | 1–3 分钟 |

注意这是**并行**跑的，墙钟接近「最慢的那个」而不是累加 —— 这是一问一答做不到的，串行对话一次只有一个视角。

---

### Slide 13 — 机制二：五维度门禁，把「该问的」变成默认动作

**画面**

```
架构 Agent    → 边界、一致性、可观测性、兼容与回滚
并发 Agent    → 幂等、重复消费、竞态、状态机
性能 Agent    → 量级、批量、慢查询、连接数
数据库 Agent  → 索引、DDL、租户前导、数据迁移
安全 Agent    → 权限、租户隔离、注入、敏感数据

治的是缺陷 ①：覆盖度不再取决于提问者
```

**口播**

回到开场那个例子 —— 批量导入超时、重复消费。

在这套流程里，**你不需要想起来问并发**。你只要判定它是 L3，并发 Agent 就一定会跑，一定会问「重复消费怎么办」。

*这是全场最重要的一句：*

**从「我记得问」变成「系统一定会问」。**

---

### Slide 14 — 机制三：让评审结论说人话

**画面**

```
finding 七字段：
  ID | 严重级别 | 位置 | 一句话白话 | 触发场景 | 不修的后果 | 建议修复

❌ 「幂等键缺失导致 CAS 失效」
✅ 「同一条消息被重复处理时，联系人会被导入两次」
   触发场景：MQ 重投 / 消费者重启未提交 offset
   不修的后果：该租户联系人列表出现重复，需人工清理

铁律：写不出具体触发场景的 Blocker，一律降级为 Major
```

**口播**

这条治两个病。

第一个病：**AI 评审爱堆术语**，没参与设计的人看不懂自己在签什么。所以强制三列白话。

第二个病，更实际：**AI 会误报**。如果误报能随便标 Blocker，门禁三天就把人卡烦了，团队就会开始绕过它。

所以那条铁律 —— **说不出具体触发场景的，自动降级。** 一条规则同时治两个病。

---

### Slide 15 — 机制四：条件必须落地，闭环必须留痕

**画面**

```
「有条件通过」≠「通过」

每一条条件 → 必须映射到 tasks.md 的一个可勾选任务
无法映射的条件 → 视同 Blocker

| C-01 | database | 幂等键唯一索引须 tenant_id 前导 | T-03 建表 DDL | 待实现 |

────────────────────────────────────────

design.md 末尾固定区块：评审意见闭环记录
| ARCH-01 | 架构 | 计数真值源不明 | 改为 DB 唯一真值源 | §3.2 | R1 |
```

**口播**

上半页：「有条件通过」是最容易失效的一环。条件写完没人管，等于没写。所以强制映射到任务项，Phase 6 逐条核对。

下半页解决一个很有意思的技术问题 —— **第二轮评审的 Agent 是全新上下文。**

它不知道 ARCH-01 上轮提过、这轮已经改了。没有留痕，它要么重新发现同一个问题，要么完全漏掉验证。

所以闭环记录不只是给人看的，**它是给下一轮 AI 的输入。** 这就是「用文件对抗上下文易失」—— 治的是缺陷 ②。

---

### Slide 16 — 机制五：人工签字是硬门禁

**画面**

```
Technical Review Approved: 张三  2026-07-31
复核（L3 必填）: 李四  2026-07-31

签字的含义：
  不是「我认可 AI 的结论」
  而是「我为这个方案进入实现负责」

  AI 评审是输入，不是免责声明
```

**口播**

*这页放慢。*

这可能是整套流程里最重要的一页，也是团队推行时第一个会吵起来的地方。

**签字不是背书 AI，是承担责任。**

规矩定得很细：L0/L1 允许作者自签；**L2/L3 不建议自签** —— 自己设计自己批准，门禁就退化成形式了。

签字前至少要做四件事：读完 summary 全文、逐条确认 Blocker 闭环、确认条件都进了 tasks、对驳回项独立判断而不是照单全收。

**如果团队普遍出现盲签，该调整的是分级规则（少跑但跑得更值），而不是继续走过场。**

## 第四幕：为什么这样更好（约 5 分钟）

### Slide 17 — 逐条对照

**画面**

| | 一问一答 | 工程化工作流 |
|---|---|---|
| **覆盖度** | 取决于提问者当天想到什么 | 分级 + 五维度清单，系统一定会问 |
| **共识载体** | 会话上下文（易失） | proposal / design / discussion-log（文件） |
| **阶段关口** | 无，随时开始写代码 | 硬门禁：未签字禁止 apply |
| **并行度** | 串行，一次一个视角 | 五个 Agent 并行，墙钟 ≈ 最慢的那个 |
| **可审计** | 无记录 | 签字 / 驳回 / risk accepted / 弃案全留痕 |
| **可复制** | 封装在个人脑子里 | 封装在 SKILL.md，团队共享、跨 agent 复用 |
| **失败模式** | 静默，三个月后线上暴露 | 显式，门禁 BLOCKED 当场亮红灯 |

**口播**

这张表是今天的核心。我不逐行念，只挑三行讲。

*挑「共识载体」「可审计」「失败模式」三行展开，各 30 秒。*

---

### Slide 18 — 一句话总结差异

**画面**

```
一问一答  优化的是：这一次回答的质量
                产出物是「文本」

工作流    优化的是：这个决策的可靠性
                产出物是「可追溯的决策链」
```

**口播**

*这是全场第二句核心的话。*

两者不是「同一件事做得好一点」的关系，**是两个不同的目标函数**。

一问一答做到极致，你得到一段很好的代码。
工作流做到极致，你得到一条**半年后还能回答「当初为什么这么定」的决策链**。

而且随着模型越来越强，**第一个目标会越来越不值钱** —— 因为它会自动变好。第二个目标不会自动变好，它只能靠流程。

---

### Slide 19 — 还有一层：资产可迁移

**画面**

```
skills/  三十来个 SKILL.md（DDD 建模 19 · OpenSpec 流程 8 · 门禁增强 4）

基于开放的 SKILL.md 标准
→ Claude Code / Codex CLI / opencode / Cursor / Gemini CLI …

npx skills add ./ -g -a '*'

换模型、换厂商，流程资产不作废
```

**口播**

最后一条好处，是战略性的。

这套东西不绑定任何一家。**流程沉淀在 Markdown 里，不在某个厂商的产品里。**

明年主力模型换一家，我的评审清单、建模方法、门禁规则，一行都不用改。

**能力会被模型迭代掉，流程不会。**

---

## 第五幕：坦白局限（约 3 分钟）

### Slide 20 — 它拦不住什么

**画面**

```
门禁是流程纪律工具，不是安全边界
它拦得住「忘了」，拦不住「铁了心要绕」

① hook 拦 Bash 的 openspec apply   → 拦不住 /opsx:apply 斜杠命令
② apply skill 的前置校验           → 提示词级约束，可被明确指令覆盖
③ 人工签字 + code review           → 签字人不看就签

始终存在的绕过路径：
  直接让 Agent 用 Edit/Write 改代码 —— 三道防线全部看不见

真正的兜底仍然是 PR review 与 CI
```

**口播**

*这页一定要讲，不能跳。*

我特意把局限性写进流程文档，也放进今天的分享。

**别把这套门禁理解成「代码不可能未经评审进主干」的技术保证。** 它做不到，我也没打算让它做到。

它的价值是：**让「评审」在正常路径上成为默认动作，而不是可选动作。**

还有一个坑必须提醒：**hook 必须在 settings.json 注册后才生效**，而且如果注册路径指向了旧版副本，它会**静默放行** —— 那比不装还危险，因为你以为有门禁。文档里有验证命令。

---

### Slide 21 — 什么时候别用这套

**画面**

```
✅ 该用一问一答的场景
   - L0 级改动：改文案、调配置、补注释
   - 探索性提问：「这个库怎么用」「这段代码什么意思」
   - 一次性脚本、临时排查

❌ 硬套工作流的代价
   - 流程摩擦 > 收益 → 团队整体放弃
   - 比没有流程更糟
```

**口播**

坦白讲，**大部分时候我也是一问一答的。**

工作流不是用来取代对话的，是用来**在高风险变更上加一道结构**。

判断标准很简单：**这个改动出事的代价，值不值得多花 5 分钟。**

L0 改文案，不值得。L3 上 MQ 异步消费，太值得了。

---

### Slide 22 — 怎么开始

**画面**

```
1. 别一次全上。先只做一件事：
   把「需求 + 方案」写进文件，再让 AI 动手
```

## 附：预判提问与答法

| 提问 | 答法 |
|---|---|
| 「改个字段也要跑五个 Agent？」 | 不用。看分级表，多数是 L0/L1。L0 直接豁免。 |
| 「AI 误报把我卡死了怎么办？」 | 两条逃生通道：**误报**（问题不成立）写驳回记录；**risk accepted**（问题真实但不修）写明复查触发阈值。都必须具名留痕，禁止直接删 finding。两者不能混用 —— 混用会让后续复查失去线索。 |
| 「这不就是把敏捷做回瀑布了吗？」 | 关键区别是**成本**。传统评审会要拉五个人开一小时会，所以只能季度做一次。现在一次 4–8 分钟，可以每个 L3 变更都做。**便宜到可以高频做的重流程，和瀑布不是一回事。** |
| 「多花的这些时间值得吗？」 | 用开场那个例子回答：L3 门禁 4–8 分钟，对比线上数据翻倍后的人工清理 + 复盘 + 修复。而且门禁是并行跑的，你可以去干别的。 |
| 「评审文档要提交 git 吗？开发完能删吗？」 | 提交，不删。签字是责任凭证；risk accepted 记着复查触发点（比如「数据量涨到 5 万条时复查」）—— 这条记录的价值恰恰在出事之后。全是纯文本，一个变更几十 KB。 |
| 「为什么评审记录不进 specs/？」 | `specs/` 是「现在应该是什么样」，是契约；评审记录是「当时为什么这么定」，是过程决策。混在一起会让 spec 没法当契约读。 |
| 「跟 Cursor / Copilot 那些内置的 review 有什么区别？」 | 那些是**代码层**的（diff 级别）。这套门禁跑在**写代码之前**，评的是 design.md。**设计错了，代码写得再干净也是错的。** 我这边代码层也有（Phase 5.5 `/opsx:quality`），两层不冲突。 |
| 「团队推不动怎么办？」 | 先别推全套。只推「方案写进文件」这一条，等大家尝到甜头。**推不动的根因通常是分级太严** —— 该降的降。 |
