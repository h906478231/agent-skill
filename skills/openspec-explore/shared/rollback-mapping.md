# 问题回退映射表

当在后续阶段发现问题时，按以下映射决定回退到哪个阶段修正，不要"原地修"跨阶段的问题。

## 核心原则

- **问题归因清晰**：每类问题都有明确的源头阶段
- **不原地修**：发现跨阶段问题时，回退到源头阶段重新执行
- **级联更新**：回退后，受影响的后续阶段需要重新验证

## 回退映射表

| 发现的问题类型 | 回退阶段 | 原因 | 处理方式 |
|----------------|---------|------|---------|
| **Phase 1 相关问题** | | | |
| 业务目标不清、定义模糊 | Phase 1 | 需求理解错误 | 重新澄清业务目标，补充业务场景 |
| 约束未识别、约束遗漏 | Phase 1 | 基本约束分析不完整 | 补充物理/业务/资源约束 |
| 必要性验证失败、投入产出比不合理 | Phase 1 | 第一性原理分析不充分 | 重新验证必要性，考虑更简单替代方案 |
| 表面需求与底层问题不匹配 | Phase 1 | 未深入追问"为什么" | 重新执行"5 个为什么"分析 |
| 核心场景遗漏 | Phase 1 | 场景识别不完整 | 补充遗漏场景，重新评估范围 |
| **Phase 2 相关问题** | | | |
| 候选方案不足（< 2 个） | Phase 2 | 方案探索不充分 | 生成至少 2 个有实质差异的候选方案 |
| 对比维度缺失（缺少成本/性能/复杂度/风险） | Phase 2 | 交叉验证不完整 | 补充四维对比矩阵 |
| 推荐方案与 Phase 1 底层问题不匹配 | Phase 1 | 需求理解偏离 | 回退 Phase 1 重新澄清底层问题 |

| 非功能性需求缺失（性能/可用性/安全） | Phase 2 | 设计细节不完整 | 补充非功能性需求设计 |
| **Phase 3 相关问题** | | | |
| 任务拆解与设计不一致 | Phase 2 | 设计细节缺失 | 回退 Phase 2 补充设计细节 |
| 验收标准无法验证设计目标 | Phase 2 | 设计目标模糊 | 回退 Phase 2 明确设计目标 |

| 测试策略与设计方案不匹配 | Phase 2 | 设计中未考虑可测试性 | 回退 Phase 2 调整设计 |
| **实施阶段问题** | | | |
| 实施中发现设计不可行 | Phase 2 | 设计假设错误 | 回退 Phase 2 重新设计 |
| 性能目标无法达成 | Phase 2 | 性能设计不足 | 回退 Phase 2 优化设计 |
| 技术栈与团队能力不匹配 | Phase 1 | 资源约束未充分识别 | 回退 Phase 1 重新评估资源约束 |
| 成本超出预期 | Phase 2 | 成本估算不准确 | 回退 Phase 2 重新对比方案成本 |

## 回退处理流程

```
发现问题
    ↓
查找问题类型（使用上表）
    ↓
确定回退阶段
    ↓
回退到该阶段重新执行
    ↓
重新执行该阶段的检查点
    ↓ 通过
重新执行后续阶段
    ↓
更新受影响的 artifacts
```

## 回退示例

### 示例 1：Phase 3 发现任务与设计不一致

**场景**：
- 在 Phase 3 拆解任务时，发现 design.md 中没有说明如何处理并发冲突
- 任务拆解无法明确验收标准

**分析**：
- 问题类型：任务拆解与设计不一致
- 回退阶段：Phase 2
- 原因：设计细节缺失（并发控制策略未定义）

**处理**：
1. 回退到 Phase 2
2. 补充并发控制设计（乐观锁 / 悲观锁 / 分布式锁）
3. 更新 design.md
4. 重新执行 Phase 2 检查点
5. 通过后，重新执行 Phase 3 任务拆解
6. 更新 tasks.md

### 示例 2：Phase 2 发现推荐方案与底层问题不匹配

**场景**：
- Phase 1 识别的底层问题：**大批量数据导入不能阻塞用户操作**
- Phase 2 推荐方案：同步批量插入（仍会阻塞 5 分钟）

**分析**：
- 问题类型：推荐方案与 Phase 1 底层问题不匹配
- 回退阶段：Phase 1
- 原因：需求理解偏离，或底层问题分析错误

**处理**：
1. 回退到 Phase 1
2. 重新执行"5 个为什么"分析
3. 确认底层问题是否正确
4. 如果底层问题正确 → 回到 Phase 2 重新选择方案
5. 如果底层问题错误 → 修正后，重新执行 Phase 2

### 示例 3：实施中发现性能目标无法达成

**场景**：
- Phase 2 设计目标：响应时间 < 100ms
- 实施后测试：响应时间 300ms

**分析**：
- 问题类型：性能目标无法达成
- 回退阶段：Phase 2
- 原因：性能设计不足

**处理**：
1. 回退到 Phase 2
2. 重新分析性能瓶颈
3. 调整方案设计（如：引入缓存、优化查询）
4. 更新 design.md
5. 重新执行 Phase 3 任务拆解
6. 重新实施并验证

## 不回退的情况

以下情况不需要回退，可以在当前阶段解决：

**Phase 3 内部调整**：
- 任务工作量估算调整
- 任务优先级调整
- 任务负责人调整
- 里程碑时间调整

**实施阶段优化**：
- 代码实现优化（不改变设计）
- 测试用例补充
- 文档更新
- 监控告警调整

**低优先级问题**：
- 不影响核心功能的次要问题
- 可以在后续迭代处理的优化项

## 回退决策检查点

在决定是否回退前，问自己：

- [ ] 这个问题是否影响核心设计决策？
- [ ] 这个问题是否在源头阶段就应该识别？
- [ ] 如果不回退，后续阶段是否会继续出问题？
- [ ] 回退的成本是否低于错误累积的成本？

如果以上任一项为"是"，应该回退。

## 回退成本估算

| 回退阶段 | 典型成本 | 影响范围 |
|---------|---------|---------|
| Phase 1 → Phase 1 | 0.5-1 天 | 需重新执行 Phase 2、Phase 3 |
| Phase 2 → Phase 1 | 1-2 天 | 需重新执行 Phase 2、Phase 3 |
| Phase 2 → Phase 2 | 0.5-1 天 | 需重新执行 Phase 3 |
| Phase 3 → Phase 2 | 0.5-1 天 | 需重新执行 Phase 3 |
| Phase 3 → Phase 1 | 1-3 天 | 需重新执行 Phase 2、Phase 3 |
| 实施 → Phase 2 | 1-3 天 | 需重新实施 |

**原则**：越早发现问题，回退成本越低。因此每个阶段的门禁检查至关重要。

## 预防回退的最佳实践

### Phase 1 最佳实践
- 充分应用第一性原理分析
- 不要跳过"5 个为什么"
- 识别所有关键约束
- 量化必要性验证

### Phase 2 最佳实践
- 至少 2 个候选方案
- 四维对比矩阵完整
- 必须回答"为什么不选其他方案"
- 回溯验证 Phase 1 底层问题

### Phase 3 最佳实践
- 任务拆解覆盖所有设计要点
- 验收标准满足 SMART 原则
- 依赖关系清晰
- 风险识别全面

## 总结

问题回退映射表的核心价值是**问题归因清晰**。通过明确每类问题的源头阶段，避免在错误的阶段"原地修"，确保问题从根源解决。

**核心原则**：发现跨阶段问题 → 查表找源头 → 回退修正 → 重新执行后续阶段。
