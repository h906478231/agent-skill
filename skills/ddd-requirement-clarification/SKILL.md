# DDD 需求澄清与歧义检测

## 一、为什么需要需求澄清

### 问题背景
在 DDD 建模过程中，输入需求的质量直接决定建模产出的质量。当需求含糊不清时，Agent 如果直接进入建模阶段，会导致：
- 阶段一事件识别结果偏差
- 后续所有阶段都基于错误理解推进
- 最终产出的领域模型与实际业务需求不符
- 需要大量返工和重新建模

### 解决方案
在进入 `ddd-modeling-workflow` 阶段 1 前，由本 skill 作为阶段 0 的唯一流程 owner，对不完整 / 模糊的需求输出结构化追问清单与澄清结果包，确保后续建模基于清晰的需求理解。

---

## 二、7 类需求歧义检测规则

### 2.1 角色缺失

**检测规则**：需求中未明确操作主体（用户、管理员、系统、外部系统）

**典型特征**：
- 使用被动语态："账户被锁定"
- 缺少主语："发送通知"
- 模糊表述："系统处理订单"

**追问模板**：
```
谁可以执行'{操作名称}'操作？
- [ ] {角色A}（如：管理员手动操作）
- [ ] {角色B}（如：系统自动触发）
- [ ] {角色C}（如：外部系统调用）
- [ ] 多个角色都可以（请说明各自的触发条件）
```

**示例**：
- 需求："锁定账户"
- 追问："谁可以执行'锁定账户'操作？是管理员手动锁定，还是系统在检测到异常登录后自动锁定？"

---

### 2.2 触发条件模糊

**检测规则**：事件触发条件使用"可能"、"有时"、"某些情况下"等不确定词汇

**典型特征**：
- "可能发送通知"
- "有时需要审批"
- "某些订单需要人工确认"
- "根据情况决定"

**追问模板**：
```
您提到'{模糊表述}'，具体触发条件是什么？
- 触发条件：{请明确列出所有条件}
- 是否每次都执行：是 / 否
- 如果不是每次都执行，判断依据是什么？
```

**示例**：
- 需求："订单创建后可能发送通知"
- 追问："订单创建后发送通知的具体条件是什么？是每次都发送，还是满足特定条件（如金额超过某个阈值、特定商品类型）才发送？"

---

### 2.3 数据边界不清

**检测规则**：涉及数量、金额、时间、长度等关键数据但无具体范围或约束

**典型特征**：
- "订单金额"（无上下限）
- "用户可以添加商品"（无数量限制）
- "优惠券有效期"（无具体时长）
- "库存数量"（无最小/最大值）

**追问模板**：
```
关于'{数据项}'，请明确以下边界：
- 最小值：{值}
- 最大值：{值}
- 默认值：{值}
- 超出范围时的处理：{拒绝/截断/人工审批/其他}
- 特殊约束：{如：必须是整数、必须大于0等}
```

**示例**：
- 需求："用户下单时输入订单金额"
- 追问："订单金额是否有上下限？最小金额是多少？最大金额是多少？超过最大金额是否需要审批？"

---

### 2.4 异常场景缺失

**检测规则**：只描述正常流程（Happy Path），未提及失败/冲突/重试/超时场景

**典型特征**：
- 只描述"用户下单成功"，未提及"库存不足"
- 只描述"支付成功"，未提及"支付失败"
- 只描述"发货"，未提及"发货失败"
- 缺少超时、网络异常、数据冲突等异常处理

**追问模板**：
```
关于'{正常流程}'，请补充以下异常场景的处理：
1. 如果{异常情况A}，应该如何处理？
   - [ ] 拒绝执行并返回错误
   - [ ] 允许重试（重试次数：___）
   - [ ] 进入补偿流程
   - [ ] 人工介入
   - [ ] 其他：___

2. 失败后的状态变化：{描述聚合状态如何变化}
3. 是否需要记录失败原因：是 / 否
```

**示例**：
- 需求："用户支付订单"
- 追问："如果支付失败，订单状态如何变化？是保持'待支付'状态允许重试，还是变为'支付失败'状态？是否有重试次数限制？超过重试次数后如何处理？"

---

### 2.5 并发语义未定义

**检测规则**：涉及状态修改但未说明并发控制策略

**典型特征**：
- "修改订单"（未说明多人同时修改如何处理）
- "扣减库存"（未说明并发扣减策略）
- "更新账户余额"（未说明并发更新处理）
- 高频写入场景未定义冲突处理

**追问模板**：
```
关于'{操作名称}'，如果多个{角色}同时执行此操作，应该如何处理？
- [ ] 乐观锁（允许并发，最后提交者检查版本，冲突时失败）
- [ ] 悲观锁（同一时间只允许一个操作，其他操作等待）
- [ ] 串行化（按提交顺序排队执行）
- [ ] 允许并发无冲突（如：只读操作）
- [ ] 其他策略：___

冲突后的用户可见反馈：
- [ ] 返回错误提示用户重试
- [ ] 自动重试（重试次数：___）
- [ ] 排队等待
- [ ] 其他：___
```

**示例**：
- 需求："多个操作员可以修改同一订单的备注"
- 追问："多个操作员同时修改同一订单时如何处理？是使用乐观锁（最后提交者检查版本，冲突时提示重新编辑），还是悲观锁（同一时间只允许一个人修改）？"

---

### 2.6 外部依赖不明

**检测规则**：提到"调用第三方"、"外部系统"、"远程服务"但未说明失败处理、超时策略、降级方案

**典型特征**：
- "调用支付网关"（未说明超时时间、失败处理）
- "查询库存系统"（未说明不可用时如何处理）
- "发送短信"（未说明发送失败后的处理）
- "同步数据到外部系统"（未说明同步失败的影响）

**追问模板**：
```
关于'{外部依赖}'，请明确以下策略：
1. 超时时间：{毫秒/秒}
2. 调用失败时的处理：
   - [ ] 立即返回错误给用户
   - [ ] 重试（重试次数：___，重试间隔：___）
   - [ ] 进入补偿流程
   - [ ] 降级处理（降级方案：___）
   - [ ] 异步重试（通过消息队列）
3. 该外部调用是否属于当前用例的必做步骤：是 / 否
4. 如果失败，主事务是否需要回滚：是 / 否
```

**示例**：
- 需求："订单支付时调用支付网关"
- 追问："调用支付网关失败时如何处理？超时时间是多少？是立即返回错误，还是进入补偿流程？如果支付网关返回'处理中'状态，如何处理？"

---

### 2.7 时序依赖模糊

**检测规则**：多个操作间的先后顺序或因果关系不清晰

**典型特征**：
- "发货和扣库存"（未说明先后顺序）
- "创建订单和扣减优惠券"（未说明顺序）
- "支付和发货"（未说明是否需要等待支付完成）
- 多个步骤间的依赖关系不明确

**追问模板**：
```
关于'{操作A}'和'{操作B}'，请明确：
1. 执行顺序：
   - [ ] 先{操作A}再{操作B}
   - [ ] 先{操作B}再{操作A}
   - [ ] 可以并行执行
   - [ ] 无严格顺序要求

2. 如果{操作A}失败，{操作B}是否还要执行：是 / 否
3. 如果{操作B}失败，{操作A}是否需要回滚：是 / 否
4. 两个操作是否必须在同一事务内完成：是 / 否
```

**示例**：
- 需求："订单发货时扣减库存"
- 追问："发货和扣库存的顺序是什么？是先扣库存再发货，还是先发货再扣库存？如果扣库存失败，是否允许发货？如果发货失败，已扣减的库存是否需要回退？"

## 三、追问优先级策略

### 3.1 高优先级问题（阻断式追问）

**特征**：影响核心建模决策，必须回答才能继续

**包含类型**：
- 角色缺失
- 并发语义未定义
- 时序依赖模糊

**处理方式**：
- 必须等待用户回答
- 不允许跳过
- 未回答前不进入后续建模阶段

---

### 3.2 中优先级问题（警告式追问）

**特征**：影响模型完整性，但可以在后续阶段补充

**包含类型**：
- 数据边界不清
- 异常场景缺失

**处理方式**：
- 建议用户回答
- 用户可选择"暂时跳过，后续补充"
- 跳过的问题进入澄清结果包的"待确认问题"部分，由 `ddd-architect` 统一决定是否落盘

---

### 3.3 低优先级问题（记录式追问）

**特征**：影响实现细节，不影响核心建模

**包含类型**：
- 外部依赖不明（超时时间、重试策略等技术细节）
- 触发条件模糊（如果不影响核心流程）

**处理方式**：
- 输出到澄清结果包的待确认问题清单
- 不阻断建模流程
- 在应用编排阶段（阶段 6）或代码实现阶段再补充

---

## 五、澄清结果包输出

### 5.1 职责边界

- 本 skill 只输出澄清问题清单、用户回答摘要、建模影响结论和待确认问题
- 本 skill 不直接写入任何 `docs/ddd` 文件，不定义文件路径、章节位置或增量写入策略
- `ddd-architect` 负责接收澄清结果包，并结合 `ddd-artifact-contract` 统一落盘

### 5.2 输出格式

```markdown
## 澄清结果包

### 澄清问题 1：角色缺失
- **位置**：需求第 3 段"系统锁定账户"
- **问题描述**：未明确操作主体
- **追问**：谁可以执行'锁定账户'操作？
- **用户回答**：管理员手动锁定 + 系统在连续登录失败 5 次后自动锁定
- **建模结论**：
  - 命令 C1：管理员锁定账户（Actor: 管理员）
  - Policy P1：连续登录失败后自动锁定（监听事件：登录失败事件，触发命令：锁定账户）
- **影响对象**：命令、Actor、Policy、领域事件
- **优先级**：高
- **状态**：已回答

---

### 澄清问题 2：并发语义未定义
- **位置**：需求第 5 段"修改订单金额"
- **问题描述**：未说明并发控制策略
- **追问**：多个操作员同时修改同一订单时如何处理？
- **用户回答**：使用乐观锁，冲突时提示用户重新编辑
- **建模结论**：
  - 订单聚合并发语义：允许冲突失败重试
  - 乐观并发令牌：version
  - 冲突后用户可见反馈：返回错误"订单已被他人修改，请刷新后重试"
- **影响对象**：聚合、并发语义、应用编排失败语义
- **优先级**：高
- **状态**：已回答
```

## 六、与建模工作流的接口关系

### 6.1 输入

- 原始业务需求
- 已有建模文档摘要（如有）
- `ddd-architect` 已识别的用户意图和建模范围

### 6.2 输出

- 需求澄清问题清单
- 高 / 中 / 低优先级分类结果
- 用户回答摘要（如已有回答）
- 建模影响结论：明确影响哪些事件、命令、聚合、Policy、读模型、应用编排语义
- 仍需确认的问题清单

### 6.3 协作方式

- `ddd-architect` 在阶段 0 触发本 skill，并负责决定是否阻断式追问用户
- 本 skill 只提供歧义检测、追问模板、优先级判断和澄清结果包
- `ddd-modeling-workflow` 从阶段 1 开始消费澄清结果包，不重复执行阶段 0
- 如果后续阶段发现新的关键歧义，应回传给 `ddd-architect`，由 `ddd-architect` 再次调用本 skill 处理

### 6.4 检测方式
- 基于规则引擎：检测关键词、句式模式
- 基于 LLM 语义分析：理解需求上下文，识别隐含歧义
- 两者结合：规则引擎快速筛选 + LLM 深度分析

## 七、使用示例

### 示例 1：完整的需求澄清流程

**用户输入需求**：
```
我需要一个订单系统，用户可以下单、支付、发货。
订单创建后发送通知，支付后扣减库存。
```

**阶段 0 输出**：
```markdown
## 需求澄清问题清单

### 问题 1：角色缺失 - 高优先级
- **位置**：整体需求
- **问题描述**：未明确"发货"操作的执行主体
- **追问**：谁可以执行'发货'操作？
  - [ ] 仓库管理员手动发货
  - [ ] 系统自动发货（触发条件：___）
  - [ ] 第三方物流系统发货
- **优先级**：高
- **状态**：待回答

---

### 问题 2：触发条件模糊 - 中优先级
- **位置**："订单创建后发送通知"
- **问题描述**：未明确发送通知的具体条件
- **追问**：订单创建后发送通知的条件是什么？
  - 是否每次都发送：是 / 否
  - 如果不是每次都发送，判断依据是什么？
  - 通知接收者是谁：用户 / 管理员 / 其他
- **优先级**：中
- **状态**：待回答

---

### 问题 3：时序依赖模糊 - 高优先级
- **位置**："支付后扣减库存"
- **问题描述**：未明确支付和扣库存的时序关系
- **追问**：支付和扣库存的顺序是什么？
  - [ ] 先支付成功再扣库存
  - [ ] 先扣库存再支付
  - [ ] 下单时预扣库存，支付后确认扣减
  
  如果扣库存失败，已支付的订单如何处理？
  - [ ] 退款
  - [ ] 人工介入
  - [ ] 其他：___
- **优先级**：高
- **状态**：待回答

---

### 问题 4：异常场景缺失 - 中优先级
- **位置**："用户支付"
- **问题描述**：未提及支付失败的处理
- **追问**：如果支付失败，订单状态如何变化？
  - [ ] 保持'待支付'状态允许重试
  - [ ] 变为'支付失败'状态
  - [ ] 自动取消订单
  
  是否有重试次数限制：是（次数：___）/ 否
- **优先级**：中
- **状态**：待回答
```

**用户回答后输出澄清结果包**：
```markdown
## 澄清结果包

### 澄清问题 1：角色缺失
- **用户回答**：仓库管理员手动发货
- **建模结论**：命令 C3：发货（Actor: 仓库管理员）
- **影响对象**：命令、Actor

### 澄清问题 2：触发条件模糊
- **用户回答**：每次订单创建都发送通知给用户
- **建模结论**：Policy P1：订单创建后发送通知（监听事件：订单已创建，触发命令：发送通知）
- **影响对象**：Policy、领域事件、领域命令

### 澄清问题 3：时序依赖模糊
- **用户回答**：下单时预扣库存，支付后确认扣减，如果扣库存失败则退款
- **建模结论**：
  - 命令 C1：创建订单（预扣库存）
  - 命令 C2：支付订单（确认扣减库存）
  - Policy P2：扣库存失败后退款（监听事件：库存扣减失败，触发命令：退款）
- **影响对象**：命令、领域事件、Policy、应用编排

### 澄清问题 4：异常场景缺失
- **用户回答**：保持'待支付'状态允许重试，30 分钟内未支付自动取消
- **建模结论**：
  - 订单状态：待支付 → 已支付 / 已取消
  - Policy P3：超时自动取消订单（监听事件：订单已创建，延迟 30 分钟，触发命令：取消订单）
- **影响对象**：聚合状态、Policy、领域事件
```

## 八、与其他 Skill 的协作

### 8.1 与 `ddd-modeling-workflow` 的接口关系
- `ddd-requirement-clarification` 是阶段 0 的唯一流程 owner
- `ddd-modeling-workflow` 从阶段 1 开始消费澄清结果包
- 高优先级澄清问题未回答时，`ddd-architect` 应阻断进入后续建模
- 中低优先级问题可以作为待确认问题进入后续建模，但必须保留建模影响说明

### 8.2 与 `ddd-event-storming` 的关系
- 需求澄清确保事件风暴的输入质量
- 澄清后的角色、触发条件、时序关系直接影响事件识别和命令识别

### 8.3 与 `ddd-aggregate` 的关系
- 澄清后的并发语义直接影响聚合边界划分
- 澄清后的数据边界影响聚合不变量定义

### 8.4 与 `ddd-persistence` 的关系
- 澄清后的并发语义决定乐观锁/悲观锁选择
- 澄清后的外部依赖策略影响事务边界划分

## 九、注意事项

### 9.1 不要过度追问
- 只追问影响建模决策的关键问题
- 技术实现细节（如具体的超时毫秒数）可以在代码实现阶段补充
- 避免一次性抛出过多问题，导致用户负担过重

### 9.2 追问要结构化
- 使用多选项、填空、是/否等结构化形式
- 避免开放式问题（如"你觉得应该怎么做？"）
- 提供常见选项，降低用户思考成本

### 9.3 结果包要完整
- 不仅输出用户回答，还要输出建模结论
- 建模结论要明确影响哪些事件、命令、聚合、Policy、读模型和应用编排语义
- 方便后续回溯和变更影响分析

### 9.4 允许迭代澄清
- 用户可能在后续阶段补充或修改回答
- 澄清结果包支持增量更新
- 每次更新标注变更轮次和变更原因

---

## 十、总结

需求澄清是 DDD 建模的第一道质量关卡。通过系统化的歧义检测和结构化追问，可以：
- 提升建模输入质量
- 减少返工和重新建模
- 确保建模结果与业务需求一致
- 为后续代码实现提供清晰的决策依据

**核心原则**：宁可多问一句，不要错建一步。
