# Phase 1: 需求澄清与第一性原理分析

> 当 `openspec-architect` 决定进入 Phase 1 时，加载本 skill 执行需求澄清。本 skill 只负责分析方法和逻辑产物输出，不负责 OpenSpec API 调用和文件落盘。

## 执行前提

- 输入应为用户的原始需求描述
- 如果用户需求过于模糊（如"做一个系统"），必须先进行基础澄清
- 本 skill 不直接调用 `AskUserQuestion`，而是在产物包中标记待确认问题，由 `openspec-architect` 决定是否追问

## 核心任务

Phase 1 的核心任务是**确保方向正确**。在明确业务目标、边界、输入输出等常规需求信息之外，必须应用第一性原理分析，避免解决错误的问题。

## 执行规则

### 1. 提炼业务目标

**目标**：识别用户真正想要达成的业务结果

**执行步骤**：
1. 识别业务目标：用户想要解决什么业务问题？
2. 识别核心场景：哪些场景是必须覆盖的？
3. 识别成功标准：什么样的结果算成功？
4. 识别关键约束：有哪些不可逾越的限制？

**输出**：
```markdown
## 业务目标
- 业务目标：{一句话描述}
- 核心场景：{场景列表}
- 成功标准：{可量化的标准}
```

### 2. 第一性原理分析（必需）

**目标**：区分表面需求与底层问题，确保解决正确的问题

**2.1 表面需求 vs 底层问题**

执行"5 个为什么"追问法：
- 用户说"需要一个缓存系统" → 为什么需要缓存？
- "因为查询慢" → 为什么查询慢？
- "因为数据库压力大" → 为什么数据库压力大？
- "因为高频重复查询" → 为什么会有高频重复查询？
- "因为前端每次渲染都重新请求" → 这才是底层问题

**判断标准**：
- 表面需求：用户提出的解决方案（"做一个 XX"）
- 底层问题：用户真正要解决的问题（"降低 XX"、"提升 XX"）

**输出**：
```markdown
### 表面需求 vs 底层问题
- **用户提出的需求**：{用户原始表述}
- **真正要解决的问题**：{追问 5 个为什么后的本质问题}
- **是否存在需求误解**：{表面需求与底层问题的差异分析}
```

**2.2 基本约束（不可绕过的事实）**

识别三类约束：

**物理约束**：
- 网络延迟下界（如：跨国网络 RTT > 200ms）
- 存储 IOPS 上限（如：HDD 随机读写 < 200 IOPS）
- CPU/内存/带宽限制
- 数据一致性定理（如：CAP 定理）

**业务约束**：
- 监管要求（如：数据不得出境、日志留存 6 个月）
- SLA 承诺（如：可用性 99.9%、响应时间 < 100ms）
- 遗留系统兼容（如：必须兼容老版本 API）
- 组织流程（如：变更必须经过审批）

**资源约束**：
- 团队规模（如：只有 2 个后端开发）
- 时间窗口（如：必须在 Q2 上线）
- 预算上限（如：云服务成本 < 1000 元/月）
- 技术栈限制（如：只能用 Java）

**判断标准**：
- 是约束：无法通过技术手段绕过
- 不是约束：可以通过调整方案规避

**输出**：
```markdown
### 基本约束（不可绕过的事实）

| 约束类型 | 具体约束 | 影响 |
|---------|---------|------|
| 物理约束 | {如：网络延迟下界、存储 IOPS 上限} | {对方案的限制} |
| 业务约束 | {如：监管要求、SLA 承诺、遗留系统兼容} | {对方案的限制} |
| 资源约束 | {如：团队规模、时间窗口、预算上限} | {对方案的限制} |
```

**2.3 必要性验证**

回答以下问题：

**不做会怎样**：
- 量化现状痛点（如：每天人工处理 500 笔，耗时 4 小时）
- 不是"用户体验不好"这种模糊描述
- 必须有数据支撑

**做了能带来什么**：
- 量化预期收益（如：自动化后耗时降至 10 分钟，节省 3.5 小时/天）
- 不是"提升用户体验"这种空洞描述
- 必须有可衡量的目标

**是否有更简单的替代方案**：
- 非技术方案（如：优化流程、培训用户、文档说明）
- 更简单的技术方案（如：配置调整、脚本自动化、购买 SaaS）
- 至少列出 1 个替代方案并说明为什么不选

**必要性结论**：
- 必须做：投入产出比合理，替代方案不可行
- 有更优替代：推荐替代方案
- 建议推迟：收益不明确或资源不足

**输出**：
```markdown
### 必要性验证

- **不做会怎样**：{现状痛点的量化影响}
- **做了能带来什么**：{预期收益的量化目标}
- **是否有更简单的替代方案**：
  - {替代方案 1}：{为什么不选}
  - {替代方案 2}：{为什么不选}
- **必要性结论**：{必须做 / 有更优替代 / 建议推迟}
```

### 3. 识别待确认问题

**问题分级**：

**高优先级（blocking: true）**：
- 影响方案选择的核心决策
- 影响业务目标定义
- 影响关键约束识别
- 必须回答才能继续

**中优先级（blocking: false）**：
- 影响设计细节
- 可以标记为待确认并继续
- 在 Phase 2 补充

**低优先级（blocking: false）**：
- 实施细节
- 记录到文档
- 在 Phase 3 或实施时补充

**输出格式**：
```json
{
  "id": "Q1",
  "priority": "high",
  "question": "系统需要支持的最大并发用户数是多少？",
  "options": [
    "< 100",
    "100-1000",
    "1000-10000",
    "> 10000"
  ],
  "status": "pending",
  "impacts": ["architecture", "technology_stack"],
  "blocking": true,
  "reason": "并发量决定是否需要分布式架构"
}
```

## Phase 1 检查点（自检）

在输出产物包前，执行以下检查：

- [ ] 业务目标已明确（不是"做一个 XX"，而是"达成什么业务结果"）
- [ ] 第一性原理分析完整：
  - [ ] 区分了表面需求与底层问题
  - [ ] 识别了至少 1 个基本约束
  - [ ] 必要性量化验证完成（不做会怎样 / 做了能带来什么 / 有无更简单替代）
- [ ] 核心场景已列出
- [ ] 成功标准可量化
- [ ] 待确认问题已分级（高/中/低）
- [ ] 高优先级问题已标记为 blocking: true

**如果检查点未全部通过**：
- 不输出产物包
- 说明缺少什么
- 给出补充建议

## 执行示例

### 示例 1：用户需求模糊

**输入**：
```
用户："我需要一个缓存系统"
```

**分析**：
- 需求过于表面，缺少业务上下文
- 需要追问底层问题

**输出**：
```json
{
  "clarification_questions": [
    {
      "id": "Q1",
      "priority": "high",
```

### 示例 2：需求清晰，执行第一性原理分析

**输入**：
```
用户："我们的订单列表页面加载很慢，用户抱怨等待时间长。
      数据库查询耗时 3-5 秒，数据量约 100 万条订单。
      需要优化查询性能，目标是 500ms 内返回结果。"
```

**分析执行第一性原理**：

1. **表面需求 vs 底层问题**：
   - 表面需求：做一个缓存系统
   - 为什么需要缓存？→ 查询慢
   - 为什么查询慢？→ 数据库压力大
   - 为什么数据库压力大？→ 全表扫描，无索引
   - 底层问题：**数据库查询未优化，缺少索引**

2. **基本约束**：
   - 资源约束：2 个后端开发，1 周时间窗口
   - 业务约束：必须保证数据实时性（不能接受 5 分钟延迟）
   - 物理约束：数据库单机 MySQL，无法快速迁移到分布式

3. **必要性验证**：
   - 不做会怎样：用户流失，客服投诉增加（每天 50+ 投诉）
   - 做了能带来什么：加载时间降至 500ms 以内，用户满意度提升
   - 更简单的替代方案：
     - 方案 1：优化 SQL + 添加索引（成本低，效果可能达到目标）
     - 方案 2：引入 Redis 缓存（成本中，需要维护缓存一致性）
     - 方案 3：迁移到 Elasticsearch（成本高，时间不够）

## 注意事项

### 不要过度追问

- 只追问影响方向性决策的问题
- 技术实现细节在 Phase 2/3 补充
- 避免一次性抛出过多问题

### 追问要结构化

- 使用多选项、填空、是/否等结构化形式
- 避免开放式问题（如"你觉得应该怎么做？"）
- 提供常见选项，降低用户思考成本

### 必须应用第一性原理

- 不能跳过"表面需求 vs 底层问题"分析
- 不能跳过"基本约束"识别
- 不能跳过"必要性验证"
- 这是 Phase 1 的核心价值

### 产物包要完整

- 输出的 JSON 必须包含所有必需字段
- 不能省略第一性原理分析区块
- 待确认问题必须分级并标注 blocking 字段

## 总结

Phase 1 的核心价值是**确保方向正确**。通过第一性原理分析，避免"技术方案设计得很好，但解决了错误的问题"。

**核心原则**：宁可多问一句底层原因，不要错判方向。
