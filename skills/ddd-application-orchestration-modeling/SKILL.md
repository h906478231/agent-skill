# DDD 应用编排建模与一致性判定

> 当需要产出或修改 `docs/ddd/application-model.md` 时，使用本 skill 对用例编排、一致性、聚合并发约束与外部协作语义进行建模。本 skill 负责方法论判定，不负责文件持久化；文档落盘由 `ddd-architect` 统一执行。

## 目标

- 为每个用例补齐应用编排语义，避免 coding 阶段自行假设
- 区分同步编排、提交后事件与 Saga/流程管理器
- 明确外部协作类型、并发冲突语义、失败语义与事务边界
- 为每个可写聚合补齐聚合并发约束（并发策略、并发令牌、CAS 行为、冲突返回语义）
- 为 `ddd-coding-workflow` 提供稳定可消费的应用编排基线

## 每个用例必须补充回答

- 该后续动作失败时，主用例是否必须整体回滚
- 该后续动作是否属于当前用例的必做步骤
- 是否存在远程 HTTP 调用
- 若存在远程 HTTP，属于远程读/校验还是远程写/状态变更
- 流程是 `同步编排`、`提交后事件` 还是 `Saga`
- 同一聚合是否可能被并发修改，冲突后语义是什么

## `application-model.md` 记录要求

对每个用例，至少补充以下语义字段或等价说明：

- 外部协作类型：`无 / 本地调用 / 远程查询 / 远程写入`
- 执行方式：`同步编排 / 提交后事件 / Saga`
- 并发冲突语义：`失败返回 / 有限重试 / 排队串行 / 人工介入`
- 失败语义：`同事务回滚 / 重试直到成功 / 补偿 / 人工介入`

## 建模判定规则

### 同步编排

适用条件：
- 后续动作失败时，主用例必须整体失败并回滚
- 后续动作本身属于当前用例的必做步骤，而不是提交后的扩展反应
- 所有步骤都可以在单个本地事务中完成，且没有跨服务写入要求

建模结论：
- 执行方式标记为 `同步编排`
- 一致性要求标记为本地事务内强一致
- 允许保留领域事件作为业务事实，但事件不承担该同步步骤的主流程职责

### 提交后事件

适用条件：
- 后续动作允许在主事务提交后执行
- 后续动作失败时，不要求主写模型回滚，只要求可重试、可补偿或人工介入
- 典型场景：通知、审计、读模型刷新、会话失效、跨系统副作用传播

建模结论：
- 执行方式标记为 `提交后事件`
- 失败语义必须明确为 `重试直到成功 / 补偿 / 人工介入` 之一
- 事实源应是领域事件或等价持久化事件记录；Spring 事件、MQ、HTTP relay 只属于后续实现机制，不是建模事实源

### Saga / 流程管理器

适用条件：
- 流程跨多个本地事务
- 需要等待人工审批、外部回调、异步确认或跨服务补偿
- 远程系统写入失败后需要回滚前置动作或推进补偿步骤

建模结论：
- 执行方式标记为 `Saga`，或明确标注 `待补充 Saga 建模`
- 未明确 Saga / 补偿模型时，不得把该用例建模为普通同步编排

### 远程 HTTP 调用

- 远程 HTTP 读 / 查询 / 校验：可以建模为同步协作，但应明确其失败语义和是否影响主事务
- 远程 HTTP 写 / 状态变更：默认不能建模为本地事务内强一致步骤
- 如果需求包含远程 HTTP 写，但用户仍要求强一致，应明确记录为建模冲突，不能默认为普通单事务用例
- 若远程写入允许主事务先提交、后续重试，则建模为 `提交后事件`
- 若远程写入涉及补偿、回调、跨事务等待或长流程状态推进，则建模为 `Saga`

### 并发与冲突语义

- 若同一聚合存在并发修改风险，必须额外记录其并发语义与冲突处理语义，不能留空
- 若聚合选择“允许冲突失败重试”，必须同时确认其版本令牌方案；若未确认，保持待确认，不能默认所有聚合都带 `version`
- 并发冲突语义必须落为 `失败返回 / 有限重试 / 排队串行 / 人工介入` 之一，或给出等价业务语义

### 聚合并发约束（聚合侧）

应用编排建模必须为 `domain-model.md` 中的**每个可写聚合**输出一条聚合并发约束，写入 `application-model.md` `## 6. 聚合并发约束`。

每条记录必须包含以下字段：

| 字段 | 取值范围 | 说明 |
|------|---------|------|
| 聚合 | 与 `domain-model.md` 聚合名一致 | 直接引用，不重新命名 |
| 并发策略 | `乐观并发(CAS) / 悲观锁 / 分布式锁 / 串行化队列 / 只读不需要` | 必须二选一以上明确 |
| 并发令牌 | `version: long` / `etag: string` / `revision: long` / 其他等价方案 / 不需要 | 选乐观并发必须给令牌方案，并与 `domain-model.md` 状态数据中的 `version` 字段保持一致 |
| CAS 行为 | `WHERE id = ? AND version = ?` / 其他等价表达 | 给出关键写入条件 |
| 冲突返回语义 | `失败返回 / 有限重试(N 次) / 排队串行 / 人工介入` | 必须与用例清单"并发冲突语义"列一致 |
| 业务理由 | 一句话说明为何选用此策略 | 关联高争用、读多写少、状态机收敛等 |

判定规则：

1. **乐观并发(CAS)**：默认选项；适用于写并发风险中等、冲突可由"重新读取后重试"消解的场景。要求聚合在 `domain-model.md` 已声明 `version` 字段。
2. **悲观锁**：仅当业务必须串行化、且读写不可错位时使用；需说明锁粒度和持有时间。
3. **分布式锁**：仅当多实例必须串行化、且数据库锁不够用时使用；需说明锁键、持有时间和兜底。
4. **串行化队列**：当冲突必须避免、但允许排队等待的场景；需说明队列粒度和退化策略。
5. **只读不需要**：聚合仅作为只读视图或仅参与读模型构建时使用；需说明无写入入口。

禁止事项：

- 不得在本 skill 输出"业务锁规则"字段；业务上的"锁定中不可登录""已提交后不可修改"等约束属于业务状态机不变量，归 `domain-model.md` 聚合不变量
- 不得让"乐观并发(CAS)"与"业务状态机约束"在同一字段混写
- 不得为"只读不需要"的聚合再补 `version` 字段

## 建模前必查项

对每个用例都显式检查：
- 后续动作失败是否要求主事务回滚
- 后续动作是否属于当前用例必做步骤
- 是否存在远程 HTTP 写入
- 是否存在跨事务等待、补偿或人工介入
- 执行方式是否已明确为 `同步编排 / 提交后事件 / Saga`
- 是否存在同一聚合被并发修改的风险
- 用例并发冲突语义与对应聚合的并发约束已对齐

对每个可写聚合都显式检查：
- 是否已选定并发策略
- 选乐观并发的聚合，是否在 `domain-model.md` 状态数据中存在 `version` 字段
- CAS 行为是否已明确
- 冲突返回语义是否已明确，且与所有调用该聚合的用例冲突语义一致

若上述关键信息缺失，应输出待确认问题，由 `ddd-architect` 统一追问；不得由 coding 阶段自行假设。

## 输出要求

本 skill 至少应产出或补全以下内容：

- 应用服务清单
- 用例清单（含并发冲突语义列）
- 每个用例的事务边界与一致性要求
- 外部协作类型与执行方式
- 失败语义
- 聚合并发约束清单（写入 `application-model.md` `## 6. 聚合并发约束`）
- 读模型清单状态声明（默认有读模型；若无读模型须显式声明，由 `ddd-modeling-workflow` 阶段 7 读模型规范提供基础数据）
- 需要补充 Saga 建模的缺口清单

## 与其他 Skill 的协作

- 与 `ddd-modeling-workflow`：本 skill 接收其领域建模结果，在阶段 7 输出逻辑产物包时被加载，为应用编排基线补齐一致性、外部协作语义与聚合并发约束
- 与 `ddd-saga`：当执行方式判定为 `Saga` 或存在长流程/补偿需求时，必须进一步加载 `ddd-saga`
- 与 `ddd-persistence`：当需要确认事务边界、并发实现机制或最终一致实现约束时，可按需加载 `ddd-persistence`；本 skill 只输出语义，不替代 `ddd-persistence` 的实现约束
- 与 `ddd-aggregate`：本 skill 输出的"聚合并发约束"中并发策略不得与 `ddd-aggregate` 定义的聚合不变量冲突
- 与 `ddd-coding-workflow`：coding 阶段只消费本 skill 输出的执行方式、一致性判定、并发冲突语义与聚合并发约束，不得自行补齐

## 与 `ddd-coding-workflow` 的衔接

- `ddd-coding-workflow` 只能消费这里输出的执行方式、一致性判定与并发语义
- 如果 `domain-model.md` / `application-model.md` 未明确这些字段，coding 阶段应停止并反馈，不得自行假设

## 注意事项

- 本 skill 只定义语义层判定，不直接展开为 MQ、Outbox、监听器、事务注解等技术实现方案
- 若信息不足以完成判定，应输出待确认问题，由 `ddd-architect` 统一向用户追问
- 若结论是“待补充 Saga 建模”，必须明确阻断普通单事务落地，不得以同步 HTTP + 本地事务伪装强一致
