# 门禁裁决与迭代规则（执行层唯一事实源）

> 本文件是 agent 执行门禁时的判定规则**唯一事实源**：怎么裁决、什么时候重走、改了什么要连带重跑什么、不认可结论怎么留痕。
> 路径：`<SKILL_DIR>/shared/gate-policy.md`
>
> **面向人的策略**（变更分级、签字人资格与责任、门禁强制力边界、产物 git 生命周期）不在本文件，见 `workflow/OpenSpec-AI-研发流程.md`。

## 1. 门禁裁决

对**全部纳入范围的维度**求值（含增量重走时沿用上轮结论的维度）：

| 条件 | 裁决 |
|------|------|
| 任一维度 `verdict = 打回`，或存在**未闭环 Blocker**（findings 表中 `严重级别 = Blocker` 且 `闭环状态 = open`，含缺省） | `BLOCKED` |
| 全部 `通过` / `有条件通过`，且无未闭环 Blocker、无待处理条件或待完成撤销 | `READY_FOR_HUMAN_APPROVAL` |

Blocker 与 Major 按不修的后果定级，不因修复要新增状态、持久文件、子命令或协议升级为 Blocker。「有条件通过」的条件原文写明修复是否新增机制，供第 5 节的推荐项使用。

四条补充判定：

- **「声称已闭环但实际未闭环」一律按未闭环 Blocker 计入裁决**（见 `closed-loop-verification.md`）。
- **纳入维度没有评审产物时裁决为 `BLOCKED`**（如增量重走时某个沿用维度上轮没有 `review/<role>.md`）—— 没评审过的维度无法求值，不得推测或编造上轮结论，把该维度加入重跑范围。
- **人工确认是硬门禁**：裁决为 `READY_FOR_HUMAN_APPROVAL` 只代表可以交人审，不代表可以 apply。人工在 `review-summary.md` 写入 `Technical Review Approved` 之前，禁止进入实现。

### 有条件通过的条件状态

条件清单列：`条件ID | 来源维度 | 来源 finding ID | 条件内容 | 对应任务或行号 | 状态`。汇总写来源与条件原文，新条件写 `待处理`；状态只取以下五种：

| 状态 | 判据 | 对应任务或行号 |
|---|---|---|
| `待处理` | 尚未选择处理，或已选修复尚未写入规划 | 空 |
| `已写入` | 选修复并已用 `/opsx:update` 写入规划 | 需改代码、测试、SQL、配置或交付文档时填任务编号；只改规划时填写明原条件的 `<文件>:<行号>`，不写任务 |
| `risk-accepted` | 当前接受记录与台账一致 | `review/<role>.md` 的有效处理记录 |
| `false-positive` | 当前驳回记录与台账一致 | 同上 |
| `deferred` | 当前移出记录与台账一致 | 同上 |

关联开放 Major 且有明确原文的待处理条件不计为 Blocker；没有其他打回原因时按第 5 节询问，但条件处理完成前保持 `BLOCKED`。缺来源、缺原文，或声称已处理却无可核对的任务、行号或当前处理记录，仍视同 Blocker。只认可最近一次、未撤销且与状态和台账相符的处理。核对见 `phase6-verification.md`；只改规划的条件不写实施任务（`../../openspec-propose/shared/task-slicing.md`「排除清单」E3）。

### 机器可读裁决行（唯一出口）

`review-summary.md` 的人工确认区必须在签字行之前写下面两行。每行只写键和一个枚举值，不加说明文字；hook 与 apply 前置校验按行首键名读取：

```markdown
Gate-Level: L2
Gate-Verdict: BLOCKED
Technical Review Approved: __________
```

| 键 | 取值 | 说明 |
|----|------|------|
| `Gate-Level` | `L1` / `L2` / `L3` / `MVP` | 与分级结论项一致（规则见 `gate-levels.md`） |
| `Gate-Verdict` | `READY_FOR_HUMAN_APPROVAL` / `BLOCKED` | 按本节上表判定，与门禁裁决项一致；理由写在门禁裁决项，不写进这一行 |

- 重走门禁、驳回或 risk accepted 改变裁决时，同步更新 `Gate-Verdict` 行。
- `Gate-Verdict: BLOCKED` 时，**即使签字行已签也禁止 apply**（hook 与 `apply-gate-check.md` 都按此拦截）。
- 读取时只认行首键名：键名前只能有列表标记（`-`、`*`）、引用标记（`>`）与空白。句中、反引号、表格单元格或其他文字后的提及不是键名行。裁决行与签字行各取全部键名行中的最后一行，不要求两行相邻。
- 裁决行冒号可以是半角 `:` 或全角 `：`，签字行只认半角冒号；标记内部的文字与空格按原文字面匹配。裁决值取最后一个标记后第一个由 ASCII 字母与下划线组成的词，签字值仍按原有占位与「签署人」截断规则读取。
- 空白包含全角空格、U+00A0 等非 ASCII 空白，与 JS 正则 `\s` 相同（清单见 `hooks/check-review-approval.sh` 的 `UNICODE_SPACES`），签字值删除空白时也用这一组。hook 与 apply 前置校验按同一规则读取，结果与 locale 无关。
- 写入规则：人工确认区是最后一节，正文引用这几行时不从行首写起。不生成独立签字示例，代码块和 HTML 注释也不例外。签字说明使用普通文字，只在人工确认区保留待用户填写的签字行。不解析 Markdown 结构，代码块与 HTML 注释中的行仍按普通行处理；后方独立示例行可能成为最后一行，不得将本规则解释为能验证签字来源。
- L3 在签字行后追加 `复核: __________`，对应分级表的「建议第二人复核」。**这一行是建议项**：留空不拦截，hook 与 apply 前置校验都不检查它。
- 本格式引入前生成的 `review-summary.md` 没有 `Gate-Verdict` 行：hook 只校验签字行，apply 前置校验从门禁裁决项读裁决。

裁决为 `BLOCKED` 时，按第 6 节判断收敛选项。选择继续修复时，必须在输出中明确告知用户：回改 `design.md` 后要在其末尾 `## 评审意见闭环记录` 区块登记每条 Blocker，格式 `finding ID | 维度 | 原始问题 | 处理方式 | 落在 design 的哪一节 | 轮次`（首轮 R1，依次 R2…）。**不登记，下一轮评审 agent 就会重复报同一个问题。**

## 2. 什么时候重走门禁

**定稿前**：`design.md` 或 `proposal.md` 的修改影响评审维度时，按下表重走。**定稿后**：先按第 5 节登记并确定规划档位，再按下表与第 3 节判断方案变更的重走范围。

| 场景 | 做法 |
|------|------|
| 修改运行假设的任一行，含定稿前选择修复 Major | **全量重走**，所有纳入维度审全文；该行及依赖新假设的修改登记为方案变更，保持 `BLOCKED`，不沿用旧裁决、不提示签字。此规则优先于条件落点 |
| 改动牵动跨维度地基（模块归属、一致性口径、表模型） | **全量重走**，纳入范围的维度全跑 |
| 改动只碰单一维度（纯转义、纯索引调整） | **增量重走**，只重跑受影响维度，其余纳入维度沿用上轮 `review/<role>.md` |
| 不认可结论（误报 / 知情接受） | **不重走**，留驳回痕迹，仅更新裁决计数 |
| 定稿后修改规划产物 | 按第 5 节区分规划档位；方案变更重走，其他三档不重走 |
| 实现阶段改了技术方案（换存储、改并发模型、改表结构） | **重走**，按下方牵连关系表确定范围 |
| 实现阶段纯 bug 修复，未动 design | **不重走** |

**判断口诀：宁可多跑一个维度，不可漏跑被牵连的维度。**

## 3. 牵连关系速查（改了左边，右边也要重跑）

| 改动内容 | 必须一并重跑 |
|---------|-------------|
| 表结构 / 索引 | database + performance + concurrency（幂等键依赖唯一索引） |
| 幂等 / 状态机设计 | concurrency + database |
| 同步改异步（引入 MQ） | 全部维度 |
| 批大小 / 并发度 | performance + concurrency + database |
| 接口出入参 | security + architecture |
| 加密 / 脱敏方案 | security + database（加密字段无法直接建唯一索引） |

增量重走时，**裁决仍对全部纳入维度求值**：沿用维度若仍有未闭环 Blocker，门禁仍 `BLOCKED`。

## 4. 不认可评审结论：驳回与 risk accepted

按 `finding-format.md` 更新技术评审台账，把已处理项移出开放 Findings，完整原发现和各次处理记录保留在同一维度报告。误报、风险接受和移到后续变更只写记录，不改规划；收窄范围按第 6 节另登记规划。

三类遗留处理（风险接受、移到后续变更、收窄范围）都写：处理方式、决定人与日期、用户回复来源、理由（没有时写「用户未说明」）、捡起条件。风险接受的捡起条件写复查触发阈值。误报也要具名和保留原发现。移到后续变更写 `deferred`，另写去向；未建后续变更时写「未建」。收窄范围写 `closed`，处理依据标「范围收窄 #<登记序号>」。

每次决定以 `R<轮次>:<finding ID>:<同 ID 的序号>` 作唯一标识；在台账「处理依据」写标识或关联收窄登记号。`## 处理记录` 下用 `### <finding ID> · <原决定标识>`，依序写本次记录和完整原发现表格行。示例：

```markdown
### CONC-03 · R2:CONC-03:1

- 处理方式：deferred
- 决定人与日期：<用户> / YYYY-MM-DD
- 来源：<本次交互中的回复>
- 理由：用户未说明
- 捡起条件：<按可核对条件描述>
- 去向：未建

| CONC-03 | Major | <影响业务功能> | <位置> | <涉及代码模块> | <一句话白话> | <触发场景> | <不修的后果> | <建议修复> | open |
```

Blocker 或 Major 不进入开放表前都保留完整原发现。普通闭环也记录依据。存在多次决定时，不把不同决定的原发现或撤销留痕合并。旧报告没有原文时，仅在可核对同 ID 旧原文后补齐，不从摘要生成；处置和撤销均走下文共用入口。

`/opsx:quality` 写的记录（双轴原始报告）另加一行来源：驳回人、接受人由 agent 按用户对该 finding ID 的 `AskUserQuestion` 回复写入，规则见 `../../openspec-code-quality/shared/dual-axis-review.md`「裁决规则」。技术评审 `review/<role>.md` 的记录不适用这一条。

### 共用写入入口

分发或准备写入前，运行 `node <SKILL_DIR>/scripts/review-write.mjs snapshot <changeRoot>`。核对该输出的 `planning` 与固定评审输入相同。输出绑定活跃目录实例、完整规划文件集合、逐文件 SHA-256、汇总及报告版本（缺失为 `null`）。不要在确认返回后替换成新版本以沿用旧决定。

将候选作为 JSON 从标准输入交给 `publish`：`expected` 是该输出，`roles` 是全部纳入的维度键，`summary` 是完整汇总，`reports` 是维度键到 Markdown 的映射，`planning` 是同批登记的相对路径到内容的映射（无修改的映射省略）。如需删除已核对且仍存在的增量规格，将该文件映射为 `null`；不删除目录，也不删除提案、设计或任务文件。受保护的入口不能分两次调用完成复核与写入，不用直接 Edit/Write 替代。保护占用或版本不符就停止；只在确认原进程结束后清理遗留保护。先原子写 `BLOCKED` 汇总，再写报告和同批规划，最后写与实际产物相符的汇总。等待用户时发布阻断版并释放保护；最终发布基于处理后的快照。首次替换失败不改其他文件。

撤销以 `withdraw` 传 `expected`、`role`、`id`、`decision`、`actor`、`reason`、`date`；恢复后取当前版本再次调用 `recover`，传 `expected`、`role`、`id`、`decision` 及全部纳入维度 `roles`。恢复核对失败不清除记录。

### 撤销处理决定

撤销风险接受、驳回或移到后续变更时，记录仍留在原维度报告。以 `finding ID` 加原决定标识区分同一 ID 的多次处理。使用共用的 `review-write.mjs` 写入入口，不用两次独立写入代替保护内的复核和写入。

1. **首次替换** `review-summary.md` 时原子写入正文与键名行的 `BLOCKED`，并写「待完成的撤销」；同时把全部同源条件改为 `待处理`，清掉旧落点。无关联条件也写这条记录。首次替换失败不修改角色报告。
2. 在对应维度报告的原决定之后写撤销人、原因与日期，恢复同次原决定的完整原发现，保留同一个 finding ID，将台账和 Findings 改为 `open`。旧报告缺原文时保持阻断并记录原因；只有核对同 ID 原文才能补齐，否则请原维度复核同 ID，不用摘要重建。
3. 继续前从实际落盘内容恢复，不重复写入同次留痕。仅恢复入口可在保护内复核：撤销留痕对应同次原决定、完整原发现已恢复、台账与 Findings 均为开放状态、所有关联条件仍待处理且无旧落点。核对成立才按全部纳入维度重算，并在一次汇总替换中清除该条；其他待完成记录保留。不一致时不清除，保持 `BLOCKED`。
4. 普通发布、处理或规划登记不得清除待完成记录，也不得在有记录时发布可签字裁决。开放 Blocker 仍阻断；重新打开的 Major 按第 5 节处理。旧批准只保留为历史说明，下一次可签字裁决使用留空的人工确认区，必须重新签字。

待完成记录写在人工确认区之前。空节不代表待完成；每行绑定具体决策：

```markdown
## 待完成的撤销

| finding ID | 原决定标识 | 维度 |
|---|---|---|
| ARCH-01 | R3:ARCH-01:1 | architecture |
```

## 5. 定稿与签字后修改

裁决首次为 `READY_FOR_HUMAN_APPROVAL` 的一轮是定稿轮。在 `review-summary.md` 的「定稿与签字后修改」节首行写 `定稿轮：R<n>`。这不是机器可读键。因方案变更重走门禁后，首次再次裁决为 `READY_FOR_HUMAN_APPROVAL` 时改写定稿轮，保留旧登记行。

定稿后每次修改 `proposal.md`、`design.md`、`specs/` 或 `tasks.md`，在同节新增一行。签字前的修改也登记。文件名用相对变更目录的路径，关联填 finding ID 或条件编号；没有关联项时填「无」。

| 序号 | 日期 | 轮次 | 文件:行号 | 关联 | 规划档位 | 说明 |
|---|---|---|---|---|---|---|

| 规划档位 | 判据 |
|---|---|
| 措辞 | 只改用词、错别字或排版；需求、场景、决策与任务的含义不变 |
| 条件落点 | 只写入汇总已列的条件，或用户已选的处理；写入内容不超出条件原文 |
| 范围收窄 | 只移除需求、场景或任务，不增加行为；保留部分不再引用移除的内容 |
| 方案变更 | 其余修改，含新增或改变决策、机制、持久文件、状态、需求或场景行为 |

判据不确定时取方案变更。措辞、条件落点、范围收窄不使签字失效；方案变更必须重走受影响维度，再由人工签字。签字后已登记的规划差异仍须按 `apply-gate-check.md` 请用户确认。

「定稿与签字后修改」与「收敛检查」都放在人工确认区之前。登记内容只写在表格行内。「说明」列以「用户选择：」或「agent 判定：」开头，不写行首的 `Gate-Verdict` 或 `Technical Review Approved` 键名。

### 定稿前处理开放 finding

实质 Blocker 或其他打回原因未清除时，不询问开放 Major。清除后、定稿和提示签字前，主会话询问每条开放 Major；Minor 可按维度合并。只待选择或写入所选修复时保留 `BLOCKED`，正文写「待条件处理」。收窄范围或接受 Blocker 后同样先处理剩余条件，不先定稿。

处理方式：

| 处理 | 写入位置 | 重走门禁 | 条件状态 |
|---|---|---|---|
| 修复 | 一次 `/opsx:update` 写入原条件；未修改运行假设时登记为条件落点，由 quality 与 verify 验收 | 不重走；修改运行假设时全量重走 | `已写入` |
| risk accepted | 按第 4 节写接受记录与复查触发阈值 | 不重走 | `risk-accepted` |
| 误报 | 按第 4 节写驳回记录 | 不重走 | `false-positive` |
| 移到后续变更 | 按第 4 节写处理记录与去向 | 不重走 | `deferred` |

后面三种只留痕，不改规划。推荐项按顺序取第一条符合的：

1. 汇总「疑似误报检测」判为误报：推荐误报。
2. 修复只改既有决策内的参数、边界、顺序或拒绝分支：推荐修复。
3. 修复要新增状态、持久文件、子命令或协议，且不修只会误拒绝或交回会话：推荐 risk accepted。
4. 其他情况：推荐移到后续变更。

每个选项说明修复是否新增机制，并写清「不重走」或「全量重走」。开放 Major 不超过 4 条时用 AskUserQuestion 逐条询问；超过 4 条时先输出 `ID | 一句话白话 | 推荐处理 | 理由` 表，请用户确认整表或改写行。用户回复写处理记录的来源。

首次定稿前的条件落点也按本节登记，逐处核对后写已核对版本，未定稿不写定稿轮。处理完成后，先比较当前运行假设与固定输入，再核对全部纳入维度、条件落点及待完成的撤销。任何一项不可核对时保持 `BLOCKED`；运行假设变化及依赖修改按第 2 节登记方案变更并全量重走，优先于条件落点。通过后才用第 4 节共用入口发布可签字裁决并写定稿轮。

### 固定评审输入与登记基线

分发前读取并固定本轮规划文件集合和原始内容。用同一份内容计算逐文件原始 SHA-256 和任务内容 SHA-256，并记录 `登记基线序号：<非负整数>`（当时登记表最后序号，空表为 0）。登记序号用递增且不重复的正整数，旧行保留，不重新编号。各维度只审阅分发的版本，不重新读取磁盘上的方案作为输入。本轮输入内容保留在会话中，不另写持久文件。

汇总前再次核对磁盘的文件集合与原始 SHA-256。汇总只转录分发时的哈希和登记基线序号，不用当前值替换。无法确认评审使用了固定版本，或发现输入不一致时，不发布可签字裁决：写 `BLOCKED` 并提示按新输入重走评审。

### 逐处核对登记差异

update 或技术评审 Step 3 写规划前，保留修改前文件的内容，并核对文件集合与哈希匹配评审输入或上一个已核对版本。缺少可验证的修改前内容时停止，不能补写评审版本。

将本批全部差异逐处对应到本批新增登记的文件、位置和规划档位判据；包括新增或删除文件。同一文件有登记不代表其全部差异已登记。采用条件落点时对照条件原文或已留痕的用户选择；采用范围收窄时只允许符合第 6 节的删除。存在未登记或超出判据的差异时停止，不写已核对版本。

通过核对后，在同一 `review-summary.md` 的「已核对版本」小节记录差异与登记的对应关系、完整文件集合、逐文件原始 SHA-256、任务内容 SHA-256 和已核对登记的最后序号。后续批次先核对上一个已核对版本，再核对本批差异。保留本轮原始评审输入和登记基线序号；不得用已核对版本替换。方案变更仍须重走门禁，不因记录已核对版本而放行。

### 评审输入版本与任务进度

逐文件记录原始 SHA-256。比较集合是汇总列出的文件与当前 `proposal.md`、`design.md`、`tasks.md`、`specs/` 下全部文件的并集；新增或删除的规划文件按已改变处理。`tasks.md` 另记录任务内容 SHA-256。评审与 apply 用同一规则计算：

1. 只移除一级标题后首个非空行中符合 `基线任务数：N（YYYY-MM-DD 首次 apply）` 格式的行及该行末尾的换行符。首次 apply 写入该行时保留原有空行。
2. 只将顶层任务项的 `- [x] ` 前缀换成 `- [ ] `。代码块中的示例按原字节保留；其余文本、顺序、空白与换行原样保留。
3. 对所得字节计算 SHA-256。新增、删除、移动或改写任务都不属于进度记录。

首次写入基线任务数、勾选既有任务不登记，也不改变切片证据要求。两边都存在的 `tasks.md` 原始值不同时，只有汇总中的任务内容 SHA-256 有效且与当前值相同，才把该文件按未改变处理。旧汇总没有任务内容 SHA-256 时，仍比较原始值；禁止用当前文件补写评审输入版本。


## 6. 收敛检查

从第 3 轮起，在 `review-summary.md` 的人工确认区之前写「收敛检查」。第 1、2 轮不写此节。表格从 R1 开始，每轮一行；「纳入」含重跑与沿用维度。「新增」只计本轮的新编号，不重复统计沿用或再次报告的同一 finding。R1、R2 将各轮行所需的统计和 finding 编号沿用在「上轮闭环验证结果」等既有小节，不新增「收敛检查」。覆盖汇总前读取既有汇总与评审记录，缺少的历史值写「未知」，不当成零。

| 轮次 | 纳入维度数 | 新增 Blocker | 新增 Major | 开放 Blocker |
|---|---|---|---|---|

第 3 轮起，裁决为 `BLOCKED` 且本轮新增 Blocker 与 Major 之和不少于上一轮时，向用户提供以下选项。两轮新增数无法确定时，不能认定触发条件成立。

| 选项 | 处理 | 重走范围 |
|---|---|---|
| 收窄范围 | 把开放 Blocker 命中的需求移出本变更，记入 proposal「不做」，在第 5 节登记范围收窄；尚无登记表就创建该表，不提前填写定稿轮 | 不重走；移出的需求不再评审 |
| risk accepted | 按第 4 节具名留痕 | 不重走 |
| 继续修复 | 回改 design 并登记闭环记录 | 重走：按第 3 节列出受影响维度 |

只有当 Blocker 的「位置」与「涉及代码模块」所列内容都已从保留的 design、specs、tasks 移除，才能将其标为 `closed`。在原维度报告保留完整原发现及处理记录，汇总保留同 ID 依据，闭环依据写「范围收窄 #<登记序号>，已移除：<位置>」。若根源仍支撑保留的需求或决策，该 Blocker 保持 `open`，只提供 risk accepted 与继续修复。

Step 3 在本轮增加范围收窄登记，保留分发时的原始哈希和登记基线序号。关闭 Blocker 或重算裁决前，按第 5 节逐处核对全部差异，记录已核对版本。存在未登记的保留内容修改或无法核对时，保持开放，不发布可签字裁决。

按第 1 节对全部纳入维度重新计算裁决，不启动新的评审子 agent。实质阻断清零后，先按第 5 节处理开放 Major 与待处理条件，再按第 4 节复核待完成的撤销。同轮裁决首次成为 `READY_FOR_HUMAN_APPROVAL` 时，才更新汇总裁决和 `Gate-Verdict`、写 `定稿轮：R<n>` 并提示人工签字。只在维度原有打回依据均已闭环时更新其结论；其他仍成立的打回依据和开放 Blocker 继续阻断。verify 按 `phase6-verification.md` 核对该关闭依据。
