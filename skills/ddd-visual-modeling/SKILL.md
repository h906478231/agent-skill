# DDD 可视化建模完整流程

> 从代码到交互式流程图的一站式解决方案

## 定位

- 本 skill 是**流程编排器**，负责协调三个阶段的执行
- 不负责具体的分析、建模、可视化逻辑（委托给子 skill）
- 负责阶段间的数据传递和错误处理

## 三阶段架构

```
┌─────────────────────────────────────────────────────────┐
│                   完整处理流程                             │
└─────────────────────────────────────────────────────────┘

阶段 1: 代码与文档分析
┌──────────────────────┐
│ ddd-code-doc-analyzer │
│  • 解析代码结构        │
│  • 提取业务语义        │
│  • 生成业务描述        │
└──────┬───────────────┘
       │ 统一业务描述
       ↓
阶段 2: DDD 建模
┌──────────────────────┐
│ ddd-modeling-workflow │
│  • 7 阶段建模流程      │
│  • 输出领域模型        │
└──────┬───────────────┘
       │ 建模产物（事件/命令/聚合/Policy）
       ↓
阶段 3: 交互式可视化
┌──────────────────────┐
│ddd-event-storm-       │
│   visualizer          │
│  • 生成 Mermaid 图    │
│  • 添加交互层         │
│  • 输出 HTML 文件     │
└──────┬───────────────┘
       │ event-storm.html
       ↓
   交互式流程图
```

## 输入参数

### 必需参数

- **codePath**: 代码路径（目录或文件列表）
- **scope**: 分析范围（业务模块名或子域名）

### 可选参数

- **docPath**: 需求文档路径（可选，但推荐提供）
- **outputPath**: 输出文件路径（默认：`./event-storm-{scope}.html`）
- **enableDataChange**: 是否启用数据变更展示（默认：false，V2 功能）
- **skipConfirmation**: 跳过建模确认（默认：false，谨慎使用）

## 执行流程

### 前置检查

1. **验证输入路径**
   - 检查 codePath 是否存在
   - 检查 docPath 是否存在（如果提供）
   - 检查 outputPath 的目录是否可写

2. **分析范围确认**
   - 如果 scope 未指定，尝试从代码结构推测
   - 列出识别的模块，让用户确认

**输出示例**：
```
检测到以下业务模块：
  1. 用户管理 (com.example.user)
  2. 订单管理 (com.example.order)
  3. 库存管理 (com.example.inventory)

请指定要分析的模块（输入编号或名称）：
```

### 阶段 1：代码与文档分析

**执行**：调用 `ddd-code-doc-analyzer`

**输入**：
- codePath
- docPath
- scope

**输出**：
```markdown
# 业务需求描述

## 业务背景
...

## 核心场景
...

## 业务术语
...

## 参与者与外部系统
...

## 业务流程与规则
...

## 待确认问题
...
```

**检查点**：
- [ ] 业务术语表不为空
- [ ] 至少识别出一个核心场景
- [ ] 至少识别出一个参与者或外部系统

**如果检查点失败**：
- 提示用户提供更多信息（文档或口头描述）
- 询问是否继续（可能建模质量下降）

---

### 阶段 2：DDD 建模

**执行**：调用 `ddd-modeling-workflow`

**输入**：阶段 1 的业务需求描述

**输出**：
```markdown
## 需求摘要
...

## 限界上下文 / 子域清单
...

## 领域事件清单
...

## 领域命令清单
...

## Policy 清单
...

## 聚合清单
...

## 聚合协作约束
...

## 读模型清单
...

## 待确认问题清单
...
```

**检查点**：
- [ ] 至少识别出 1 个命令
- [ ] 至少识别出 1 个事件
- [ ] 至少识别出 1 个聚合
- [ ] 命令-事件映射完整（每个命令都有产生的事件）

**如果有待确认问题**：
- 列出待确认问题清单
- 询问用户是否现在确认（可选择跳过，后续修正）

**建模确认**（除非 skipConfirmation=true）：
```
建模完成，识别到：
  • 5 个命令
  • 6 个事件
  • 2 个聚合
  • 3 个 Policy

待确认问题：
  1. 超时未支付订单的库存如何恢复？
  2. ...

是否继续生成流程图？(y/n/review)
  y: 继续
  n: 中止
  review: 查看完整建模结果
```

---

### 阶段 2.5：建模数据校验（Verify）

**执行**：在生成流程图前校验建模数据

**目标**：确保建模产物完整、一致，避免生成失败

**校验内容**：
1. **完整性检查**：commands/events/aggregates/policies 对象都存在
2. **引用一致性**：所有引用的 ID 都存在
3. **必填字段**：关键字段都已填写

**校验通过**：
```
✅ 建模数据校验通过

统计信息：
  • 5 个命令
  • 6 个事件
  • 2 个聚合
  • 3 个策略
  
所有引用关系一致，准备生成流程图...
```

**校验失败**：
```
❌ 建模数据校验失败

引用一致性问题：
  • 命令 C1 引用的聚合 'OrderAggregate' 不存在
  • 命令 C2 引用的事件 'E99' 不存在

必填字段问题：
  • 事件 E1 缺少 meaning 字段

是否修正后重试？(y/n)
```

**处理方式**：
- 校验通过 → 继续阶段 3
- 校验失败 → 显示错误详情，询问用户是否修正

---

### 阶段 3：交互式可视化

**执行**：调用 `ddd-event-storm-visualizer`

**输入**：阶段 2 的建模产物

**输出**：交互式 HTML 文件

**检查点**：
- [ ] HTML 文件成功生成
- [ ] 文件大小合理（> 10KB，包含完整代码）
- [ ] 包含所有节点的交互数据

**生成成功提示**：
```
✅ 交互式事件风暴流程图已生成

文件路径: ./event-storm-order.html
文件大小: 45 KB

包含内容:
  • 5 个命令节点
  • 6 个事件节点
  • 2 个聚合节点
  • 3 个 Policy 节点

功能：
  ✓ 点击节点查看详情
  ✓ 高亮处理链路
  ✗ 数据变更展示（未启用）

在浏览器中打开查看：
  file://./event-storm-order.html
```

## 错误处理

### 阶段 1 失败：代码分析失败

**可能原因**：
- 代码路径错误
- 代码结构无法识别（非标准项目结构）
- 代码语言不支持

**处理方式**：
1. 提示用户检查路径
2. 询问是否手动提供业务描述（跳到阶段 2）
3. 提示支持的代码语言和项目结构

---

### 阶段 2 失败：建模失败

**可能原因**：
- 业务描述信息不足
- 业务逻辑过于复杂
- 存在无法解析的歧义

**处理方式**：
1. 列出缺失的信息
2. 询问用户补充
3. 提供简化建模的选项（只建模核心流程）

---

### 阶段 3 失败：可视化失败

**可能原因**：
- 建模产物格式错误
- 节点数量过多（> 100）
- 输出路径不可写

**处理方式**：
1. 检查建模产物完整性
2. 建议拆分子域（如果节点过多）
3. 检查输出路径权限

## 配置选项

### 代码分析配置

```yaml
codeAnalysis:
  # 支持的代码语言
  supportedLanguages: [java, python, typescript, go]
  
  # 忽略的目录
  ignoreDirs: [test, tests, __tests__, node_modules, target, build]
  
  # 最大分析文件数
  maxFiles: 500
```

### 建模配置

```yaml
modeling:
  # 是否自动回答待确认问题（不推荐）
  autoAnswer: false
  
  # 简化模式（只输出核心流程）
  simplified: false
  
  # 最大命令数（超过则建议拆分）
  maxCommands: 50
```

### 可视化配置

```yaml
visualization:
  # 图表布局方向
  direction: LR  # LR (左右) | TB (上下)
  
  # 节点样式主题
  theme: default  # default | dark | colorful
  
  # 是否显示节点编号
  showNodeId: true
  
  # 数据变更展示（V2 功能）
  enableDataChange: false
```

## 常见问题

### Q1: 代码分析不准确怎么办？

**A**: 提供更详细的需求文档，或手动补充业务描述。代码是实现细节，文档是业务意图的最佳来源。

### Q2: 流程图节点太多看不清？

**A**: 考虑拆分子域。一个子域的命令数建议不超过 20 个。使用 `--scope` 参数缩小分析范围。

### Q3: 想修改建模结果怎么办？

**A**: 保存中间产物（`{scope}-domain-model.md`），手动修改后使用 `--input-model` 参数重新生成流程图。

### Q4: 支持哪些代码语言？

**A**: MVP 版本优先支持 Java（Spring Boot）。后续会支持 Python、TypeScript、Go 等。

### Q5: 生成的流程图能二次编辑吗？

**A**: V1 不支持。推荐的工作流是：修改建模文档 → 重新生成流程图。V2 会考虑双向同步。
