# Phase 2: 方案探索与交叉验证

> 当 `openspec-architect` 决定进入 Phase 2 时，加载本 skill 执行方案设计。本 skill 只负责方案生成、对比分析和逻辑产物输出，不负责 OpenSpec API 调用和文件落盘。

## 执行前提

- 输入应为 Phase 1 的产物包（proposal.md 内容）
- Phase 1 必须已通过门禁（第一性原理分析完整、高优先级问题已回答）
- 本 skill 不直接调用 OpenSpec API，只输出逻辑产物包

## 核心任务

Phase 2 的核心任务是**在多个候选方案之间做出有依据的选择**。单一方案无法交叉验证，至少需要 2 个有实质差异的候选方案。

## 执行规则

### 1. 生成候选方案（至少 2 个）

**目标**：识别至少 2 个有实质差异的技术方案

**"有实质差异"的判断标准**：
- ✓ 架构不同（如：单体 vs 微服务）
- ✓ 技术栈不同（如：同步 vs 异步）
- ✓ 成本差异显著（如：自建 vs SaaS）
- ✗ 只是参数微调（如：缓存过期时间 5 分钟 vs 10 分钟）
- ✗ 只是命名不同（如：UserService vs AccountService）

**方案生成策略**：

**策略 1：从简单到复杂**
- 方案 A：最简单可行（MVP）
- 方案 B：平衡方案（满足当前需求 + 适度扩展性）
- 方案 C：过度设计（为了对比，展示"做太多"的成本）

**策略 2：从约束出发**
- 方案 A：优先满足资源约束（时间/预算最少）
- 方案 B：优先满足性能约束（性能最优）
- 方案 C：优先满足可维护性（长期成本最低）

**策略 3：从技术路线出发**
- 方案 A：同步方案（如：直接数据库查询 + 索引优化）
- 方案 B：异步方案（如：Redis 缓存 + 异步更新）
- 方案 C：离线方案（如：定时任务 + 物化视图）

**每个方案必须包含**：
- 方案名称（简短描述性名称）
- 核心思路（一句话）
- 架构图或关键组件
- 技术栈
- 数据流
- 关键实现细节

### 2. 四维对比矩阵（必需）

**对比维度**：

**维度 1：成本**
- 开发成本（人日，如：2 人日）
- 资源成本（如：需要引入 Redis / MQ / 新增 2 台服务器）
- 学习成本（如：团队需要学习新技术）
- 迁移成本（如：需要数据迁移 / 灰度发布）

**维度 2：性能**
- 响应时间（如：P50 / P95 / P99）
- 吞吐量（如：QPS / TPS）
- 资源消耗（如：CPU / 内存 / 磁盘 IO）
- 是否阻塞（同步 vs 异步）

**维度 3：复杂度**
- 开发复杂度（如：需要处理分布式事务 / 消息重试）
- 测试复杂度（如：需要 mock 外部依赖 / 集成测试）
- 运维复杂度（如：需要监控 MQ / 处理死信队列）
- 理解成本（新人能否快速上手）

**维度 4：风险**
- 技术风险（如：新技术不稳定 / 团队不熟悉）
- 扩展性风险（如：无法应对未来数据量增长）
- 依赖风险（如：引入新的外部依赖 / 单点故障）
- 业务风险（如：不满足 SLA / 数据一致性问题）

**对比矩阵格式**：

```markdown
## 候选方案交叉验证矩阵

| 维度 | 方案 A（如：同步批量插入） | 方案 B（如：异步 MQ 分片消费） | 方案 C（如：ETL 离线导入） |
|------|------------------------|---------------------------|----------------------|
| **成本** | 开发 2 人日 / 无额外资源 | 开发 5 人日 / 需引入 MQ | 开发 3 人日 / 需 ETL 调度平台 |
| **性能** | 10 万条需 5 分钟，阻塞 | 10 万条需 2 分钟，非阻塞 | 10 万条需 10 分钟，离线无感知 |
| **复杂度** | 低：单体同步逻辑 | 高：需处理消息重试/死信/幂等 | 中：需配置 ETL 任务与监控 |
| **风险** | 超时风险高，无法扩展 | MQ 依赖引入新故障点 | ETL 平台依赖，实时性差 |
```

### 3. 推荐方案及决策依据（必需）

**必须回答的三个问题**：

**3.1 推荐哪个方案？**
- 明确推荐方案名称
- 一句话说明推荐理由

**3.2 为什么不选其他方案？**
- 逐个说明为什么不选方案 A、B、C...
- 必须有具体理由，不能只说"不够好"

**3.3 推荐方案是否解决了 Phase 1 的底层问题？**
- 回溯 Phase 1 的"底层问题"
- 验证推荐方案是否直接解决该问题
- 如果不匹配，说明是需求理解偏离，需要回退 Phase 1

**输出格式**：

```markdown
### 推荐方案及决策依据

- **推荐**：方案 B（异步 MQ 分片消费）
- **决策依据**：
  1. 性能满足需求（2 分钟 < 目标 3 分钟），且非阻塞不影响用户操作
  2. 复杂度虽高但可复用现有 MQ 基础设施（已有 RabbitMQ 集群）
  3. 可扩展性强，未来百万级数据只需加消费者实例
  4. 风险可控：MQ 故障有降级方案（回退到方案 A 的同步小批量）

- **为什么不选方案 A（同步批量插入）**：
  - 超时风险无法接受（当前已有 5 万条数据，方案 A 需 2.5 分钟，接近超时边界）
  - 阻塞用户操作，影响体验
  - 无法扩展到未来百万级数据

- **为什么不选方案 C（ETL 离线导入）**：
  - 业务要求 5 分钟内可见（实时性要求），离线 ETL 延迟 10+ 分钟不满足
  - 引入 ETL 平台依赖，增加系统复杂度

- **回溯第一性原理验证**：
  - Phase 1 的底层问题：**大批量数据导入不能阻塞用户操作**
  - 方案 B 直接解决此问题：异步非阻塞，用户无感知
  - 方案 A 仍会阻塞，方案 C 虽不阻塞但实时性不足
  - ✓ 推荐方案与底层问题匹配
```

### 4. 设计细节

**必须包含的设计内容**：

**4.1 架构设计**
- 系统架构图（可以用 Mermaid 图或 ASCII 图）
- 核心组件及职责
- 数据流转路径

**4.2 关键设计决策**
- 数据模型设计
- 接口设计（API / 消息格式）
- 并发控制（乐观锁 / 悲观锁 / 分布式锁）
- 事务边界
- 错误处理
- 监控告警

**4.3 边界场景处理**
- 异常场景（如：超时 / 失败 / 重试）
- 并发场景（如：多人同时操作）
- 边界场景（如：空数据 / 超大数据）
- 降级方案（如：依赖不可用时如何处理）

**4.4 非功能性需求**
- 性能指标（如：响应时间 < 100ms，QPS > 1000）
- 可用性指标（如：99.9% 可用性）
- 可扩展性（如：支持水平扩展）
- 安全性（如：认证 / 授权 / 数据加密）

### 5. 被否决方案（如有）

记录过程中考虑过但被否决的方案，避免后续重复讨论。

**格式**：
```markdown
### 被否决方案

#### 方案 X：使用 Elasticsearch 全文搜索

- **方案描述**：将订单数据同步到 ES，通过 ES 查询
- **否决理由**：
  1. 引入 ES 集群成本高（运维 + 资源）
  2. 团队无 ES 运维经验，风险大
  3. 当前需求不需要全文搜索，SQL + 索引已足够
- **否决时间**：2026-08-20
```

### 6. 识别待确认问题

**Phase 2 常见的待确认问题**：

**架构选择相关**：
- 是否需要考虑未来迁移到微服务？
- 是否需要支持多租户？
- 是否需要跨地域部署？

**技术栈相关**：
- 团队是否熟悉推荐的技术栈？
- 是否有现成的基础设施可以复用？
- 是否有技术选型限制？

**性能相关**：
- 实际的并发量是多少？
- 可接受的响应时间是多少？
- 是否有突发流量场景？

**输出格式**：
```json
{
  "id": "Q2",
  "priority": "medium",
  "question": "团队是否熟悉 RabbitMQ？是否有现成的 MQ 集群可以复用？",
  "options": [
    "熟悉，有现成集群",
    "熟悉，需要新建集群",
    "不熟悉，需要学习",
    "完全没接触过"
  ],
  "status": "pending",
  "impacts": ["implementation_complexity", "timeline"],
  "blocking": false,
  "reason": "影响实施复杂度和时间预估"
}
```

## Phase 2 检查点（自检）

在输出产物包前，执行以下检查：

- [ ] 至少有 2 个有实质差异的候选方案
- [ ] 四维对比矩阵完整（成本 / 性能 / 复杂度 / 风险）
- [ ] 推荐方案有明确决策依据
- [ ] 回答了"为什么不选其他方案"（逐个说明）
- [ ] 推荐方案回溯验证了 Phase 1 的底层问题
- [ ] 设计细节覆盖架构、数据模型、接口、并发、错误处理
- [ ] 边界场景处理完整（异常 / 并发 / 边界）
- [ ] 非功能性需求已明确

**如果检查点未全部通过**：
- 不输出产物包
- 说明缺少什么
- 给出补充建议

## 注意事项

### 必须有至少 2 个候选方案

- 单一方案无法交叉验证
- 如果只能想到 1 个方案，说明思考不够深入
- 可以生成"过度设计"方案作为对比

### 对比矩阵必须完整

- 四个维度都必须填写
- 不能只说"方案 B 更好"，必须量化
- 成本要具体（人日 / 资源）
- 性能要具体（响应时间 / QPS）

### 必须回答"为什么不选其他方案"

- 逐个说明，不能遗漏
- 必须有具体理由
- 不能只说"不够好"

### 必须回溯验证 Phase 1

- 检查推荐方案是否解决了 Phase 1 的底层问题
- 如果不匹配，标记为需要回退 Phase 1
- 不要强行推进

## 总结

Phase 2 的核心价值是**有依据的方案选择**。通过候选方案交叉验证，避免"只看到一个方案，没有对比就做决策"。

**核心原则**：至少 2 个方案，四维对比，必须回答"为什么不选其他方案"。
