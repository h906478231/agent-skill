# 访谈核心机制：决策树 + frontier 分轮提问

> 本文件是访谈机制的唯一事实源，SKILL.md 引用不复制。

## 决策树模型

把变更的设计问题组织成一棵**决策树**：每个决策节点分出「挂在这个决策上的后续决策」。例如「订单要不要支持部分取消」决定了「部分取消时库存怎么还」「已支付金额怎么退」——后两者依赖前者，前者未定时问它们等于瞎猜。

## frontier 与轮次

**frontier = 前置决策都已明确的那些问题**：现在就能问、不用等你还没听到的答案。

- 一轮提问 = 一次性问出整个 frontier，每问编号、附推荐答案
- 用户答完一轮 → 已定决策把 frontier 向外推，解锁下游问题 → 重算 frontier，进入下一轮
- **某问题的答案依赖本轮还未定的问题 → 它属于后面的轮次，本轮禁止问**

一轮的格式：

```markdown
❓ **Q1 - 部分取消**：订单能否只取消其中部分商品？
（背景：当前 `OrderService.cancel()` 整单取消。若支持部分取消，库存与退款逻辑复杂度翻倍）

➡️ 推荐：不支持。近三个月无部分取消客诉，先做整单取消 + 手工客服通道兜底。

---

❓ **Q2 - 取消窗口**：支付完成后多久内允许取消？

➡️ 推荐：30 分钟内，与现有支付渠道的自动关单时间对齐。
```

## 每问必附推荐答案

不附推荐的提问是把设计工作推回给用户。推荐答案要求：

- 给出明确倾向 + 理由（引用代码事实、既有约定或量级数据）
- 多选一时列出被否选项的关键缺陷
- 推荐错了由下一轮纠正——推荐是加速器，不是结论

## 职责划分

| 类型 | 归属 | 动作 |
|------|------|------|
| 事实（代码现状、表结构、既有约定、环境） | **agent** | 派子 agent 查证；返回走 `openspec-discussion-sync` 五段契约；结论标注依据（file:line 或「推断，未验证」） |
| 决策（业务规则、取舍、优先级、口径） | **用户** | 编号提问 + 推荐答案，等用户拍板 |

正在跑的子 agent 也是「未定前置」：只让依赖它的问题等待，frontier 上其余问题照常问，**不要空转等探索结果**。

## 结束条件（两个都要满足，缺一不可）

1. **本次阻断 frontier 为空**：关键决策已确认；无关或明确延期的问题记录范围与理由，不扩展到所有可能的设计。无进展时暂停并列出阻塞项，不假装达成共识
2. **用户确认共识**：输出共识摘要（已定决策 / 弃掉的方案 / 开放问题），用户显式说「确认」或等义表述

用户确认前，**不得基于访谈结论开始任何产出动作**（写 proposal、生成 artifact）。

## 领域语言压力测试（访谈中的三个主动动作）

提问之外，以下三个动作**当场触发、不等访谈结束**（源自 domain-modeling 实践，是消除概念模糊的主要手法）：

| 触发 | 动作 | 示例 |
|------|------|------|
| **用户用词模糊或 overloaded** | 当场逼问精确化，给出候选切分 | 「你说的 account 是 Customer（下单的人）还是 User（登录账号）？这是两个东西」 |
| **讨论领域关系/规则时** | 发明具体边界场景压测，迫使双方明确概念边界 | 「两个客服同时取消同一单会怎样？」「部分支付后再取消，退多少？」——答不上来说明边界没定清楚 |
| **用户陈述与代码行为可能矛盾** | 主动对照代码，矛盾当面指出 | 「你说订单可以部分取消，但代码 `OrderService.cancel()` 是整单取消——哪个是对的？」 |

第三个动作是防隐含假设的头号手段：用户记忆中的系统行为与代码实际行为不一致，是需求误解的最大来源。澄清后立即更新 `CONTEXT.md`（见 `context-format.md` 更新时机表）。

## 常见走样（自查）

| 走样 | 纠正 |
|------|------|
| 一次把所有问题平铺出来 | 只有 frontier 上的问题进本轮；依赖未定答案的收回去 |
| 问用户「代码里有没有 X」 | 这是事实，自己查；查完把结论带回再问决策 |
| 推荐答案写「两种都行」 | 必须有倾向；真两可时列差异请用户选，那本身就是决策 |
| 用户答了一半就推进 | 一轮的全部问题有答复（或被用户明确搁置并记录）才进下一轮 |
| 结束时说「那就按刚才说的做」 | 必须输出共识摘要并取得显式确认 |
