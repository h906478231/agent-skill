# DDD 流程管理器 (SAGA / Process Manager)

> 来源: https://ddd-fans.github.io/ddd-guideline/

## 定义
用一个对象负责管理一个长业务流程的执行，这个对象就是流程管理器（Process Manager, SAGA）。

## SAGA 词源
源自古斯堪的那维亚语"长篇故事"，计算机术语来自 Hector Garcia-Molina 和 Kenneth Salem 1987 年论文《SAGAS》。

## 长业务流程特征
- **多本地事务**：由多个本地数据库事务组成，不在一次事务中完成
- **可暂停**：流程可被阻塞、暂停、持久化，条件满足时继续执行
- **耗时长**：时间跨度从数秒到数天甚至数年

典型例子：审批流程进入等待人工审核状态后，流程对象不能一直在内存中，必须持久化。

## 是否必须建模
不是。并非所有业务场景都有长流程需要建模。

## 何时建模流程管理器
业务中存在需要明确表达的长流程时。表达长流程有两种方式：
- **编制 (orchestration)**：集中由一个对象协调流程 → 流程管理器
- **编排 (choreography)**：分散的多个业务对象间协作完成流程

前者更直观，后者更灵活。需要编制时就设计流程管理器。

## 流程管理器是聚合吗
如果需要自己实现，它是一个聚合：
- 有自己的 id
- 有状态变化
- 承担推动流程执行直到稳定状态的职责

如果借助流程引擎（BPM），由外部系统负责实现，就不在我们的问题域内，不需要标记为聚合。

## BPM vs 流程管理器
- BPM 是标准化的专业流程工具，可定义、执行、管理流程
- 简单场景：BPM 引入复杂性，直接编码成本更低
- 流程多且经常变动：专业 BPM 引擎更低成本应对

## SAGA 是一种聚合
承担协作职责，有状态长期存在，需要持久化和载入，有 id，符合聚合定义。聚合可以触发命令的执行。

## 远程 HTTP 写操作的 Saga 判定规则

### 默认原则
跨服务远程 HTTP 写操作，不应被当作单个本地事务的一部分来追求伪强一致。

### 三种处理方式
#### 1. 同步前置校验
适用条件：
- 远程调用只是查询、校验、风控判断、配额检查。
- 不改变远程系统状态。

建议：
- 允许同步调用。
- 默认放在本地事务开始前完成。

#### 2. 提交后最终一致
适用条件：
- 远程调用是提交后的副作用传播。
- 失败时不要求本地事务回滚，只要求重试和最终送达。

建议：
- 不建模 Saga。
- 使用 `Outbox -> relay -> HTTP adapter`。

#### 3. Saga / 流程管理器
适用条件：
- 远程 HTTP 写是核心业务步骤，而不是可忽略的副作用。
- 失败后需要补偿前置动作，或等待回调 / 异步确认。
- 流程跨多个本地事务推进。

建议：
- 升级为 Saga / Process Manager 建模。
- 在建模文档中明确：流程状态、推进事件、补偿命令、终止条件。
- 未完成这些建模前，不生成“本地事务 + 同步远程写”代码模板。
