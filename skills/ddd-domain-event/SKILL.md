# DDD 领域事件

> 来源: https://ddd-fans.github.io/ddd-guideline/

## 一、建模篇

### 定义
领域事件是问题域中已发生的、对解决问题有用的事件。不可变，一旦确定发生就不会变更。

### 命名规则
必须用完成时态。例如"已取消订单"而非"取消订单"，要表达出事实已经发生。

### 是否必须
- 事件风暴建模方式：领域事件是必须的
- 其它建模方式：不一定需要

### 作用
- 作为业务决策和逻辑判断的事实依据。例如判断订单能否取消，需依据"已创建订单""已取消订单"等事实
- 驱动事件驱动的业务流程，模块内外通过监听领域事件执行动作

### 与聚合的关系
- 领域事件必须由聚合发出（对当前系统和上下文而言）
- 如果事件发生后领域模型没有任何改变，该事件无意义
- 领域模型的变化通过聚合内部状态变化体现
- 聚合应封装状态变化和领域事件发布逻辑，确保状态变化必定发布事件
- 不存在不使用聚合就发布领域事件的途径

### 本质
领域事件是一种值对象。

## 二、实现篇

### 是否必须实现
即使不用 CQRS、不用事件溯源，只要建模出了领域事件，建议照样发布。领域事件是很好的扩展机制，将来补发成本更高。

### 标准字段
- id：唯一标识事件
- 事件类型
- 发出事件的聚合类型
- 发出事件的聚合 id
- 事件内容（业务场景数据）
- 事件发生的时间

### 为什么需要 id
主要用于唯一区分事件，对幂等消费很有用。

### 在哪里发布领域事件
- 最佳：在聚合对象内直接发布（封装业务逻辑，避免泄露）
- "XX已创建"类事件：在工厂里发布合理（创建时聚合本身还不存在）
- 受框架限制不能在聚合内发布时：妥协处理

### 事件发出与投递时机

| 方式 | 特点 | 回滚 |
|------|------|------|
| 事务内立刻投递 | 聚合未写入数据库，需确保内存中同一对象 | 可回滚 |
| 事务内聚合持久化后投递 | 暂存事件，持久化后再投递 | 可回滚 |
| 事务内提交前投递 | 变更已写入数据库但仅当前事务可见 | 可回滚 |
| 事务外提交后投递 | 变更已持久化，失败需最终一致性 | 不可回滚 |

### 是否需要持久化
建议都持久化。用途：
- 排查业务问题
- 给将来新聚合或读模型回溯用
- 商业智能、数据挖掘

### 广播 vs 队列
领域事件本身是广播语义，所有监听者都可监听到。具体技术实现可选发布订阅或队列模式。

### 监听方式
- 同进程内：监听者模式，同步/异步，事务内/外
- 分布式：共享存储（redis、数据库）轮询
- MQ 中间件：ActiveMQ、RabbitMQ、Kafka 等

### 分布式发布
关注最终一致性时采用发件箱模式。

### 幂等消费
- 有 id：记录已消费 id，每次查询是否消费过
- 无 id：结合业务数据做幂等（如订单号）
- 建议将 id、类型等放消息头部，避免解析消息体

## 三、何时不用领域事件承载主流程

领域事件表达的是“业务事实已经发生”，不应默认承担当前用例中必须同事务完成的主流程编排职责。

### 应改为同步编排的场景
满足以下任一条件时，优先直接在 `Application Service` 中同步编排，不要把它做成事件监听：
- 该后续动作失败时，主用例必须整体失败并回滚。
- 该动作属于当前用例的必做步骤，而不是提交后的扩展反应。
- 该动作只是本地多个命令处理器之间的显式顺序编排。

### 适合使用领域事件的场景
- 提交后通知、审计、埋点、读模型刷新。
- 允许重试和最终一致的跨系统副作用。
- 当前用例之外的扩展消费方需要订阅该业务事实。

### 与 Spring 事件、Outbox 的关系
- Spring 事件是同进程内的一种投递机制，不应被当作领域事实的唯一持久化来源。
- 需要最终一致和可重试时，优先把领域事件持久化到 Outbox，再由 Outbox relay 投递 Spring 事件或 MQ。
- 如果某一步骤要求强一致回滚，不要把它降级为 `@EventListener` 或同类监听机制。
