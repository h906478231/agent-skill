# DDD 事件溯源与 LMAX 架构

> 来源: https://ddd-fans.github.io/ddd-guideline/

## 一、事件溯源 (Event Sourcing)

### 定义
只持久化领域事件，不持久化聚合。命令到达要载入聚合时，通过回溯领域事件重建聚合。

### 优点
- **高性能写**：只持久化领域事件（时间序列不可变数据），只插入不更新，顺序写性能极高
- **聚合设计更灵活**：不用考虑聚合持久化问题（ORM 映射限制），完全自由设计聚合内部状态
- **时间机器**：查看任意时刻聚合状态，用于业务分析、debug、特定业务场景

### 如何重建聚合
仓储载入领域事件后按顺序传递给聚合，聚合根据事件计算内部状态演变。所有事件消费完即重建完成。无法重建说明建模遗漏。

### 事件数量多导致载入慢？
- 按聚合 id 载入关联事件，不是全部事件，数量有限可控
- 大量事件的聚合：采用快照机制，每隔一段事件存储聚合状态快照，下次从快照处开始重建

### 快照 ≠ 又持久化了聚合
- 快照数据是非结构化的（如 JSON 序列化），只用于恢复聚合，不承担查询责任
- 快照可异步非实时生成，继续享受高性能写优点
- 总体持久化难度仍低于不用事件溯源

### 事件溯源一般需要 CQRS
只要有领域事件以外的查询需求，都必须采用 CQRS。

### 适用场景
- 需要提高命令处理速度
- 需要更灵活自由的聚合内部设计
- 需要聚合时间机器能力

### 可以只对部分聚合采用
从聚合外部看，通过仓储载入/保存聚合，是否使用事件溯源没有差别。

### 难点
- 转变思维习惯
- 必须严格建模保证能重建聚合

## 二、LMAX 架构

### 定义
在 CQRS + 事件溯源基础上，将聚合常驻内存，避免反复重建聚合的开销，追求极致性能。

### 一致性保证
某个聚合实例常驻在一个服务器节点上，避免多服务器多实例数据不一致。

### 并发控制
- 不允许多线程访问同一个聚合对象
- 并发请求进入队列，由线程串行执行聚合
- 一个线程可执行多个聚合的代码
- 不允许阻塞线程

### 非阻塞实现
可采用 Reactor 模式，也可采用 Go/Java 虚拟线程。但采用 Reactor 不等于 LMAX，关键是聚合常驻内存。

### 内存管理
聚合数量有限可控，分区放到不同服务器。聚合增多则增加服务器节点。

### 故障恢复
不会丢失数据。采用事件溯源，领域事件已持久化，重启后重建聚合。

### 高可用
冗余应用服务器。一主一备，备份机监听主机领域事件同步更新内存聚合状态，主机不可用时切换。

### 不使用数据库事务
只持久化领域事件，无需数据库事务。一个命令只变更一个聚合，事件合并记录。记录失败则事件当未发生，重建聚合回退。

### 命令执行中发现违反业务规则的回滚
- **内存事务机制**：命令到达时建快照，暂存事件到临时队列，异常时恢复快照清除事件（复杂）
- **所有校验通过后才变更**：严格分析业务逻辑，确保万无一失后才变更聚合（简单但可能打破封装）

### 适用场景
- 需要高性能
- 容易把聚合分区（粒度更大，减少聚合间交互，最好一个命令只操作一个聚合）
- 聚合数量有限可控（不适合短时间快速产生大量聚合）
- 聚合总体活跃（冷聚合常驻内存是浪费）
