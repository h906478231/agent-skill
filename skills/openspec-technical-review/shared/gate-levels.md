# 技术评审门禁适用范围分级

**不是所有变更都要跑全部门禁维度。** 强行全跑会让开发者放弃整套流程。按变更性质分级：

| 等级 | 典型变更 | 门禁要求 | 人工签字 |
|------|---------|---------|---------|
| **L0 豁免** | 纯文案/注释/日志文案、配置值调整、格式化、依赖小版本升级、纯测试补充 | **跳过门禁**，直接 apply | 不需要；**不要创建 `review-summary.md`**（该文件存在即视为已启用门禁，hook 会要求签字行） |
| **L1 轻量** | 单表单接口 CRUD、新增非核心字段、既有能力的小范围扩展 | 只跑 **database + security** | 需要 |
| **L2 标准** | 新增业务流程、跨模块调用、引入缓存、批量操作 | 跑 **architecture + database + security + performance** | 需要 |
| **L3 全量** | 涉及 MQ/异步、并发消费、分布式一致性、状态机、大数据量、新建核心表、对外开放接口 | **五维度全跑** | 需要，且建议第二人复核 |


> **L0 的落点（勿与门禁产物混用）**：L0 豁免**不要创建 `review-summary.md`** —— 该文件的存在本身就是「本变更已启用技术评审门禁」的开关（见 `apply-gate-check.md`「何时执行」与 `hooks/check-review-approval.sh`），创建了就必须有非空签字行，与「跳过门禁」的初衷矛盾。豁免理由写在变更目录的 `overview.md` 开头一行，注明豁免人与日期，供事后追溯。
## 判定口诀

**拿不准就升一级。** 漏评审的代价远高于多跑一个维度。

## 触发升级的信号

命中任一，至少 L3：

- 出现「异步」「MQ」「并发消费」「重试」「幂等」
- 出现「批量」且量级 ≥ 1 万
- 新建表，或对既有表加唯一索引/改字段类型
- 接口对外网开放，或处理用户上传内容
- 涉及租户隔离、权限判定、敏感数据

## 分级决策责任

分级结论必须写进变更目录的 `overview.md` 开头（等级 + 判定人 + 依据）—— **分级本身也是一个需要负责的决策**。若本变更走了门禁（即存在 `review-summary.md`），该结论同时写入 `review-summary.md` 的分级结论项（见 `../SKILL.md` Step 2 第 14 项）。

## 门禁耗时与成本预期

开发者最关心「跑一次要多久」。实测量级（供参考，随方案文档长度与模型浮动）：

| 模式 | 并行 Agent 数 | 墙钟耗时 | 相对 token 成本 |
|------|-------------|---------|----------------|
| L1（2 维度） | 2 + 1 汇总 | 约 2–4 分钟 | 低 |
| L2（4 维度） | 4 + 1 汇总 | 约 3–6 分钟 | 中 |
| L3（5 维度全量） | 5 + 1 汇总 | 约 4–8 分钟 | 高 |
| 增量重走（1 维度） | 1 + 1 汇总 | 约 1–3 分钟 | 很低 |

各子 agent 并行，墙钟接近「最慢的那个」而非累加。**迭代时优先用增量重走**，别每次都全量。
