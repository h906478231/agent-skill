# DDD 总览

> 来源: https://ddd-fans.github.io/ddd-guideline/

## DDD 是什么

DDD (Domain-Driven Design) 领域驱动设计，由 Eric Evans 于 2002 年提出。核心方法论：领域问题驱动模型设计，模型驱动软件设计。从领域问题出发设计领域模型，再设计软件实现领域模型。

## 核心判断标准

一个项目满足以下两个条件即采用了 DDD：
- 遵循了 DDD 核心方法论
- 有单独的模块来实现领域模型

## DDD 优势

- 为新手提供普遍有效的可快速上手的软件设计方法
- 让程序员更关注领域问题，更容易开发出带来用户价值的软件
- 要求有专门实现领域模型的程序模块作为核心，提升可理解性和可维护性
- 推荐的实践方式（领域事件、六边形架构、CQRS 等）帮助构建易扩展、高性能的系统

## 关键概念

- **领域**：软件系统要解决的问题的范围，用户真正关注的问题
- **领域模型**：针对领域问题设计的模型，是领域问题的解决方案，忽略技术实现细节

## 错误的 DDD 实践

- 不建模，只照抄"DDD 规范"代码形式 → 成本上升却无收益
- 空谈建模不用代码实现 → 建模和实现脱节
- 项目病入膏肓才想用 DDD 重构 → 多半搞不成

## 何时使用 DDD

建议只要是需要长期维护的项目，不管是否简单，都从一开始就采用 DDD：
- 实施 DDD 的成本已不比不采用高
- 简单项目在长期维护中很可能变复杂
- 开发人员容易低估业务复杂性

## 四层架构（反模式）

四层架构（UI层、应用层、领域层、基础设施层）来自 Eric Evans 原书，但存在严重缺陷：
- 领域层依赖基础设施层 → 聚合中直接访问数据库、拼接 SQL
- 领域模型不容易被测试
- "应用层"概念模糊 → 业务逻辑泄露到应用层

**结论：永远使用端口适配器架构，永远不要使用四层架构。**

## DDD 发展历史关键节点

| 时间 | 技术 | 贡献者 | 对 DDD 的价值 |
|------|------|--------|--------------|
| 2005 | 六边形架构 | Alistair Cockburn | 分离核心业务逻辑与外部系统 |
| 2005 | 事件溯源 | Greg Young | 记录状态变化事件序列还原系统状态 |
| 2010 | CQRS | Greg Young | 读写分离，优化复杂系统性能和可维护性 |
| 2010 | LMAX | Martin Thompson | 事件驱动高吞吐低延迟 |
| 2013 | 事件风暴 | Alberto Brandolini | 协作式工作坊快速发现领域事件、命令和聚合 |
| 2014 | 微服务 | Martin Fowler | 与限界上下文结合拆分独立服务 |
