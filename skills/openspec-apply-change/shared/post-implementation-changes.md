# 实现后修改登记规则（唯一事实源）

> 实现后修改的定义、登记表格式、三档判定、各档最少动作与示例。
> 本文件**住在它的内容领域**（登记表写在 `tasks.md`，规则随 apply skill 走）。`skills/openspec-apply-change/SKILL.md` 用 skill 内相对路径 `shared/post-implementation-changes.md` 引用本文件；其他 skill 跨 skill 引用 `../openspec-apply-change/shared/post-implementation-changes.md`；Glob 兜底搜 `**/openspec-apply-change/shared/post-implementation-changes.md`。
> 确定性校验脚本（下文 `<GATE>`）= `../openspec-technical-review/scripts/implementation-gate.mjs`（相对本 skill 目录解析；解析不到时 Glob 搜 `**/openspec-technical-review/scripts/implementation-gate.mjs`），运行需 Node.js ≥ 16。

## 为什么需要

切片全部勾选之后，代码还会被修改：评审修复、补日志、静态分析重构、补注释。以前这些修改只有「新增任务」一种登记方式，修改一行注释也要重跑全部验证与两轴评审。档位让流程成本随修改性质变化：只有注释差异时由脚本确认，不开新一轮；行为修改仍走完整流程。

## 定义

**实现后修改**：不在 `/opsx:apply` 某个未勾选任务内进行的代码修改。典型情况：

- 切片的任务全部勾选之后的修改；
- 一轮评审之后的修复或重构；
- 门禁外提交：不经过 OpenSpec 流程的提交，如静态分析修复、补排查日志。

在未勾选任务内进行的修改按 apply 规则处理（证据先于勾选），不登记。

## 何时登记

- 在下一次 `/opsx:quality` 或 `/opsx:verify` 之前登记。
- 每次修改新增一行，不修改已有行。同一文件再次修改时也新增一行，写新的登记指纹。
- `classify` 用登记指纹核对登记之后的修改。`other` 中的文件算登记：至少一行合法行列出它，并且「该行登记指纹 → `--to`」之间它只有注释差异或没有差异。合法行是档位与登记指纹都合法的行。只有档位不是 `非行为` 的合法行能证明登记。
- `classify` 的 `issues` 分两类：
  - 行级问题：档位不是 `非行为`、`等价`、`行为`，或登记指纹为空、格式不合法的行，整行不算登记。只写登记编号与原因，不写文件。
  - 文件级问题：只写给列入 `unregistered` 的文件。列出它的合法行登记之后又有非注释修改、登记指纹的 tree 对象不存在或档位为 `非行为` 时，写出文件、登记编号与原因。另一行已证明该文件登记时，这些行不报出。没有合法行列出的文件只列入 `unregistered`，不写入 `issues`。
- 登记不改变任务进度：登记表不含勾选项，`tasks.md` 的已完成数与总数不变。

## 登记表格式

写在 `tasks.md` 全部切片之后，标题固定为 `## 实现后修改登记`，不含勾选项：

```markdown
## 实现后修改登记

| 编号 | 文件 | 提交 | 登记指纹 | 档位 | 判定依据 | 验证 | 判定人 | 日期 |
|---|---|---|---|---|---|---|---|---|
| M1 | src/a/Foo.java、src/a/Bar.java | abc1234 | git-tree:<sha> | 非行为 | classify：commentOnly 2 个 | 编译通过 | /opsx:apply（agent） | 2026-10-20 |
| M2 | src/a/Job.java | def5678 | git-tree:<sha> | 等价 | 新增 3 条 INFO 日志，不改分支与写入 | 模块完整测试，本次引入的失败：0 | 用户（确认档位） | 2026-10-20 |
```

| 列 | 要求 |
|----|------|
| `编号` | `M1`、`M2` 依次递增，不复用 |
| `文件` | 本次修改的**全部**文件（相对仓库根），用顿号或逗号分隔；漏列的文件在 `classify` 中列入 `unregistered` |
| `提交` | 提交的短 SHA；尚未提交写 `未提交` |
| `登记指纹` | 本次修改与验证完成后运行 `node <GATE> fingerprint <changeRoot>` 的输出（`git-tree:<sha>`）。规划目录不计入指纹，写登记表不会改变它 |
| `档位` | `非行为` / `等价` / `行为`，判定见下文「三档判定」 |
| `判定依据` | `非行为`：`classify` 的结果；`等价`：不改哪些行为；`行为`：新增的任务编号 |
| `验证` | **实际运行**的命令与结果摘要，范围见下文「各档最少动作」；未运行不能写通过 |
| `判定人` | 做出判定的 agent 或用户；`等价` 写 `用户（确认档位）` |
| `日期` | 登记日期 |

## 三档判定

| 档位 | 定义 | 谁可以登记 |
|------|------|-----------|
| `非行为` | `classify` 把本次修改的全部文件列入 `commentOnly` | agent 直接登记 |
| `等价` | 不改输入、输出、数据写入、外部调用与异常路径。例如：新增日志语句、提取方法、静态分析的抑制注解 | agent 提议，**用户确认后**才写入该行 |
| `行为` | 其他全部情况 | agent 直接登记，同时新增任务 |

- **拿不准时取较高档位**。例如：无法确定一次重构是否保持异常路径不变，登记为 `行为`。
- `非行为` 只看脚本结果，不看 agent 判断。`classify` 不支持的文件类型（如 `.mjs`、Markdown）只改注释时，脚本把它列入 `other`，不能登记为 `非行为`。
- 只有档位不是 `非行为` 的合法行能证明 `other` 中的文件已登记：`非行为` 只对应 `commentOnly` 中的文件。`等价` 行登记之后又有未登记的行为修改，再改一行注释并登记为 `非行为` 时，该文件仍列入 `unregistered`，`issues` 写出两个登记编号。否则行为修改可以借旧的 `等价` 行沿用 Spec Fidelity，不经过忠实度评审。

登记步骤：

1. 运行 `node <GATE> classify <changeRoot> --from <修改前的指纹>`。修改前的指纹取最近一个被认可的指纹：verify 已通过时取 `verification.md` 的 `Fingerprint`；评审过时取上一轮评审基线的 `Fingerprint`；否则取最近记录的切片证据的 `Fingerprint`。
2. `commentOnly` 中的文件登记一行 `非行为`。
3. `other` 中的文件由 agent 判定 `等价` 或 `行为`。判定为 `等价` 时，先向用户说明判定依据并请用户确认。
4. 按「各档最少动作」完成验证，把实际结果写进 `验证` 列。
5. 运行 `node <GATE> fingerprint <changeRoot>`，把输出写进 `登记指纹` 列。验证之后又改了代码时，重新验证并重新取指纹。
6. 再次运行 `classify`：只在新增并已勾选的任务内修改的文件不登记（见「定义」），它们在 `unregistered` 与 `issues` 中的条目不处理；勾选之后又有修改时照常登记。判断方法：用 `git diff -U0 <修改前指纹的 sha> <当前指纹的 sha> -- <文件>` 列出该文件的修改（指纹的 sha 是 `git-tree:` 后面的部分；当前指纹用 `node <GATE> fingerprint <changeRoot>` 取，修改前的指纹见第 1 步）。`-U0` 不输出上下文行，每个 `@@` 区块算一处。不加 `-U0` 时，两处修改之间不超过 6 行未修改的行，git 就把它们合成一个区块。逐处核对：每处都能对应到某个新增并已勾选的任务时不登记；区块中只有部分行能对应到任务时，算对应不上；对应不上或拿不准时照常登记。除不登记的文件之外，`unregistered` 与 `issues` 都为空时登记完成。`classify` 不读取任务内容，无法自动排除这些文件。命令输出与退出码见 `slice-evidence.md`「命令级校验」。

## 各档最少动作

| 档位 | 验证 | 切片证据 | 双轴评审 | overview |
|------|------|---------|---------|----------|
| `非行为` | 编译或等价的静态检查 | 按注释差异规则保持新鲜（`slice-evidence.md`「新鲜度判定」） | 不开新一轮 | 不刷新 |
| `等价` | 受影响模块的完整测试套件 + 编译 | 刷新该套件覆盖的切片；其他切片按现有豁免规则 | 只跑 Standards，Spec Fidelity 沿用 | 不刷新 |
| `行为` | 现有 apply 规则：新增任务、切片证据、完整测试套件 | 刷新 | 两轴增量 | 本规则不要求刷新 |

- `非行为`、`等价` 只要求上表的动作，不要求新增任务，也不要求刷新 overview。
- `行为` 修改照常在 `tasks.md` 新增任务，按 apply 规则先写证据再勾选；登记行的 `判定依据` 写该任务编号。
- `行为` 修改改变了 `design.md` 中的决策时，先走 `/opsx:update`，再改代码。
- 只有注释差异的修改不需要人工登记豁免：证据新鲜度由脚本按注释差异判定，不读登记表。等价修改仍要用测试刷新证据。

## 示例

**例 1：切片勾选后修正两处 Javadoc**

- `classify --from <上一轮评审基线指纹>`：`commentOnly` 为 `src/a/Foo.java`、`src/a/Bar.java`，`other` 为空。
- 登记 `M1 | src/a/Foo.java、src/a/Bar.java | abc1234 | <fingerprint 输出> | 非行为 | classify：commentOnly 2 个 | 编译通过 | /opsx:apply（agent） | <日期>`。
- 不开新一轮评审，任务进度不变。

**例 2：评审后补 3 条 INFO 日志**

- `classify`：`other` 为 `src/a/Job.java`。
- agent 提议 `等价`（不改分支、写入与异常路径），用户确认后登记 `M2 | src/a/Job.java | def5678 | <fingerprint 输出> | 等价 | 新增 3 条 INFO 日志，不改分支与写入 | 模块完整测试，本次引入的失败：0 | 用户（确认档位） | <日期>`。
- 刷新该模块测试覆盖的切片证据；下一轮只跑 Standards。

**例 3：删除一处方法调用**

- `classify`：`other` 为 `src/a/Sync.java`。删除调用改变了外部调用，档位为 `行为`。
- 在对应切片新增任务 `3.4`，按 apply 规则写证据并勾选；登记 `M3 | src/a/Sync.java | 未提交 | <fingerprint 输出> | 行为 | 删除重复的同步调用，见任务 3.4 | 完整测试套件，本次引入的失败：0 | /opsx:apply（agent） | <日期>`。
- 两轴在增量基线上重跑。

## 产物的 git 边界

登记表写在变更目录的 `tasks.md` 中，随变更归档。登记时不执行 `git add` 或 `git commit`。项目 `.gitignore` 忽略 `openspec/` 时，不得用 `git add -f` 加入产物。是否提交由用户决定。
