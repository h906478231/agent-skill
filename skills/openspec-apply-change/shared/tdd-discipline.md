# apply 阶段 TDD 实施纪律（唯一事实源）

> 编码实施期间的测试与反馈纪律。`skills/openspec-apply-change/SKILL.md` 用 skill 内相对路径 `shared/tdd-discipline.md` 引用本文件，`claude/commands/opsx/apply.md` 以 skill 名定位引用，不各写一份。
> 本文件**住在它的内容领域**（实施纪律属于 apply，规则随 skill 走、装了 apply 就一定有）。其他 skill 跨 skill 引用 `../openspec-apply-change/shared/tdd-discipline.md`；Glob 兜底搜 `**/openspec-apply-change/shared/tdd-discipline.md`。

## 何时生效

apply 进入代码实现即生效，**所有等级默认执行**（含 L0——纯测试补充类变更本身就是测试行为）。

前置文件要求：design.md 有「测试 Seam 决策」区块（L2/L3 变更必有）时，严格按区块执行；无该区块（L0/L1 或存量变更）时，动笔前先与用户口头确认测试边界，确认结果回记到 tasks.md 对应切片的 `Seam:` 行。

## 核心纪律

1. **Seam-first**：只在 design.md「测试 Seam 决策」区块（或口头确认后回记的 `Seam:` 行）声明的公共边界写测试。未声明的边界不写测试，先问。
2. **Red before green**：先写失败测试，再写刚好让它通过的实现。不预写「未来测试会需要」的能力，不 anticipating。
3. **一次一个切片**：按 tasks.md 的切片顺序实施（frontier 上的切片可并行）。切片内一次一个行为：一个失败测试 → 最小实现 → 下一个行为。
4. **只测外部行为**：通过公开接口观察行为。不测私有方法，不 mock 内部协作者，不通过查库等侧信道断言（那是实现的细节，不是行为）。

## 三个反模式（发现即停）

| 反模式 | 特征 | 为什么致命 |
|--------|------|-----------|
| **实现耦合测试** | mock 内部协作对象、测私有方法、靠查数据库断言接口行为 | 重构不改变行为时测试也会碎，测试从保险变成枷锁 |
| **同义反复测试** | 断言用实现自己的方式重算期望值（如 `expect(add(a,b)).toBe(a+b)`） | 永远通过，等于没测。期望值必须来自独立事实源：已知样例、规格、手算结果 |
| **水平切片测试** | 先写完一个切片的所有测试再实现 | 测的是想象中的行为。一个测试 → 一个实现交替推进 |

## 反馈节奏

- 每完成一个任务项（checkbox 勾选前）：跑该任务相关的**单个测试文件** + 类型检查
- 全部任务完成：跑一次**完整测试套件**
- 测试失败且原因不明：停下来诊断，禁止用「删测试 / 放宽断言 / skip」让绿

## 重构的归属

**重构不属于 red-green 循环。** 实施期间发现的可重构点，记入 tasks.md 新任务项或留给 `/opsx:quality`（Phase 5.5 代码质量评审），不在让测试变绿的路径上顺手重构——那会把「行为验证」和「结构改动」混在一个不可回退的动作里。

## 禁止事项

- 禁止跳过失败的测试直接做下一个任务
- 禁止为了让测试通过而注释、删除或放宽既有断言（发现的坏测试记 finding，交 `/opsx:quality` 评审处置）
- 禁止在未声明的 seam 上堆测试
- 禁止把「重构让代码更好」作为偏离本纪律的理由——重构走 quality 评审通道
