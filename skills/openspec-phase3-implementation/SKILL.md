# Phase 3: 实施落地与任务拆解

> 当 `openspec-architect` 决定进入 Phase 3 时，加载本 skill 执行任务拆解。本 skill 只负责任务分解、验收标准定义和逻辑产物输出，不负责 OpenSpec API 调用和文件落盘。

## 执行前提

- 输入应为 Phase 1 + Phase 2 的产物包（proposal.md + design.md 内容）
- Phase 2 必须已通过门禁（至少 2 个候选方案、交叉验证矩阵完整、推荐方案已确定）
- 本 skill 不直接调用 OpenSpec API，只输出逻辑产物包

## 核心任务

Phase 3 的核心任务是**将设计转化为可执行的任务清单**。每个任务必须：
- 有明确的验收标准
- 可以在 1-3 天内完成
- 依赖关系清晰
- 风险可控

## 执行规则

### 1. 任务拆解原则

**拆解粒度**：
- 单个任务：1-3 天完成
- 过大（> 5 天）：继续拆解
- 过小（< 0.5 天）：合并相关任务

**拆解维度**：

**维度 1：按架构分层**
- 数据层任务（数据模型、数据库表、索引）
- 领域层任务（业务逻辑、领域对象）
- 应用层任务（用例编排、接口暴露）
- 基础设施层任务（Repository、外部调用）
- 接口层任务（API、MQ 消费者）

**维度 2：按实施阶段**
- 基础设施准备（数据库、MQ、缓存）
- 核心功能开发（主流程）
- 边界场景处理（异常、并发、降级）
- 测试验证（单元测试、集成测试）
- 监控告警（日志、指标、告警规则）
- 文档完善（API 文档、运维文档）

**维度 3：按价值优先级**
- P0（核心功能）：必须完成，阻塞上线
- P1（重要功能）：应该完成，影响体验
- P2（次要功能）：可以延后，不影响主流程
- P3（优化项）：未来迭代

**拆解策略**：
1. 先按架构分层，识别每一层需要做什么
2. 再按实施阶段，确定先后顺序
3. 最后按价值优先级，标注重要性

### 2. 任务清单生成

**每个任务必须包含**：

**基本信息**：
- 任务 ID（如：TASK-001）
- 任务名称（动词开头，如"实现订单创建 API"）
- 任务描述（详细说明做什么）
- 优先级（P0 / P1 / P2 / P3）
- 预估工作量（人日）

**验收标准**（必需）：
- 功能验收（如：API 返回正确的订单数据）
- 性能验收（如：响应时间 < 100ms）
- 质量验收（如：单元测试覆盖率 > 80%）
- 文档验收（如：API 文档已更新）

**依赖关系**：
- 前置任务（必须先完成哪些任务）
- 阻塞任务（本任务完成后才能开始哪些任务）
- 并行任务（可以同时进行的任务）

**风险识别**：
- 技术风险（如：新技术不熟悉）
- 依赖风险（如：依赖外部团队交付）
- 时间风险（如：可能延期）
- 质量风险（如：边界场景复杂）

**任务格式示例**：

```markdown
### TASK-001: 设计并创建订单表

**描述**：
设计订单表结构，包含订单号、用户 ID、商品列表、总金额、状态、创建时间、更新时间等字段。
创建数据库表，添加必要的索引。

**优先级**：P0（核心功能）

**预估工作量**：0.5 人日

**验收标准**：
- [ ] 订单表已创建，包含所有必需字段
- [ ] 已添加索引：user_id, status, created_at
- [ ] 已执行 DDL 并验证表结构
- [ ] 已更新数据库设计文档

**依赖关系**：
- 前置任务：无
- 阻塞任务：TASK-002（实现订单 Repository）

**风险识别**：
- 无明显风险
```

### 3. 验收标准定义（必需）

**验收标准必须满足 SMART 原则**：
- **S**pecific（具体）：明确要验收什么
- **M**easurable（可衡量）：可以用测试、指标验证
- **A**chievable（可达成）：不是理想化目标
- **R**elevant（相关）：与设计目标一致
- **T**ime-bound（有时限）：在任务时间内完成

**常见验收标准类型**：

**功能验收**：
- [ ] API 返回正确的数据格式
- [ ] 业务逻辑符合需求（如：订单总金额 = 商品金额之和）
- [ ] 异常场景处理正确（如：库存不足时返回错误）

**性能验收**：
- [ ] 响应时间 < 100ms（P95）
- [ ] QPS > 1000
- [ ] 数据库查询 < 50ms

**质量验收**：
- [ ] 单元测试覆盖率 > 80%
- [ ] 集成测试通过
- [ ] 代码审查通过

**文档验收**：
- [ ] API 文档已更新
- [ ] 运维文档已更新
- [ ] README 已更新

**监控验收**：
- [ ] 已添加关键指标监控（如：订单创建成功率）
- [ ] 已添加告警规则（如：错误率 > 1% 告警）
- [ ] 已验证告警生效

### 4. 依赖关系分析

**依赖类型**：

**顺序依赖**（强依赖）：
- A 必须在 B 之前完成
- 示例：数据库表创建 → Repository 实现 → Service 实现

**并行依赖**（弱依赖）：
- A 和 B 可以同时进行
- 示例：订单模块开发 || 库存模块开发

**可选依赖**（建议依赖）：
- A 完成后 B 会更容易，但不是必需
- 示例：监控告警完成后，更容易排查问题

**依赖关系可视化**：

```
TASK-001 (创建订单表)
    ↓
TASK-002 (实现 OrderRepository)
    ↓
TASK-003 (实现 OrderService) ← TASK-004 (实现库存检查) (并行)
    ↓
TASK-005 (实现订单创建 API)
    ↓
TASK-006 (集成测试)
```

### 5. 风险识别与缓解

**常见风险类型**：

**技术风险**：
- 风险：团队不熟悉 RabbitMQ
- 影响：开发进度延期
- 缓解：提前技术调研 + 技术分享

**依赖风险**：
- 风险：依赖外部团队的用户服务 API，可能延期交付
- 影响：无法集成测试
- 缓解：提前 mock API + 并行开发

**时间风险**：
- 风险：任务 TASK-003 可能延期（复杂度高）
- 影响：整体进度延期
- 缓解：提前开始 + 增加人手

**质量风险**：
- 风险：并发场景复杂，可能有 bug
- 影响：生产环境数据不一致
- 缓解：增加并发集成测试 + 灰度发布

**输出格式**：

```markdown
## 实施风险

| 风险 ID | 风险描述 | 风险等级 | 影响 | 缓解措施 | 负责人 |
|---------|---------|---------|------|---------|--------|
| RISK-001 | 团队不熟悉 RabbitMQ | 中 | 开发进度延期 1-2 天 | 提前技术调研 + 技术分享 | 张三 |
| RISK-002 | 依赖外部用户服务 API | 高 | 无法集成测试 | 提前 mock API + 并行开发 | 李四 |
```

### 6. 测试策略

**测试层次**：

**单元测试**：
- 覆盖率目标：> 80%
- 测试内容：业务逻辑、边界场景、异常处理
- 工具：JUnit / pytest / Jest

**集成测试**：
- 测试内容：API 集成、数据库集成、MQ 集成
- 工具：Postman / RestAssured / Testcontainers

**端到端测试**：
- 测试内容：完整业务流程
- 工具：Selenium / Cypress / Playwright

**性能测试**：
- 测试内容：响应时间、QPS、并发
- 工具：JMeter / Gatling / k6

**输出格式**：

```markdown
## 测试策略

### 单元测试
- 目标覆盖率：> 80%
- 重点测试：
  - OrderService.createOrder() 各种场景
  - 库存不足时的错误处理
  - 并发创建订单的幂等性

### 集成测试
- 数据库集成：使用 Testcontainers 启动 MySQL
- MQ 集成：使用 embedded RabbitMQ
- 外部 API 集成：使用 WireMock

### 性能测试
- 场景 1：单用户创建订单，响应时间 < 100ms
- 场景 2：1000 并发创建订单，QPS > 1000
```

### 7. 里程碑与交付物

**里程碑定义**：

**里程碑 1：基础设施就绪**
- 时间：第 1-2 天
- 交付物：数据库表、MQ 队列、缓存配置
- 验收：基础设施可用，通过连接测试

**里程碑 2：核心功能完成**
- 时间：第 3-5 天
- 交付物：订单创建 API、库存检查、订单查询
- 验收：主流程可跑通，单元测试通过

**里程碑 3：边界场景处理完成**
- 时间：第 6-7 天
- 交付物：异常处理、并发控制、降级方案
- 验收：边界场景测试通过

**里程碑 4：上线就绪**
- 时间：第 8-10 天
- 交付物：监控告警、文档、灰度发布
- 验收：生产环境验证通过

## Phase 3 检查点（自检）

在输出产物包前，执行以下检查：

- [ ] 任务拆解覆盖所有设计要点（数据层、业务层、接口层、测试、监控）
- [ ] 每个任务有明确的验收标准（功能 + 性能 + 质量）
- [ ] 验收标准满足 SMART 原则（具体、可衡量、可达成、相关、有时限）
- [ ] 任务依赖关系清晰（顺序 / 并行 / 可选）
- [ ] 风险识别完整（技术 / 依赖 / 时间 / 质量）
- [ ] 测试策略完整（单元 / 集成 / 性能）
- [ ] 里程碑与交付物明确

**如果检查点未全部通过**：
- 不输出产物包
- 说明缺少什么
- 给出补充建议

## 注意事项

### 任务粒度要合适

- 过大（> 5 天）：难以验收，风险高
- 过小（< 0.5 天）：管理成本高
- 推荐：1-3 天

### 验收标准必须可验证

- ✓ "响应时间 < 100ms"（可测量）
- ✗ "性能很好"（不可测量）
- ✓ "单元测试覆盖率 > 80%"（可测量）
- ✗ "测试充分"（不可测量）

### 依赖关系要准确

- 不要遗漏关键依赖
- 不要创建循环依赖
- 明确哪些任务可以并行

### 风险识别要全面

- 技术风险：新技术、复杂场景
- 依赖风险：外部团队、第三方服务
- 时间风险：工作量评估、假期
- 质量风险：边界场景、并发

## 总结

Phase 3 的核心价值是**将设计转化为可执行计划**。通过任务拆解和验收标准定义，确保实施有章可循。

**核心原则**：任务明确、验收可测、依赖清晰、风险可控。
