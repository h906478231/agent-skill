# DDD 聚合与实体

> 来源: https://ddd-fans.github.io/ddd-guideline/

## 一、聚合建模篇

### 定义
聚合是 DDD 术语，指一些对象在一起完成一组高耦合的功能，总是被一起载入内存一起持久化。不是简单的对象集合。聚合是面向对象领域模型中与技术实现关系最紧密的对象，建模到聚合才能被代码实现。

### 聚合由功能定义
聚合存在的意义是实现高耦合高内聚的功能。有什么样的功能就有什么样的聚合。聚合内持有的数据完全服务于功能，功能不需要的数据不必硬塞。

### 聚合根
- 聚合和外部交互的入口，外部只能通过聚合根访问聚合功能
- 聚合必须有聚合根，聚合和聚合根一一映射
- 聚合 ID = 聚合根 ID

### 高内聚高耦合
功能间存在强依赖关系（函数互调、共享数据），对外低依赖。如果聚合内存在无关功能，考虑拆分。

### 聚合 ≠ 数据库表
先设计聚合再设计表。多个聚合可共用一张表，一个聚合可存多张表。

### 聚合内数据强一致
每次操作聚合，内部状态必然一致，不存在修改一半的情况。一般串行使用聚合功能。

### 聚合的单写者语义
同一时刻同一聚合实例只应有一个成功写入者。只要聚合采用“先读到内存，再修改，再保存”的方式，就必须假设存在更新丢失风险。并发读取可以存在，并发写入必须被串行化或显式冲突检测。

### 业务状态机约束 ≠ 并发控制
- "锁定中不可登录""已提交后不可修改""审批通过后不可撤回"等业务状态机约束，是聚合状态的一部分，写为聚合字段、不变量或命令前置条件，归 `domain-model.md`
- 这些业务状态机约束本身不替代技术并发控制；两个线程同时读到"未锁定"快照仍可能发生覆盖写
- 防止覆盖写的技术并发语义（必须串行化 / 允许冲突失败重试 / 并发令牌方案 / 分布式锁选型 / 冲突返回语义）由 `ddd-application-orchestration-modeling` 输出，写入 `application-model.md` `## 6. 聚合并发约束`，不写入 `domain-model.md`
- 不要在 `domain-model.md` 中保留"业务锁规则"这种与并发控制混写的字段

### 高争用聚合的建模信号
出现以下信号时，要回到建模阶段审视边界，而不是只在基础设施层盲目加锁：
- 同一聚合经常被多个命令同时修改
- 聚合中只有少数字段高频变化，却拖着大量低频状态一起整存整取
- 为了避免冲突不得不长时间持锁

可选方向：
- 缩小聚合边界
- 把高频且生命周期独立的对象拆为独立聚合
- 把查询模型与写模型分离

### 状态与状态机
- 不是所有聚合都必须有 status 字段
- 很多聚合从状态变化角度看确实是状态机，但状态机是表象不是本质
- 简单状态转化不必画状态图

### 聚合间引用规则
- 不可持有另一个聚合的引用（避免边界模糊、庞大对象网络）
- 可以持有另一个聚合的 id
- 可以依赖另一个聚合的功能（通过方法调用协作）

### 全局唯一聚合
有状态的全局唯一功能可设计为只有一个实例的聚合，无需显式指定 id。

### 聚合不能继承聚合
继承意味着"是"同一个聚合。只可能存在一个聚合接口有多种实现。

## 二、实体建模篇

### 定义
领域实体是存活时间长、跨越多次命令、持有状态数据的对象。必须有 id，类型和 id 相同则为同一对象。

### 实体 ≠ 数据库实体
两者不是同一概念。领域实体不一定存储到关系型数据库，不一定只存一张表。

### 实体与聚合的关系
- 聚合根都是实体，聚合内部可有多个实体
- 实体脱离聚合无意义
- 聚合比实体更重要

### 如何建模实体
不必特意找实体。聚焦功能和聚合，聚合根自然是实体，聚合内部复杂功能可再分拆出内部实体。

### 实体 id
可借用业务 id，找不到时设计人造 id。满足唯一不变即可。

### 实体内状态数据
由功能定义，服务于实体要实现的业务功能。

### 实体不是贫血模型
实体应封装功能和数据，不应设计成纯数据存取对象。

### 实体间引用
聚合内实体可像普通对象那样引用。不应持有别的聚合的引用，但可持有别的聚合的 id。

## 三、聚合实现篇

### 聚合 ID 生成
不推荐由数据库在保存时生成。建议定义接口在领域模块外实现生成算法：
- 数据库序列（推荐大部分场景）：易实现、全局有序、空间小
- Redis 计数：更高性能，需持久化机制
- 雪花算法：极高性能，需管理 worker node id
- UUIDv4：简单但占空间大、无序
- UUIDv7（数据库不支持序列时推荐）：简单、基本有序

### 为什么给聚合定义接口
- 显式定义聚合功能
- 隐藏内部实现
- 保持接口不变更容易重构

### 聚合可以当 ORM 映射类吗
侵入不大时可以。但是先设计聚合再恰好映射，不是先设计表再当聚合。

### 技术锁不进入领域语言
悲观锁、乐观锁、分布式锁是持久化 / 基础设施实现手段，不应作为业务概念出现在命令和事件中。`domain-model.md` 中聚合状态数据可以列出 `version` 字段（只说明其用于乐观并发控制），但**不**在 `domain-model.md` 中决定并发语义。

并发语义建模归属：

- `domain-model.md`：在采用乐观并发的聚合状态数据中列出 `version` 字段；业务状态机约束写为聚合不变量
- `application-model.md`：`## 6. 聚合并发约束` 输出每个可写聚合的并发策略、并发令牌、CAS 行为、冲突返回语义，由 `ddd-application-orchestration-modeling` 维护
- `ddd-persistence`：负责实现层并发控制的技术约束，消费 `application-model.md` 输出，不再决定并发策略

补充约束：

- 不是所有聚合都必须声明 `version` 业务字段
- 只有该聚合选择乐观并发控制时，其状态数据才必须具备 `version` 或等价并发令牌
- 聚合是否选择乐观并发由 `application-model.md ## 6. 聚合并发约束` 决定，不在 `domain-model.md` 决定

### 聚合函数不只处理命令
聚合是普通对象，可提供非命令处理的函数。

### 领域事件暂存
不必暂存到聚合里，也可暂存到统一队列。

### 聚合只操作自己的字段
任何对象都应只操作自己的字段，不能看到或操作别的对象的字段。

### 聚合可以调用别的聚合方法
当然可以，对象间通过方法调用协作。

### 聚合内功能复杂时
定义新对象承担部分功能，聚合根委托给它（普通 OO 设计）。

### 领域模块外使用聚合
可使用只读功能（无副作用）。业务变更必须通过命令。

### 查询冗余字段
使用 CQRS 时由读模型实现，聚合不需要。不使用 CQRS 时聚合需加入冗余字段。建议使用 CQRS。
