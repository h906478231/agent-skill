# Concurrency Analysis

## 核心原则

先证明业务不变量，再选择并发手段。不要从“加锁”开始，而要先说明：

- 哪些状态、记录、消息、缓存或外部副作用会被多个入口同时触碰。
- 哪些顺序、唯一性、可见性、频控、终态或最多一次/至少一次语义必须成立。
- 哪个事实源可信，哪些只是派生索引、暂态消息或性能优化。
- 正常路径失败后，系统如何恢复到可继续处理的状态。

并发分析的目标不是消灭所有交错，而是把允许的交错、禁止的交错和可补偿的交错讲清楚。

## 分析流程

### 1. 提炼业务不变量

先把需求翻译成必须一直成立的规则。优先使用业务语言，不要急着落到技术组件。

常见不变量：

- 唯一性：同一业务对象只能创建一次、同一任务在同一队列中只能有一个有效位置。
- 顺序性：同一主体下必须按某个排序键处理，或者恢复后必须排到队尾。
- 单飞性：同一主体同一时刻最多一个在途执行。
- 频控性：两次外部触达之间必须有间隔。
- 可见性：删除、暂停、冻结、失效后的对象不得再被普通链路选中。
- 终态性：终态记录不得被重新执行或被非预期覆盖。
- 幂等性：重复请求、重复消息、重复回调不能制造重复副作用。
- 可恢复性：缓存丢失、消息丢失、进程宕机、事务回滚后不能永久饥饿或锁死。

把不变量写成检查句式：

```text
无论发生什么并发交错，都必须保证：<主体> 在 <条件> 下 <约束>。
```

### 2. 列出共享事实与入口

建立两张清单。

共享事实清单：

- DB 表、状态字段、版本号、唯一键、排序键、游标、运行态字段。
- Redis key、锁、租约、ZSET、counter、缓存、限流状态。
- MQ 消息、延迟消息、重试消息、旧 payload、新 payload。
- 定时任务扫描结果、补偿任务候选集。
- 外部接口副作用、回调、第三方幂等键。
- 前端或 API 可见的聚合结果、缓存结果。

入口清单：

- 创建、编辑、删除、暂停、恢复、取消、重试。
- Scanner、Consumer、Worker、Job、补偿任务、回调处理。
- 迁移脚本、停机初始化、灰度双写、回滚路径。
- 人工修复、后台操作、管理端批处理。

### 3. 构造冲突矩阵

用“入口 × 共享事实”找冲突，而不是凭感觉找风险。

```text
                 DB状态   Redis索引   MQ消息   外部接口   聚合缓存
创建任务            W        W         -        -         W
扫描投递            R        W         W        -         -
消费执行            W        W         R        W         W
删除任务            W        -         -        -         W
超时恢复            W        W         -        -         W
```

重点追问每一个交叉点：

- 两个入口同时写同一事实时，谁赢？是否需要 CAS、唯一约束或版本号？
- 一个入口读到旧事实，另一个入口刚提交新事实时，会不会越权执行？
- 一个入口先改派生索引、后改 DB，或者先弹出 Redis、后投 MQ，中途失败会怎样？
- 旧消息、重复消息、延迟消息到达时，是否仍能被当前事实拦截？
- 外部接口已经调用但本地结果未知时，重试会导致重复副作用还是漏处理？

### 4. 给每个冲突选择保护机制

按语义选择机制，不要用一个锁覆盖所有问题。

| 语义 | 优先机制 | 注意点 |
| --- | --- | --- |
| 防重复创建 | DB 唯一约束、幂等键 | Redis 锁只能减压，不能替代唯一约束 |
| 状态流转互斥 | 状态 CAS、版本号、事务内更新 | 更新条件必须包含旧状态 |
| 同主体单飞执行 | 租约 + DB 在途字段 / 状态 CAS | 租约过期后仍要靠 DB 防第二条在途 |
| 全局或局部排序 | 单调序列、稳定排序键 | 序列空洞通常可接受，不要强求连续 |
| 派生索引一致 | DB 为事实源 + 回灌任务 | Redis/MQ 丢失后必须能从 DB 重建 |
| 删除/暂停可见性 | 状态过滤、二次查库 | 已投递消息不能只靠投递前判断 |
| 外部副作用幂等 | 外部幂等键、调用前标记、结果恢复策略 | 区分未调用、已调用、结果未知 |
| 失败重试 | retry_count、退避、终态兜底 | 避免无限重试和重复副作用 |
| 聚合最终一致 | 事件补偿、定时重算、缓存失效 | 区分内部终态和外部展示口径 |

### 5. 分层事实源

明确每个字段或组件属于哪一层。

```text
持久事实：DB 状态、业务运行态、唯一约束、终态记录
派生索引：Redis ZSET、缓存、搜索索引、预计算聚合
暂态控制：MQ payload、lease token、扫描批次、线程内变量
外部事实：第三方接口副作用、回调结果、客户已触达状态
```

经验规则：

- 派生索引丢失后必须能由持久事实重建。
- 暂态控制过期或重复后必须能被持久事实拦截。
- 外部事实不可回滚时，本地必须记录“可能已发生”的保守状态。
- 一个字段不要同时承担两个互相独立的不变量；例如“频控到期”和“当前是否有在途执行”应拆开表达。

### 6. 推演关键竞态

至少覆盖这些竞态族：

- 创建 vs 创建：重复生成、重复占位、序列空洞、事务回滚。
- 创建 vs 扫描：新对象刚提交或未提交时是否会被扫到。
- 扫描 vs 扫描：多实例是否重复投递同一主体。
- 扫描 vs 消费：lease 过期、MQ 重复、旧消息到达。
- 消费 vs 删除/取消：已 claim 但未外呼、已外呼但未回写、回写时已取消。
- 暂停 vs 消费：暂停后新工作是否还能继续，已开始工作是否允许补完。
- 恢复 vs 消费：恢复排序、可见性、是否插队。
- 超时恢复 vs 正常回写：卡死检测是否会覆盖刚完成的结果。
- 补偿任务 vs 主链路：补偿是否绕过统一锁、统一 CAS 或统一可见性判断。
- 迁移/回滚 vs 旧消息：旧 payload 到达新 Consumer、新状态被旧代码读取。

用时序写出最危险的交错：

```text
T0: A 读取旧状态
T1: B 修改状态并提交
T2: A 基于旧状态继续执行
T3: A 回写结果

风险：A 是否越过了 B 的新状态？
保护：A 在 T2 或 T3 必须二次查库 / 状态 CAS / token 校验。
```

### 7. 补偿与恢复检查

对每个“先拿走、后处理”的动作都要问：如果中途失败，谁把对象放回来？

必须检查：

- DB 提交成功但 Redis/MQ 写入失败。
- Redis 已弹出但 MQ 投递失败。
- MQ 已投递但 Consumer 宕机。
- Consumer 已 claim 但外部接口未调用。
- 外部接口已调用但本地结果未知。
- 本地已回写但缓存/聚合未更新。
- lease 过期但 DB 仍显示在途。
- 补偿任务误判时是否会破坏终态。

输出补偿策略时写清楚：

- 事实源：补偿从哪里读可信事实。
- 候选条件：扫描哪些状态、时间、版本或在途字段。
- 修复动作：改回等待、转终态、补冻结、重建索引、重新入队。
- 上限治理：最大重试次数、退避时间、告警、人工介入条件。

最终输出使用这个结构：


注意把结论写成“方案补充项”，便于直接追加到 proposal/design/review 文档里。

## 常见误区

- 只写“加分布式锁”，但没有 DB 唯一约束或状态 CAS。
- 用 Redis 锁表达业务事实，锁丢失后无法从 DB 恢复。
- 扫描前判断可发送，实际发送前不二次确认。
- 把审计时间、展示时间或缓存值误用为调度事实。
- 要求序列连续，导致删除、回滚、失败后必须修补空洞。
- 补偿任务直接绕过主链路锁或状态机，制造第二套并发语义。
- 对外部接口结果未知时简单重发或简单失败，没有幂等键、保守标记和次数上限。
- 新增内部终态后，遗漏聚合、缓存、终态判断和旧代码兼容。

## 简短示例

如果需求是“同一账号同一时刻最多发送一条消息，并且两次发送间隔不少于 N 秒”，不要只用一个 `next_time` 字段证明并发安全。

更稳妥的分析是：

- `next_time` 只证明频控，不证明当前没有在途发送。
- 需要额外的在途事实，例如 `current_message_id` 或 `EXECUTING` 状态 CAS。
- Scanner 的租约只能防重复投递，不能防 lease 过期后的第二次 claim。
- Consumer 发送前必须二次确认消息和任务仍可见。
- Consumer 宕机后需要 StuckDetector 或等价补偿释放在途事实，并按外部调用是否可能发生决定是否保守等待。
