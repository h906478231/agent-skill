# 上轮闭环验证（所有评审角色共用）

> 本文件是「重走门禁时如何验证上轮 Blocker 是否真的闭环」的**唯一事实源**。角色提示词、SKILL.md、命令、workflow 脚本一律引用本文件，不复制。
> 路径：`<SKILL_DIR>/shared/closed-loop-verification.md`

## 什么时候执行本节

仅当 `design.md` 末尾存在 `## 评审意见闭环记录` 区块时执行 —— 该区块的存在说明这是**重走门禁**，上一轮提过问题、作者已回改。

**必须先做本节验证，再做角色审查清单。** 你是全新上下文，没有上轮记忆：不先读该区块，你要么重复报告同一个问题（让作者觉得改了也没用），要么完全漏掉「作者声称改了但其实没改」的情况。

## 闭环记录的格式

`design.md` 末尾的区块每行记录一条历史 finding：

```
finding ID | 维度 | 原始问题 | 处理方式 | 落在 design 的哪一节 | 轮次
```

## 验证方法

只处理「维度」属于**你这个角色**的行。对每一行：按「落在 design 的哪一节」翻到 `design.md` 对应章节，核实改动**是否真的落地**、且**是否真正解决了原始问题**。

判定按下表，同时必须满足角色提示词中给出的「本维度闭环判据」—— 那是本维度特有的、比通用标准更严的验收线（例如并发要能指出幂等键、性能要重新算一遍数）：

| 情况 | 处理 | 本轮 findings 表中的 `闭环状态` |
|------|------|------------------------------|
| **已真正闭环** | 不要重复报告。在输出的「上轮闭环验证」小节记为「已闭环」，并指出依据的 design 章节 | 已闭环的 Blocker 与 Major 写入台账，状态 `closed`，处理依据写设计位置或任务编号；不再进 Findings |
| **假闭环** —— 声称已改但 design 查无对应内容，或改动不足以解决原始问题 | **沿用原 finding ID** 重新报告，严重级别保持 `Blocker`，在「一句话白话」中写明「上轮声称已闭环但实际未闭环」 | `open` |
| **risk accepted / 驳回 / 移到后续变更** | 尊重该决策，不再作为 Blocker 重复报告。若你认为其决策依据已不成立（前提条件变了），沿用原 ID 改为 `open`，依据变化后的后果定级并说明变化点 | `risk-accepted`（驳回则为 `false-positive`）；依据不再成立而重报时改回 `open` |

本轮**新发现**的问题使用新 ID，不得与闭环记录中的历史 ID 冲突。

## 输出要求

在 findings 表格**之前**先写一节：

```markdown
## 上轮闭环验证

| 历史 finding ID | 结论 | 判断依据 |
|----------------|------|---------|
| CONC-02 | 已闭环 | §4.1 已给出 msg_id 唯一索引与 CAS 更新条件 |
| PERF-03 | 未闭环 | §5.2 措辞改为「批量写入」但未给批大小，复算后端到端仍超 SLO |
| SEC-01 | risk accepted 沿用 | 暴露面未变化，接受该决策 |
```

**未闭环的项必须同时作为 finding 出现在下方 findings 表格中，且 `闭环状态` 标为 `open`**，否则汇总时不会计入裁决。

不在本轮范围内的开放 Blocker 按原 ID 与完整字段留在 Findings，除非已有可核对的同 ID 处理依据。关闭或处理 Blocker / Major 前，同份报告保留完整原发现及对应处理记录。发布前逐 ID 核对旧台账、开放台账与 Findings、旧开放 Blocker 的处理依据和留存正文；不能用行数代替，不核对两个当轮附录。旧报告无台账时，以旧 Findings 的开放 Blocker 与 Major 作为迁移依据。

## 重走时的评审范围

首轮审 proposal 与 design 全文。重走先验证上轮闭环，再按核对通过的范围审查。先固定本轮 proposal、design、tasks 及全部 specs 的原文、文件集合与原始 SHA-256；核对和分发使用同一份输入。

- 定稿前，读取 `design.md` 末尾「评审意见闭环记录」的「落在 design 的哪一节」列。优先只修 Blocker，但每处实质修改都登记；非 finding 引起的修改使用 `自改-R<n>`，维度写受影响维度或「全部」。定稿前已选择修复的条件落点另按 `gate-policy.md` 第 5 节登记。
- 定稿后，主会话或 workflow 调用方从「定稿与签字后修改」表摘出 `文件:行号`。子 agent 不读取 `review-summary.md` 或其他维度的报告。只有登记覆盖通过、位置依据的完整文件集合与逐文件哈希等于本轮固定输入时，才把位置作为纯文本注入提示词。旧版本的位置列表不得沿用。
- 对每个维度，以该维度最后一次完成评审的版本为依据，核对旧正文与留存哈希，再逐处对照登记与实质差异，含新增或删除文件。仅排除 `gate-policy.md` 第 5 节定义的任务进度。新哈希只证明本次版本，不证明登记覆盖。
- 漏登记、旧正文与哈希不符、旧输入不可用或无法核对时，不沿用受影响维度的报告，也不限范围，恢复 proposal 和 design 全文评审；影响不明时全量评审全部纳入维度。主会话同时核对 specs、tasks 与设计和提案的行为一致；无行为依据时停止，先补齐规划。运行假设变化按 `gate-policy.md` 第 2 节全量重走。
- 先按 `finding-format.md` 硬规则 4 核对缺码或错码。范围外新发现只有是带有效代码的 Blocker，且被本次已登记修改波及，或是正常使用 `[T1]` / 外部输入 `[T4]` 导致数据损坏或外部安全越权，才进 Findings。其余写「建议」，不计入裁决。上轮仍开放的条目不按新发现分流。

## 实现后双轴评审的差异

`/opsx:quality` 重跑时也按本文件做上轮闭环验证，但闭环来源与记录位置不同：

- **闭环来源**：本轴上一轮报告的 `## Finding 台账` 中 `open` 的行（不是 `design.md` 的闭环记录区块）。核实对象是代码与测试，不是 design 章节。
- **已闭环项写入台账**：把该行 `状态` 改为 `closed`，填 `闭环轮次`，`闭环依据` 写实现位置 `文件:行号` 或覆盖它的测试名。已闭环项**不再放进 Findings 表**，只留在台账中。台账行不删除。
- **报告原地覆盖**：重跑覆盖上一轮报告，不生成 `-roundN` 副本；轮次历史由台账保留（格式见 `../openspec-code-quality/shared/dual-axis-review.md`「原地覆盖与 Finding 台账」）。
- **门禁外提交**：修复代码不是通过 `/opsx:apply` 提交时（`classify --from <上一轮基线 Fingerprint>` 的 `unregistered` 中有其他文件：只在新增并已勾选的任务内修改的文件不算，勾选之后又有修改时照常登记，修改与任务对应不上或拿不准时照常登记，判断方法见登记步骤 6），先按档位登记到 `tasks.md` 的 `## 实现后修改登记`，`行为` 档位同时新增任务并写明提交 SHA 或文件，再开始下一轮评审（规则见 `../openspec-apply-change/shared/post-implementation-changes.md`）。闭环依据必须指到该提交中的具体行。
