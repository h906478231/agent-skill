# 上轮闭环验证（所有评审角色共用）

> 本文件是「重走门禁时如何验证上轮 Blocker 是否真的闭环」的**唯一事实源**。角色提示词、SKILL.md、命令、workflow 脚本一律引用本文件，不复制。
> 路径：`<SKILL_DIR>/shared/closed-loop-verification.md`

## 什么时候执行本节

仅当 `design.md` 末尾存在 `## 评审意见闭环记录` 区块时执行 —— 该区块的存在说明这是**重走门禁**，上一轮提过问题、作者已回改。

**必须先做本节验证，再做角色审查清单。** 你是全新上下文，没有上轮记忆：不先读该区块，你要么重复报告同一个问题（让作者觉得改了也没用），要么完全漏掉「作者声称改了但其实没改」的情况。

## 闭环记录的格式

`design.md` 末尾的区块每行记录一条历史 finding：

```
finding ID | 维度 | 原始问题 | 处理方式 | 落在 design 的哪一节 | 轮次
```

## 验证方法

只处理「维度」属于**你这个角色**的行。对每一行：按「落在 design 的哪一节」翻到 `design.md` 对应章节，核实改动**是否真的落地**、且**是否真正解决了原始问题**。

判定按下表，同时必须满足角色提示词中给出的「本维度闭环判据」—— 那是本维度特有的、比通用标准更严的验收线（例如并发要能指出幂等键、性能要重新算一遍数）：

| 情况 | 处理 |
|------|------|
| **已真正闭环** | 不要重复报告。在输出的「上轮闭环验证」小节记为「已闭环」，并指出依据的 design 章节 |
| **假闭环** —— 声称已改但 design 查无对应内容，或改动不足以解决原始问题 | **沿用原 finding ID** 重新报告，严重级别保持 `Blocker`，在「一句话白话」中写明「上轮声称已闭环但实际未闭环」 |
| **risk accepted / 驳回** | 尊重该决策，不再作为 Blocker 重复报告。若你认为其决策依据已不成立（前提条件变了），可降级为 `Major` 并说明变化点 |

本轮**新发现**的问题使用新 ID，不得与闭环记录中的历史 ID 冲突。

## 输出要求

在 findings 表格**之前**先写一节：

```markdown
## 上轮闭环验证

| 历史 finding ID | 结论 | 判断依据 |
|----------------|------|---------|
| CONC-02 | 已闭环 | §4.1 已给出 msg_id 唯一索引与 CAS 更新条件 |
| PERF-03 | 未闭环 | §5.2 措辞改为「批量写入」但未给批大小，复算后端到端仍超 SLO |
| SEC-01 | risk accepted 沿用 | 暴露面未变化，接受该决策 |
```

**未闭环的项必须同时作为 finding 出现在下方 findings 表格中**，否则汇总时不会计入裁决。
