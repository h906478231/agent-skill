# finding 统一格式（所有评审角色共用）

> 本文件是 finding 字段与维度结论的**唯一事实源**。角色提示词、SKILL.md、命令、workflow 脚本一律引用本文件，不复制。
> 路径：`<SKILL_DIR>/shared/finding-format.md`

## 字段

每条 finding 必须含以下 7 个字段，缺一不可：

| 字段 | 内容 |
|------|------|
| `ID` | 维度前缀 + 序号，如 `ARCH-01`。前缀见各角色提示词，不得与历史 ID 冲突 |
| `严重级别` | `Blocker` / `Major` / `Minor` |
| `位置` | 指向 `design.md` 的具体章节（实现层评审则指向 `文件:行`） |
| `一句话白话` | 用大白话说清「哪里会出什么事」 |
| `触发场景` | 什么条件下会真的发生 |
| `不修的后果` | 影响面 + 严重度 |
| `建议修复` | 具体到可执行的动作 |

表格写法：

```markdown
| ID | 严重级别 | 位置 | 一句话白话 | 触发场景 | 不修的后果 | 建议修复 |
|----|---------|------|-----------|---------|-----------|---------|
| CONC-01 | Blocker | §4.1 幂等设计 | 同一条消息被消费两次，计数会多加一次 | MQ 至少一次投递下消费者超时后重投；两个消费者同时处理同一 msg_id，都读到 count=5，都写 count=6 | 客户看到的联系人总数偏大，且无法自愈，需人工对账修数 | 给 msg_id 加唯一索引，写入用 `UPDATE ... WHERE version=?` 判 affected=1 |
```

## 三条硬规则

这三条是为了让**没参与设计的人**也能判断问题真伪与轻重 —— 门禁的读者不只是方案作者。

### 1. 「一句话白话」不得出现未解释的专有名词

写给不了解本方案细节的人看。出现幂等、CAS、IDOR、N+1、公式注入这类词时，要么换成大白话，要么当场用半句话解释。

- ✅ 「同一条消息被消费两次，计数会多加一次」
- ❌ 「幂等性缺失导致 at-least-once 语义下状态机非幂等累加」

### 2. 「触发场景」必须可复现，写不出来的 Blocker 一律降级为 Major

必须说清这四类中至少一类的具体取值，并写出**可观测的现象**（报错信息、数据错乱的表现、超时、内存增长）：

| 触发维度 | 要写清什么 |
|---------|-----------|
| 输入 | 什么参数 / 什么文件 / 什么字符 |
| 时序 | 谁和谁并发、按什么顺序交错 |
| 数据量 | 多少条 / 多大 / 什么增长速度 |
| 故障 | 超时、重启、网络抖动、部分成功 |

**只能写出「理论上可能有风险」而给不出具体触发场景的，不得判 Blocker，降级为 Major 并注明「触发条件未确认」。**

这条规则同时解决两个问题：一是逼着评审说人话而不是堆术语；二是压住 AI 误报 —— 编不出复现路径的问题，多半本来就不成立，不该卡住整个变更。

### 3. 「不修的后果」不写空话

要写影响面（哪些用户 / 哪些数据 / 哪个接口）+ 严重度（能否自愈、要不要人工修数、是否有数据泄露）。

- ✅ 「客户看到的联系人总数偏大，且无法自愈，需人工对账修数」
- ❌ 「可能影响数据准确性」

## 维度结论（verdict）

每份评审末尾给出该维度结论，三值之一：

| 结论 | 含义 |
|------|------|
| `通过` | 无 Blocker，可进入下一步 |
| `有条件通过` | 无 Blocker，但存在必须落地的前提条件 |
| `打回` | 存在未闭环 Blocker |

- 存在未闭环 Blocker（含「上轮声称已闭环但实际未闭环」）时，结论**必须**为 `打回`，并单独列出 Blocker 清单。
- **「有条件通过」的每一条条件都必须能映射到 `tasks.md` 的一个可勾选任务项**；映射不上的条件视同 Blocker —— 它没有落地路径，写完就没人管。

## 输出骨架

```markdown
# <维度>评审（<Change Name>）

## 上轮闭环验证        ← 仅重走门禁时，见 shared/closed-loop-verification.md

## Findings
| ID | 严重级别 | 位置 | 一句话白话 | 触发场景 | 不修的后果 | 建议修复 |

## 本维度特有内容      ← 如性能的容量估算、数据库的 DDL 要点

## <维度>评审结论：通过 / 有条件通过 / 打回
### 进入实现前必须闭环的 Blocker
### 有条件通过的条件（须映射 tasks.md）
```
