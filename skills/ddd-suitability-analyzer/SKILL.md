# DDD 适用性判定分析器

> 本 skill 帮助团队在投入 DDD 建模前，快速评估目标业务领域是否真正适合 DDD，避免过度设计或设计不足。

## 定位与目标

**目标**：通过结构化的评估维度，判断业务领域是否应该采用 DDD 建模，以及应该采用哪种级别的 DDD 实践。

**不做什么**：
- 不执行具体的 DDD 建模工作（由 `ddd-modeling-workflow` 负责）
- 不生成领域模型文档（由 `ddd-architect` 调度）
- 不做技术架构设计（聚焦业务复杂度判断）

**输入**：业务需求描述、现有代码路径（可选）、团队背景（可选）

**输出**：
1. **适用性评分报告**（0-100 分，分级建议）
2. **详细维度分析**（业务复杂度、技术复杂度、团队契合度）
3. **推荐方案**（完整 DDD / 轻量 DDD / 传统分层 / 其他模式）
4. **风险提示**（过度设计风险 / 设计不足风险）

---

## 执行流程

### 阶段 1：业务复杂度评估（权重 60%）

这是判断是否适合 DDD 的**最核心维度**。如果业务复杂度不够，DDD 是过度设计。

#### 评估维度 1.1：业务规则密度（25 分）

**评分标准**：

| 分数段 | 特征描述 | 典型示例 |
|--------|---------|---------|
| 20-25 分 | • 业务规则 > 10 条且相互关联<br>• 规则之间有冲突需要协调<br>• 规则频繁变化（月级别）<br>• 需要领域专家深度参与 | • 保险承保规则引擎<br>• 促销折扣叠加计算<br>• 信贷风控评分模型 |
| 10-19 分 | • 业务规则 5-10 条<br>• 规则相对独立<br>• 规则变化频率中等（季度级别）<br>• 业务逻辑有一定复杂度 | • 订单审核流程<br>• 会员等级升降级<br>• 库存分配策略 |
| 5-9 分 | • 业务规则 < 5 条<br>• 规则简单清晰<br>• 规则变化少（年级别或不变） | • 用户注册验证<br>• 文件上传处理<br>• 简单状态流转 |
| 0-4 分 | • 几乎没有业务规则<br>• 纯 CRUD 操作<br>• 数据管理为主 | • 配置项管理<br>• 日志记录<br>• 字典维护 |

**判定问题**：
1. 如果让业务专家描述这个功能，会用多少个"如果...那么...除非..."？
2. 业务规则之间有冲突或优先级关系吗？
3. 规则变化频率如何？谁能决定规则变化（技术 or 业务）？
4. 代码评审时需要业务专家参与吗？

#### 评估维度 1.2：领域概念丰富度（15 分）

**评分标准**：

| 分数段 | 特征描述 | 典型示例 |
|--------|---------|---------|
| 12-15 分 | • 领域概念 > 8 个且关系复杂<br>• 有清晰的领域语言（Ubiquitous Language）<br>• 概念之间有聚合/组合/关联关系<br>• 业务人员能自然理解这些概念 | • 订单履约（订单/库存/物流/售后/结算）<br>• 保险理赔（保单/险种/责任/理赔/核赔）<br>• SOP 流程（任务/步骤/触发器/守卫/执行单元） |
| 6-11 分 | • 领域概念 4-8 个<br>• 有一定的业务术语<br>• 概念关系相对简单 | • 会话管理（会话/消息/成员/权限）<br>• 自动回复（规则/匹配/模板/变量） |
| 3-5 分 | • 领域概念 2-3 个<br>• 术语简单直白<br>• 主要是技术概念 | • 任务调度（任务/执行记录）<br>• 文件上传（文件/分片） |
| 0-2 分 | • 几乎没有领域概念<br>• 纯技术实体 | • 日志表<br>• 配置表 |

**判定问题**：
1. 能列出多少个核心的业务概念（非技术术语）？
2. 这些概念之间有什么关系？（一对多/组合/关联/依赖）
3. 业务人员能直接理解这些概念吗？还是需要技术翻译？

#### 评估维度 1.3：业务不变量复杂度（10 分）

**评分标准**：

| 分数段 | 特征描述 | 典型示例 |
|--------|---------|---------|
| 8-10 分 | • 跨多个实体的一致性约束<br>• 非平凡的聚合边界判定<br>• 需要事务一致性保证<br>• 违反不变量会导致业务损失 | • 库存扣减（超卖防护、预留、释放）<br>• 账户余额（并发转账、透支控制）<br>• 课程选课（容量、冲突、依赖） |
| 4-7 分 | • 单实体内的一致性约束<br>• 状态转换有约束<br>• 有业务完整性要求 | • 订单状态机（待支付→已支付，不可逆）<br>• 会员升级（积分达标且未过期） |
| 2-3 分 | • 简单的字段约束<br>• 外键约束 | • 手机号格式验证<br>• 必填字段检查 |
| 0-1 分 | • 几乎没有约束 | • 自由文本输入 |

**判定问题**：
1. 有哪些数据必须同时成功或同时失败？
2. 违反一致性约束会导致什么后果？（业务损失 or 数据不一致）
3. 一致性边界在哪里？（单表 / 多表 / 跨服务）

#### 评估维度 1.4：业务生命周期复杂度（10 分）

**评分标准**：

| 分数段 | 特征描述 | 典型示例 |
|--------|---------|---------|
| 8-10 分 | • 状态机 > 5 个状态<br>• 状态转换伴随复杂的副作用<br>• 需要业务补偿逻辑<br>• 有丰富的业务语义 | • 订单取消（退款、库存恢复、积分回退）<br>• 合同终止（违约金、结算、存档）<br>• SOP 流程（激活/暂停/恢复/完成，含子任务协调） |
| 4-7 分 | • 状态机 3-5 个状态<br>• 状态转换有一定业务逻辑<br>• 副作用相对简单 | • 工单流转（待处理/处理中/已完成/已关闭）<br>• 文章审核（草稿/待审/已发布/已下架） |
| 2-3 分 | • 状态机 2-3 个状态<br>• 状态转换简单 | • 任务执行（PENDING→RUNNING→DONE）<br>• 开关状态（启用/禁用） |
| 0-1 分 | • 无状态或单向状态<br>• 纯技术状态 | • 上传状态（上传中→完成）<br>• 消息发送（发送中→成功） |

**判定问题**：
1. 有多少个业务状态？状态转换路径有多少条？
2. 状态转换时需要做什么？（仅改状态 or 有副作用）
3. 状态转换的触发条件是什么？（简单条件 or 复杂规则）
4. 业务人员会关心状态转换的语义吗？

---

### 阶段 2：技术复杂度评估（权重 20%，扣分项）

**重要说明**：技术复杂度高**不是** DDD 的理由，反而可能是过度设计的信号。本阶段是**扣分评估**。

#### 评估维度 2.1：是否主要是技术挑战（扣 20 分）

**扣分标准**：

| 特征 | 扣分 | 说明 |
|------|------|------|
| 核心挑战是高并发调度 | -15 分 | 如：秒杀、抢红包、群发调度 → 更适合任务调度框架 |
| 核心挑战是分布式一致性 | -10 分 | 如：分布式事务、最终一致性 → 更适合 SAGA/事件驱动 |
| 核心挑战是性能优化 | -10 分 | 如：查询优化、缓存设计 → 更适合 CQRS/读写分离 |
| 纯状态机协调（无业务语义） | -15 分 | 如：任务状态流转（PENDING→RUNNING→DONE） |
| 主要是协议转换/适配 | -10 分 | 如：接口网关、消息转换 → 更适合 Adapter 模式 |

**判定问题**：
1. 如果需求变更，主要改的是业务规则还是技术实现？
2. 核心难点在业务逻辑理解还是技术架构设计？
3. 代码评审的重点是业务正确性还是技术方案？

#### 评估维度 2.2：是否 CRUD 密集（扣 10 分）

**扣分标准**：

| 特征 | 扣分 | 说明 |
|------|------|------|
| 80% 以上是 CRUD 操作 | -10 分 | 主要是数据管理，业务逻辑少 |
| 读多写少（读写比 > 10:1） | -5 分 | 更适合查询优化，非 DDD |
| 纯配置管理 | -10 分 | 字典、配置项等 |

---

### 阶段 3：团队与项目契合度评估（权重 20%）

#### 评估维度 3.1：团队 DDD 能力（10 分）

**评分标准**：

| 分数段 | 特征描述 |
|--------|---------|
| 8-10 分 | • 团队有 DDD 实践经验<br>• 有领域专家支持<br>• 认同 DDD 理念 |
| 4-7 分 | • 团队愿意学习 DDD<br>• 有一定 OOP 基础<br>• 有时间学习成本 |
| 0-3 分 | • 团队无 DDD 经验<br>• 抵触复杂设计<br>• 项目紧急交付 |

#### 评估维度 3.2：项目规模与周期（10 分）

**评分标准**：

| 分数段 | 特征描述 |
|--------|---------|
| 8-10 分 | • 长期维护项目（> 2 年）<br>• 需求持续演进<br>• 多团队协作 |
| 4-7 分 | • 中期项目（6 个月 - 2 年）<br>• 需求相对稳定 |
| 0-3 分 | • 短期项目（< 6 个月）<br>• 一次性需求<br>• PoC / MVP |

## 综合评分与判定

### 评分计算公式

```
总分 = 业务复杂度得分（60 分）
     + 技术复杂度扣分（-20 ~ 0 分）
     + 团队契合度得分（20 分）
```

### 分级建议

| 总分范围 | 适用性评级 | 推荐方案 |
|---------|----------|---------|
| **70-100 分** | 🔥 **强烈推荐 DDD** | **完整 DDD 建模**<br>• 聚合根 + 领域事件 + Repository<br>• 领域服务 + 应用服务分层<br>• 事件溯源（可选）<br>• 建议投入时间：前期 30%-40% 用于建模 |
| **50-69 分** | 🔶 **适合轻量 DDD** | **轻量 DDD 实践**<br>• 核心域用聚合根 + Repository<br>• 不必完整事件建模<br>• 状态机 + 领域服务<br>• 建议投入时间：前期 15%-20% 用于设计 |
| **30-49 分** | ⚠️ **谨慎使用 DDD** | **传统分层架构**<br>• Controller + Service + Repository<br>• 提取关键业务逻辑到 Service<br>• 避免贫血模型，适当封装<br>• 可用设计模式：Strategy / State / Template Method |
| **0-29 分** | ❌ **不推荐 DDD** | **简化方案**<br>• CRUD + 基础校验<br>• 或采用其他模式：<br>  - 任务调度：Quartz / XXL-JOB<br>  - 状态机：Spring State Machine<br>  - 规则引擎：Drools / Easy Rules<br>  - 工作流：Activiti / Camunda |

## 使用示例

### 示例 1：群发任务（masstask）

**输入**：分析 lokra-ro/masstask（群发任务执行）是否适合 DDD

**评估结果**：

| 维度 | 得分 | 说明 |
|------|------|------|
| 业务规则密度 | 8 / 25 | 规则简单：选人、选内容、发送 |
| 领域概念丰富度 | 6 / 15 | 概念简单：任务/会话/消息 |
| 业务不变量复杂度 | 3 / 10 | 主要是技术一致性（幂等、冻结） |
| 业务生命周期复杂度 | 4 / 10 | 状态机简单，无复杂副作用 |
| 技术复杂度扣分 | -15 | 核心是高并发调度 |
| 团队契合度 | 12 / 20 | 长期项目，团队有能力 |
| **总分** | **18 / 100** | |

**结论**：❌ 不推荐 DDD

**推荐方案**：任务调度框架 + 状态机模式
- XXL-JOB / Quartz（定时调度）
- Spring State Machine（状态流转）
- Repository 模式（持久化）
- 分布式协调（Redis / Zookeeper）

### 示例 2：SOP 自动化流程

**输入**：分析 lokra-ro/sop（标准化运营流程）是否适合 DDD

**评估结果**：

| 维度 | 得分 | 说明 |
|------|------|------|
| 业务规则密度 | 22 / 25 | 规则密集：触发条件、守卫、动作编排 |
| 领域概念丰富度 | 13 / 15 | 概念丰富：流程/步骤/触发器/守卫/执行单元 |
| 业务不变量复杂度 | 8 / 10 | 流程完整性、执行约束 |
| 业务生命周期复杂度 | 9 / 10 | 复杂状态机 + 业务补偿 |
| 技术复杂度扣分 | -5 | 有一定调度需求，但业务占主导 |
| 团队契合度 | 15 / 20 | 长期项目，团队可学习 |
| **总分** | **77 / 100** | |

**结论**：🔥 强烈推荐 DDD

**推荐方案**：完整 DDD 建模
- 聚合根：SopTask / SopStep / SopExecution
- 领域事件：已激活 / 已触发 / 已执行 / 已完成
- Repository + 领域服务

## 常见误区

### 误区 1：复杂就要用 DDD

**错误认知**：系统很复杂，所以要用 DDD

**正确认知**：要区分业务复杂度和技术复杂度
- 技术复杂（高并发、分布式）→ 不是 DDD 的理由
- 业务复杂（规则密集、概念丰富）→ 才是 DDD 的理由

### 误区 2：有状态机就要用 DDD

**错误认知**：有状态流转就要建聚合

**正确认知**：要看状态转换是否有业务语义
- 纯技术状态（PENDING → RUNNING → DONE）→ State 模式足够
- 业务状态（待审核 → 审核通过 → 已发布，含审核规则）→ 考虑 DDD

### 误区 3：DDD 就是多建几个聚合

**错误认知**：把 DO 改名为 Entity，加个 Repository 就是 DDD

**正确认知**：DDD 的核心是业务规则内聚
- 聚合根封装业务不变量
- 领域服务表达业务规则
- 领域事件驱动业务流程
- 不是为了 DDD 而 DDD

### 误区 4：不用 DDD 就是贫血模型

**错误认知**：不用 DDD 就写不出好代码

**正确认知**：模式为业务服务，不是教条
- 简单业务用简单模式（CRUD + 基础封装）
- 复杂业务用复杂模式（DDD）
- 关键是适配，不是追求"先进"
